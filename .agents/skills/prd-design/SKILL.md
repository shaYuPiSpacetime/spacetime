# Spacetime PRD / 需求文档编写

本 skill 把 `docs/需求文档/标准/` 里的规范变成可执行流程。**规范内容以标准文件为准，本 skill 只负责编排顺序、强调铁律、在该停下时停下。** 不要把标准文件的内容默写一遍——按需读取它们。

## 标准文件（唯一事实源，按需读取）

| 文件 | 作用 | 何时读 |
|------|------|--------|
| `docs/需求文档/标准/README.md` | 导航 + 使用顺序 + 使用建议 | 开工先读 |
| `docs/需求文档/标准/00_PRD编写规范.md` | 总纲：12 条要求、ID 规范、字段/操作/状态/验收标准、反模式 | 开工必读 |
| `docs/需求文档/标准/10_模板_全局定义_共享层.md` | 共享层模板：术语/枚举/状态机/业务规则/第三方/错误码/接口（全项目唯一） | 写/改全局定义时 |
| `docs/需求文档/标准/11_模板_全局定义_端专属层.md` | 端专属层模板：菜单树/权限/UI 空态/文案（每端一份） | 写/改全局定义时 |
| `docs/需求文档/标准/20_模板_模块PRD.md` | 模块 PRD 模板 | 每个模块开始时 |
| `docs/需求文档/标准/30_模板_页面规格.md` | 页面规格模板 | 每个页面一份 |
| `docs/需求文档/标准/05_PRD评审清单.md` | 定稿前逐项评审（P0 阻塞 / P1 加分） | 定稿前 |

## 正式版 PRD 前置事实源（强制）

写正式版 PRD（包括 `docs/需求文档/需求文档-正式版/` 下的模块 PRD、页面规格、前置准备清单，或用户明确要求"正式 PRD"、"正式版"、"PRD 固定流程"）时，开始写正文前必须读取：

| 文件 | 作用 | 处理要求 |
|------|------|----------|
| `docs/需求文档/PRD找茬确认问题清单.md` | 汇总已发现的 PRD 问题、冲突、遗漏和待确认口径 | 逐条处理；能根据既有资料闭环的直接回写到正式 PRD；超出一期范围的写入"本期不做/后续承接"；无法自行判断的必须停下来问用户 |
| `docs/需求文档/一期上线目标.md` | 控制一期交付范围、功能边界和优先级 | 所有正式 PRD 范围必须对齐一期目标；超范围需求不得写成一期必做，只能标为本期不做、后续承接或待用户拍板 |

强制规则：
- 这两个文件缺失、不可读，或找茬清单中存在无法自行决定的问题时，必须先向用户确认；确认前不得开始写正式 PRD 正文。
- 找茬清单提出的问题必须全部有处理结论：`已解决`、`本期不做/后续承接`、`需用户确认`、`不采纳及原因`，不得遗漏。
- 正式 PRD 的范围、页面、字段、状态和验收标准必须能追溯到一期上线目标；不确定是否属于一期时，按 Decision Gate 询问用户。

## 核心理念

PRD 不是"功能描述"，是"决策集合"。凡是能被合理追问"到底是哪一个？"的点，都必须在 PRD 里拍死。没写死的地方，AI 会随机猜，UI 会按自己理解画，分歧最终堆到开发期爆炸。

## 产出物路径

- 全局定义：`docs/需求文档/{端}/全局定义_共享层.md`、`docs/需求文档/{端}/全局定义_端专属层.md`（项目级，复用已有则更新，不重建）
- 模块 PRD：`docs/需求文档/{移动端|管理后台}/{模块名}_模块PRD.md`
- 页面规格：`docs/需求文档/{移动端|管理后台}/页面规格/` 下按 `docs/需求文档/标准/30_模板_页面规格.md` 的命名规范落地；移动端使用 `APP-两位序号_页面名.md`，管理后台使用 `页面名.md`

目录不存在则创建。不要写进 `标准/` 文件夹（那里只放模板），不要写进隐藏目录、临时 plan、聊天摘要。

## 工作流

复制并维护此 checklist：

```markdown
PRD Design:
- [ ] Step 0: 读 README + 00 编写规范；正式版 PRD 还必须读 PRD 找茬确认问题清单 + 一期上线目标，先闭环问题并确认产出范围（哪些端、几个模块、几个页面）
- [ ] Step 1: 需求澄清，列待确认项，Decision Gate 等用户拍板
- [ ] Step 2: 更新全局定义（共享层 + 端专属层），新概念先在这里定 ID
- [ ] Step 3: 写模块 PRD（目标/范围/边界/流程/数据模型/依赖/页面清单）
- [ ] Step 4: 逐页写页面规格（字段表/操作表/联动/状态/验收）
- [ ] Step 5: 对照 05 评审清单逐项打勾，输出评审结论
```

## Step 0：定范围

读 `README.md` + `00_PRD编写规范.md`。先把产出范围问清楚，别上来就写：

如果是正式版 PRD，继续读取 `docs/需求文档/PRD找茬确认问题清单.md` 和 `docs/需求文档/一期上线目标.md`，先做前置处理：

1. 从找茬清单提取与当前模块/端/页面相关的问题，形成处理清单。
2. 逐条判断处理方式：已能闭环的写入 PRD；超出一期上线目标的放入"本期不做/后续承接"；无法自行判断的列入 Step 1 Decision Gate。
3. 用一期上线目标校准模块边界、页面范围、字段范围、状态范围和验收标准，禁止把二期/远期能力写成一期必做。
4. 在写正文前确认没有未处理的找茬问题；如仍有未决项，必须先问用户。

| 维度 | 必答问题 |
|------|----------|
| 端 | 管理后台 / 移动端 / 两者都要？ |
| 模块边界 | 这次写几个模块，模块号怎么分？ |
| 是新项目还是已有项目 | 新项目要先建全局定义；已有项目复用并扩展现有全局定义 |
| 交付物 | 只要 PRD，还是 PRD + 评审？ |

## Step 1：需求澄清 + Decision Gate（关键，别跳）

PRD 的价值就在于消除歧义。分析需求后，把所有"无法唯一推导"的点一次性列给用户，**等拍板再写**。这一步对应本项目最痛的教训——上一版 PRD 攒了 580 行待确认清单，全是这步没做。

正式版 PRD 的 Decision Gate 必须覆盖 `PRD找茬确认问题清单.md` 中无法自行闭环的问题；不能只问用户新需求里的歧义点。

```markdown
需求里以下点必须先拍板，否则写出来又是待确认清单：

🔴 必须确认（影响页面形态/字段范围/核心规则）
1. {如：核心准入/通过门槛到底是哪几项}
2. {如：某字段是否必填、枚举有哪些值}

🟡 建议确认（多方案选择）
3. {方案 A/B 各自影响}

🟢 风险提醒（不阻塞，记录在案）
4. {...}
```

规则：
- 🔴🟡 未拍板，对应内容在文档里标 `[待确认]`，**不要伪装成"默认假设"写死**。
- 拍板后回写正文，删除 `[待确认]`，并在文档变更记录登记。

## Step 2：先改全局定义（单一事实源）

任何新概念（术语、枚举、状态、角色、错误码、第三方、业务规则）先在全局定义里定 ID，页面规格只引用不复述。

- 跨端共享的（术语/枚举/状态机/业务规则/第三方/错误码/接口）→ **共享层**，全项目唯一一份，不在两端各写。
- 端内独有的（菜单树/权限矩阵/UI 空态/文案）→ **端专属层**，后台一份、移动端一份。
- 改已有全局定义时，**变更记录必须列出受影响的页面 ID**，并同步通知/更新引用方。

## Step 3：写模块 PRD

用 `20_模板`。这一层定方向和边界，不展开字段/操作细节。重点写全这几节（本项目上一版普遍缺）：
- 边界（本期不做）+ 处理方式（隐藏/置灰/空态/仅预留结构）→ 消灭"首版是否做 X"
- 关键业务流程（含分支和异常，不只顺流程）
- 核心数据模型 + 跨模块字段引用
- 非功能性需求（权限/安全合规/性能/并发幂等/埋点）
- 跨模块依赖 + 兜底

## Step 4：逐页写页面规格

用 `30_模板`，每页一份。三个最容易偷工的地方，必须写全：
- **字段表 10 列**：只写字段名 = 不合格。类型/必填/枚举/校验/默认/可编辑/敏感级别/来源都要有。
- **操作表**：行级/批量/页面级三类，每个含触发条件/权限/二次确认/成功态/失败态/影响。
- **状态穷举 6 类**：加载/空/错误/无权限/业务态（按状态机逐一）/降级。只写 happy path = 不合格。

每个核心功能配 Given/When/Then 验收标准（含异常路径），引用全局 ID。

## Step 5：对照评审清单打勾

用 `05_PRD评审清单.md`，产品/技术/一致性三维度逐项检查，输出评审结论表。P0 必须全过，P1 ≥ 80%。重点盯一致性维度（C）：是否有复述、术语是否统一、PRD 间是否矛盾。

## 核心原则（铁律）

- 不确定就停下来问，标 `[待确认]`，绝不把猜测写成定论。
- 字段只写名字 = 不合格；状态只写 happy path = 不合格；"待确认"遗留到定稿后 = 不合格。
- 共享层的东西只写一份，端专属层不复述。
- 新项目（如择业、高考志愿）没有现成全局定义时，Step 2 要从零建共享层 + 端专属层，别跳过直接写页面。

## 常见反模式（来自本项目踩坑）

| 反模式 | 正确做法 |
|--------|----------|
| 散文式叙述藏歧义 | 写死：哪几种、前置条件、互斥还是并行、失败能否切换 |
| 只写字段名 | 按 10 列表格写全 |
| 只写顺流程 | 补审核中能否改、驳回能否重提、超时、第三方处理中等状态 |
| 跨 PRD 各写一遍同一规则 | 抽进共享层 `GLB-RULE-xxx`，各处只引用 |
| "首版是否做 X" 满天飞 | 进"本期不做"清单，写明处理方式 |
| 权限一句话带过 | 角色 × 操作矩阵，每格填允许/禁止/脱敏/仅本人 |
| 定稿后仍留大量待确认 | 拍板回写正文；实在不能拍的标 `[阻塞]` + 负责人 + 截止日期 |
| 把 AI 预填的业务值当定论 | 预填值一律视为草案，未拍板标 `[待确认]` |
