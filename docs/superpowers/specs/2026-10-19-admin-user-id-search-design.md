# 管理后台用户 ID 统一搜索设计

## 目标

在管理后台现有“用户搜索”输入框中增加用户 ID 搜索能力，不新增独立筛选控件，并保持姓名、昵称、手机号、身份证和标签的既有搜索行为。

## 覆盖范围

- App 用户管理
- 实名认证审核
- 学历认证审核
- 头像认证审核
- 资料照片审核
- 文字内容审核

以上页面的输入框提示统一为：`用户ID/姓名/昵称/手机号/身份证/标签`。

## 当前状态

- 实名、学历和头像审核共用 `VerificationManagementPage` 与 `VerificationAdminServiceImpl`。后端已将纯数字关键词加入候选用户 ID，并继续匹配其他用户字段。
- 资料照片和文字审核共用 `ModerationPage` 与 `ModerationAdminServiceImpl`。后端同样已支持纯数字关键词精确匹配用户 ID。
- App 用户管理使用 `CustomersPage` 与 `AppUserAdminServiceImpl`。现有关键词覆盖昵称、学校、标签、手机号、OpenID、实名和身份证，但尚未在同一关键词条件中匹配用户主键。

## 方案选择

### 采用方案：扩展现有关键词查询

- 三个共用搜索输入框只更新提示文案，不增加新的状态字段或请求参数。
- App 用户管理在原关键词 OR 条件组中增加用户 ID 精确匹配。
- 只有关键词能安全解析为正整数 `Long` 时才添加用户 ID 条件。
- 数字关键词仍保留手机号等既有模糊匹配，因此不会因支持用户 ID 而破坏手机号搜索。

### 未采用方案

1. 前端识别数字并改发独立 `userId` 参数：会让纯数字关键词从“多字段搜索”变成“只按 ID 搜索”，容易破坏手机号片段匹配。
2. 抽取新的跨模块用户搜索解析服务：能够统一实现，但本次只有 App 用户管理缺少后端条件，重构范围超过需求。

## 数据流

1. 管理员在现有“用户搜索”输入框输入关键词。
2. 前端继续使用当前 `keyword` 参数请求分页接口。
3. 审核模块沿用现有用户 ID 候选集合逻辑。
4. App 用户管理判断关键词是否为可解析的正整数：
   - 是：在原多字段 OR 条件中追加 `app_user.id = 关键词`。
   - 否：仅执行既有多字段匹配。
5. 其他筛选条件、分页、排序和权限逻辑保持不变。

## 边界与异常处理

- 空白关键词不增加任何用户 ID 条件。
- 非数字关键词不尝试按用户 ID 查询。
- 超出 `Long` 范围的数字串不得抛出接口异常，按普通关键词继续执行原搜索条件。
- `0` 和负数不作为有效用户 ID 条件。
- 用户 ID 使用精确匹配，不做前缀或模糊匹配。

## 测试设计

按 TDD 顺序实施：

1. App 用户管理先增加失败测试，证明关键词 `1882` 尚未生成用户 ID 精确条件；实现后验证该条件与手机号等原条件同时存在。
2. 增加超长数字关键词测试，验证不会因数值溢出导致查询异常。
3. 补充实名认证/学历/头像共用服务的数字用户 ID 回归断言。
4. 补充资料照片/文字审核共用服务的数字用户 ID 回归断言。
5. 对三个前端页面增加静态门禁，确保提示文案均包含“用户ID”且仍使用原 `keyword` 参数。
6. 执行相关后端单元测试和前端构建。

## 验收标准

- 六个模块的“用户搜索”输入框均显示 `用户ID/姓名/昵称/手机号/身份证/标签`。
- 输入存在的用户 ID（例如 `1882`）后，各模块只返回该用户关联记录。
- 输入手机号、姓名、昵称、身份证或标签时，现有搜索结果不回退。
- 输入不存在的用户 ID 时返回空列表，不报错。
- 输入超出 `Long` 范围的数字串时接口不报数值转换异常。
- 本次不新增页面、不新增独立筛选项、不调整列表字段和其他筛选逻辑。
