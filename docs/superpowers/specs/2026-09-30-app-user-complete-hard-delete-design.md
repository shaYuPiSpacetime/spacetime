# App 用户完整物理删除设计

## 目标

后台“彻底删除用户”必须在一个数据库事务内删除指定 App 用户及其全部可识别业务数据。当前过程 `spacetime_delete_app_user_data` 停留在迁移 089，遗漏 PRD-03 消息中心相关表，导致用户主表删除后仍残留私信、悄悄话、通知和举报证据。

本次首个执行目标为后台显示的 `U821（小乔公主）`。执行前必须从目标数据库再次读取 `app_user.id = 821` 并核对昵称，不允许仅凭截图或同名记录删除。

## 方案

新增下一号生产迁移，完整重建 `spacetime_delete_app_user_data`，不修改已经执行过的历史迁移。过程继续由现有管理后台删除接口调用，保持 Controller、Service 和 DAO 契约不变。

删除范围在现有 089 基础上补齐：

- 旧版悄悄话 `app_whisper`。
- 私信会话、成员、消息、悄悄话申请、系统消息和官方助手消息。
- 消息事件收件箱、渠道投递箱和用户 TIM 账号。
- 与被删除用户、其消息、其悄悄话或其举报案件关联的举报冻结证据。
- 后续新增且存在直接用户引用的 App 业务表；官网 `website_*` 使用独立账号体系，不按相同数值 ID 误删。

对双方共享的数据采用“整条事实删除”：只要会话、消息、关系或举报证据任一侧属于目标用户，对应共享事实和依赖记录一并删除，避免留下能反向识别该用户的孤立数据。

## 删除顺序与事务

1. 校验目标用户恰好存在一条有效记录。
2. 用临时表固化社区帖子、评论、举报、消息会话、消息和悄悄话范围。
3. 先删叶子表：投递、冻结证据、消息记录、成员等。
4. 再删共享主表：会话、悄悄话、关系、社区内容等。
5. 删除单用户通知、TIM 账号、认证、设置、商业化和推荐数据。
6. 最后删除 `app_user` 主表。
7. 对关键用户引用表执行残留计数；任一计数非零时抛错，由现有 Spring 事务回滚全部删除。
8. 数据库过程成功后、Spring 事务提交前撤销该用户全部登录态，并写入现有脱敏操作审计；任一步失败都不得记录删除成功。

## 安全边界

- 未知表或不存在的兼容表通过 `information_schema` 检查后执行，保证不同迁移状态下可部署。
- 不删除 OSS 对象本体；数据库引用删除后由独立的对象生命周期任务清理，避免误删被其他事实引用的对象。
- 不删除全局消息规则、模板、运行配置和敏感访问审计；敏感访问审计仅保存管理员访问事实，不应被用户删除入口抹除。
- 不通过手机号、昵称或模糊条件删除，只接受已核验的内部用户 ID。

## 验证

- 数据库契约测试断言新迁移覆盖所有消息用户引用和残留校验。
- 后端单元测试继续验证：数据库清理失败时不撤销登录态、不写成功审计。
- 在目标环境先执行只读残留统计；确认 `U821` 身份后调用现有后台删除接口。
- 删除后再次按用户 ID、消息发送/接收方、会话双方、TIM 账号和举报证据查询，结果必须全部为零；同时确认其他用户主表仍存在。
