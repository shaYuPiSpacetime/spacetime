# 资料编辑与私信女性保护优化设计

## 目标

在不改变地址逻辑、不把业务后端放入普通私信发送链路的前提下，完成以下调整：

1. “爱听的歌曲”改为用户直接输入歌曲名称，不调用歌曲搜索或第三方歌曲接口。
2. 学校复用现有 `school_dictionary`、联想搜索接口及现有远端补全能力；用户必须选择联想结果，不能以纯手填名称作为保存结果。
3. 私信中对方头像和我方头像分别使用双方当前公开生效的个人头像。
4. 女性保护改为“一发一回”：保护期内男方可以发送一条消息；如果女方尚未回复，男方不能继续发送；女方回复后男方可再发送一条。
5. 普通私信继续由小程序直接调用腾讯 IM SDK，发送前不增加业务后端请求，也不依赖腾讯 IM“发单聊消息之前回调”。

## 不在本次范围

- 不调整现居地、家乡的省市/区县保存和展示逻辑。
- 不新建学校字典表，不重新采购或接入新的学校数据源。
- 不将普通私信改回“业务后端代发腾讯 IM”。
- 不提供对篡改客户端的强对抗能力；本次女性保护面向正式小程序客户端的正常使用流程。

## 已确认的现状

- 歌曲页面当前调用搜索接口并展示内置/供应方歌曲列表，保存请求强制要求 `songId`。
- 学校已经有 `school_dictionary`、关键词联想和远端结果回填，但组件允许用户不选择候选项直接保留手填名称。
- 私信对方头像已经从公开审核头像读取；我方消息气泡仍使用固定默认头像。
- 当前女性保护实现为“女方从未发过消息时，男方完全不能先发”；女方只要发过一次，后续男方可以连续发送。
- 普通私信当前由小程序直连腾讯 IM；发送后回调负责把消息异步归档到本地数据库。

## 方案选择

### 采用：直连腾讯 IM + 本地会话状态 + 数据库恢复

- 进入会话时，现有会话详情接口查询本地消息库，依据最后一条有效用户消息计算 `canSend`。
- 男方发送成功后，小程序立即把当前会话锁为“等待女方回复”，不等待发送后回调。
- 小程序收到女方实时消息事件后立即解锁输入框。
- 腾讯 IM“发消息之后回调”继续异步归档消息；重新进入会话时，以数据库中的最后一条有效消息恢复状态。
- 该方案不增加每条消息的前置网络跳数，保持当前直连发送速度。

### 不采用：腾讯 IM 发消息之前回调

该回调会把腾讯 IM 到业务后端的网络请求、业务校验和数据库读取放进发送关键路径。任何网络波动都会直接放大发送延迟，不符合当前体验优先目标。

### 不采用：业务后端代发

每条消息需要先调用业务接口，再由后端调用腾讯 IM，链路最长，且此前已出现明显发送延迟。

### 不采用：纯客户端、不读数据库

仅靠页面内存无法在重进页面、应用重启后恢复等待状态，也无法利用已经归档的回复记录。

## 详细设计

### 1. 歌曲名称输入

- 保留“爱听的歌曲”独立页面和导航，不再加载或展示歌曲列表。
- 页面只显示一个歌曲名称输入框和确认按钮。
- 输入内容去除首尾空格；空值不能保存；最大长度 100 个字符。
- 继续复用现有收藏歌曲保存接口，但请求只要求 `songName`。
- 保存时清空旧的 `favoriteSongId`、歌手和封面字段，避免历史第三方元数据与手填名称混用。
- 现有歌曲搜索接口暂不删除，避免影响其他潜在调用；小程序本页面不再调用它。

### 2. 学校必须选择字典项

- 继续复用现有 `SchoolSearchInput` 和 `/miniapp/dict/schools` 搜索接口。
- 用户输入时立即清空已选 `schoolCode`；只有点击某个联想候选项后才重新获得有效 `schoolCode`。
- 基本资料编辑和学历认证两个入口都必须同时具备 `schoolName` 与 `schoolCode` 才能提交。
- 没有选中候选项时，确认操作提示“请从搜索结果中选择学校”，不得保存纯手填内容。
- 后端保存时根据 `schoolCode` 查询现有 `school_dictionary`，以字典中的规范名称为准；编码不存在或名称不匹配时拒绝保存。
- 保留当前学校供应方按关键词补全并回写 `school_dictionary` 的能力，不增加新表或新数据源。

### 3. 私信双方真实头像

- 会话详情继续返回 `peerUser.avatarUrl`，来源保持为对方公开审核通过头像。
- 会话详情新增 `selfAvatarUrl`，同样通过公开头像服务读取当前用户的生效个人头像。
- 私信页收到的消息使用 `peerUser.avatarUrl`；发出的消息使用 `selfAvatarUrl`。
- 任一头像为空时才使用现有默认头像，不影响历史会话展示。

### 4. 女性“一发一回”保护

#### 服务端状态计算

- 仅当会话开启女性保护且仍处于保护期时应用该规则。
- 女方始终可以发送。
- 男方是否可发送由本地数据库最后一条有效用户消息决定。“有效用户消息”限定为 `app_message_record` 中发送成功、发送人与接收人均明确的私信文本或悄悄话请求/回复；系统模板、失败消息和撤回消息不参与判断：
  - 没有历史用户消息：允许男方发送第一条。
  - 最后一条由女方发送：允许男方发送一条。
  - 最后一条由男方发送：禁止继续发送，原因返回 `female_reply_pending`。
- 会话详情的女性保护对象新增：
  - `appliesToCurrentUser`：当前用户是否为受限制的男方。
  - `waitingForFemaleReply`：当前是否正在等待女方回复。
- 删除旧字段 `waitingForFemaleFirstMessage`，小程序与后端统一只使用 `appliesToCurrentUser` 和 `waitingForFemaleReply`，避免同一接口同时存在两套相反语义。

#### 小程序实时交互

- 男方点击发送时仍直接调用腾讯 IM SDK。
- 防止连点：一次发送请求完成前禁止再次触发发送。
- 发送成功后，如果女性保护适用于当前用户，小程序立即设置 `canSend=false`、`waitingForFemaleReply=true`，输入框保持锁定并提示“等待女方回复后可继续发送”。
- 发送失败时恢复输入内容和原发送权限，允许重试。
- 收到对方实时消息后立即设置 `canSend=true`、`waitingForFemaleReply=false`，无需等待数据库回调或重新请求会话详情。
- 页面重新进入、前后台恢复或重新连接时，通过会话详情接口从本地数据库恢复最终状态。

#### 数据归档

- 继续使用腾讯 IM“发消息之后回调”把双方消息写入本地消息表并更新会话最后消息投影。
- 归档不参与当前消息发送完成条件，不阻塞气泡展示和输入交互。
- 腾讯 IM“发单聊消息之前回调”可保持关闭。

#### 管理端说明

- 女性保护配置说明改为：“保护期内男方每发送一条消息后，需等待女方回复才能继续发送；仅影响启用保护的新会话。”
- 配置开关、保护天数及版本发布方式保持不变。

## 错误处理

- 歌曲名称为空：前端阻止提交，后端返回明确参数错误。
- 学校只有名称没有编码、编码不存在或名称与字典不一致：拒绝保存并提示重新选择。
- 会话详情读取最后消息失败：不伪造允许状态，返回接口错误；已打开页面保留当前本地状态。
- 腾讯 IM 发送失败：不进入等待女方回复状态，恢复输入和发送按钮。
- 头像为空或审核头像服务没有结果：仅该头像回退现有默认图。

## 测试策略

### 后端

- 收藏歌曲仅提交 `songName` 可以保存，并清理旧第三方元数据；空名称失败。
- 学校编码存在且名称匹配时通过；缺编码、未知编码、名称不一致时失败。
- 女性保护期内：无消息时男方可发、最后为女方时男方可发、最后为男方时男方被阻止、女方始终可发、保护期外不限制。
- 会话详情分别返回真实 `peerUser.avatarUrl` 和 `selfAvatarUrl`。

### 小程序与管理端

- 歌曲页不再调用搜索接口，只有名称输入与保存。
- 学校输入后未选择候选不能确认，选择候选后携带 `schoolCode`。
- 男方发送成功立即锁定；收到女方消息立即解锁；发送失败恢复。
- 发出消息使用 `selfAvatarUrl`，收到消息使用 `peerUser.avatarUrl`。
- 管理端女性保护文案与新规则一致。
- 执行后端定向单测、小程序现有消息/资料编辑回归脚本、小程序生产构建和管理端生产构建。

## 验收标准

1. 用户能够输入任意非空歌曲名称并保存，页面不再出现内置歌曲列表或搜索动作。
2. 学校必须来自现有联想结果，手填未选择不能保存。
3. 私信双方气泡头像与各自当前公开个人头像一致。
4. 保护期内男方可发送一条；女方未回复时无法继续发送；女方回复到达后立即恢复发送。
5. 普通私信发送仍为“小程序 -> 腾讯 IM SDK”，无每条消息的业务后端前置请求，发送速度不因保护规则增加网络等待。
6. 地址相关代码、接口和展示保持不变。
