# 商业化小程序与管理后台闭环实施计划

> **目标：** 按 APP-04、ADM-04 正式 PRD，完成千寻币真实接口闭环，并复核 VIP 共享支付与资产链路；生产运行路径不得依赖演示数据。

## 约束

- 小程序只验证微信小程序编译，不运行 H5 编译。
- 生产页面只消费后端接口；`lanhuDemo` 仅允许保留在明确的设计稿资料或静态校验中，不得作为接口失败、空列表或支付成功的兜底。
- 复用现有 Controller -> Service -> DAO -> Mapper 分层和权限注解，不跨 `miniapp`、`admin` 依赖。
- 资产变动必须在后端事务内完成，支付回调、主动确认、消费/解锁和退款回退按业务单号幂等。

## 任务拆分

### 任务 1：接口与数据契约门禁

- [ ] 阅读移动端和后台页面规格，核对 8 个千寻币消费场景、套餐、订单、流水、退款和对账字段。
- [ ] 新增小程序静态门禁，检查真实余额/流水/支付确认接口、无 demo 兜底、真实解锁接口和来源页回跳。
- [ ] 新增后台静态门禁，检查各菜单路由不再使用占位页、各查询/保存/退款/导出接口均有真实调用。
- [ ] 先运行门禁并记录预期红灯原因。

### 任务 2：后端千寻币资产闭环

- [ ] 补齐千寻币套餐、余额、流水、消费场景配置的移动端响应字段。
- [ ] 将千寻币支付订单接入真实创建、微信支付主动确认和回调入账；禁止前端直接增加余额。
- [ ] 修正资产扣减为带余额条件的原子更新，补充目标对象有效性、重复解锁、请求幂等和流水余额前后值。
- [ ] 将扣币价格改为消费场景配置，不保留硬编码单价；补齐 8 个场景映射和解锁记录。
- [ ] 为支付入账、扣币、重复回调/重复消费和余额不足补充后端单元测试或可执行门禁。

### 任务 3：小程序千寻币页面闭环

- [ ] `useCoins` 改为加载真实余额、套餐、流水和消费场景，保留加载、空态、失败重试。
- [ ] 充值页支付按钮调用真实微信支付参数，支付后调用确认接口并刷新余额/流水/结果承接页。
- [ ] 流水页只展示接口分页结果；充值结果、余额不足和业务解锁使用真实订单/资产接口。
- [ ] 删除生产路径中的模拟支付、演示余额、演示流水、假用途和前端加余额逻辑。
- [ ] 复核会员相关共享支付链路，确保 VIP 已支付后由后端确认状态，不因本次千寻币改造回归。

### 任务 4：管理后台闭环

- [ ] 商业化配置页保存真实 9 项权益、VIP 套餐、千寻币套餐和 8 个消费场景，校验图标、价格、币数、状态和审计版本。
- [ ] 订单、资产流水、退款、轻量对账和用户商业化详情分别使用真实分页/详情/操作接口，补齐筛选、导出、退款二次确认和权限。
- [ ] 将 `/commercial/*` 路由从占位/演示承载拆为可用工作区，避免任何硬编码列表作为生产展示。
- [ ] 对高风险配置、退款和导出保留后端权限与审计记录。

### 任务 5：验证与验收

- [ ] 运行后端 Maven 测试，使用仓库要求的 JDK。
- [ ] 运行小程序静态门禁和 `npm run build:weapp`；不运行 H5 编译。
- [ ] 运行管理后台 `npm run build` 和静态门禁。
- [ ] 执行 `git diff --check`，更新测试/验收记录，明确未具备微信支付凭据时无法做真实渠道支付的验证边界。
