# 本地敏感词前置机审：选型评估与接入建议

> 日期：2026-09-08
> 状态：已完成词库与代码核查；以下为推荐设计，命中处置规则待业务确认，不作为实施定稿。
> 需求：微信文本机审前增加本地敏感词校验，保留附件原始分类，评估独立模块与字典模块的取舍。

## 1. 结论

建议在「内容审核」下增加「敏感词库」管理页，词条使用专用业务表，分类名称和编码可复用系统字典。公共校验能力放在 `common/`，继续使用现有单体架构、数据库和 RBAC。

理由不在于 MySQL 存不了五万条字典数据，而在于现有字典的字段、树形维护方式、权限与生命周期不适合批量词库、匹配规则、审核证据和运行时版本管理。

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| 最小改动 | 词条全部存入 `sys_dict_data`，按分类建父节点 | 能复用增删改页面，但仍需开发批量导入、搜索分页、词条去重、匹配配置和缓存刷新；不推荐作为正式方案 |
| 平衡方案（推荐） | 独立敏感词页面、词条专表、公共匹配服务；分类元数据复用字典 | 边界清楚，能保留多分类来源，权限与更新不会混入普通资料选项；无需新增基础设施 |
| 完整方案 | 进一步增加规则审批、多版本发布、灰度、误拦统计、场景策略平台 | 适合后续运营规模扩大后建设；当前需求不需要一次引入 |

### 分类原则

完整保留上述 18 个文件标识作为原始分类/来源，包括「色情类型」与「色情词库」，不擅自合并。可在页面隐藏文件扩展名，但导入记录保存完整文件名。JSON 使用 `SensitiveLexicon` 作为来源分类，不凭词义重新分组。

文件名同时包含内容主题与来源名称，不能直接根据名字推定全部词条的风险级别。风险处置单独配置，不能把「分类」等同于「一律拒绝」。同一词可归属多个原始分类，匹配时计算一次、展示全部命中归属。

## 3. 现状与接入位置

| 场景 | 现有调用链 | 接入影响 |
| --- | --- | --- |
| 自我介绍、资料问答 | `OpenTextAuditServiceImpl` → `TextSafetyProvider` → `WechatTextSafetyProvider` → `CommunityContentSecurityPort.checkText` | 本地校验应接入公共文本入口，并继续通过原审核服务回写状态和审核历史 |
| 社区动态、诚意贴 | `CommunityServiceImpl.createPost` → `CommunityContentSecurityPort.checkPost` → `checkText` → `checkImages` | 当前只有文本 PASS 才继续图片审核；新增前置判断要保留这一短路顺序 |
| 社区评论 | `CommunityServiceImpl` → `CommunityContentSecurityPort.checkText` → `CommunityAuditPolicy.decideComment` | 评论的 REVIEW/UNAVAILABLE 当前返回重试，不进入人工队列，不能直接复用资料的人工复核方案 |

建议将 `CommunityContentSecurityPort` 的业务入口组合为本地校验和微信校验两级；微信适配器继续只处理微信调用。所有生产文本调用方统一使用组合入口，避免资料与社区各维护一套过滤逻辑。实现时显式区分组合服务与底层适配器，避免 Spring 多实现注入歧义或递归调用。

建议流程：

```text
文本提交
  → 参数及原有业务校验
  → 本地词库匹配
      → 命中拒绝规则：结束本次机审，记录本地证据，返回不通过
      → 命中复核规则：按该业务已有能力处理，不公开
      → 未命中启用规则：继续微信文本机审
          → 按原审核状态机处理
```

本地通过只代表可以继续微信校验，不能直接视为业务审核通过。图片和音频仍由现有微信能力处理，文本词库不承担 OCR 或音频识别。首期建议覆盖现有已接入微信的文本入口；昵称、私信等其他范围不能仅因它们属于文本就宣称已经覆盖。

社区配置关闭机审时，当前业务层会跳过公共接口。本地校验是随总机审开关关闭，还是独立运行，需要在实施定稿时写清，不能只改适配器就宣称所有提交路径始终经过本地检查。

### 审核结果和来源

`auditSource` 继续表示 MACHINE/MANUAL；在机审明细中区分本地词库与微信步骤，保存词库版本、词条标识、全部分类、匹配规则和最终动作。词条命中详情仅向有审核权限的后台展示，小程序保留统一审核提示。

现有 `WechatProviderResultMapper` 把 provider 固定为 `wechat-content-security`。如果只在微信调用前返回本地拒绝而不调整结果映射，本地命中会被错记为微信拒绝；需同步调整结果来源模型和审核详情展示。结构化证据应使用 JSON 序列化，不把原始命中文字直接拼进字符串 JSON。

## 4. 推荐的维护方式

### 管理后台

入口建议为「内容审核 → 敏感词库」，采用分页列表，支持按词条、原始分类、状态搜索。首期必要操作为新增/编辑、启停、批量导入、批量启停、导入结果查看和匹配试验。

导入先给出预览：各文件词数、重复数、归一化碰撞、异常行、超长词和单字符词；之后才进行持久化。文件内容不能作为 SQL、正则或脚本直接执行。重复导入应幂等，也不能重新启用管理员已手动停用的词条。

### 数据模型方向

| 数据 | 推荐承载 | 主要内容 |
| --- | --- | --- |
| 原始分类元数据 | 系统字典中的专用类型，如 `sensitive_word_category` | 稳定编码、名称、排序；保留附件分类 |
| 词条 | 专用词条表 | 原词、规范化键、启停状态、匹配方式、处置方式等 |
| 分类归属 | 词条与分类关系表 | 一个词可关联多个来源分类；保留来源文件、原行位置/JSON 索引等导入证据 |
| 导入记录 | 导入批次及结果记录 | 文件摘要、执行人、数量统计、异常清单、词库版本 |
| 命中证据 | 现有审核记录及结构化扩展 | 本地/微信步骤、命中归属、规则版本与结论 |

新业务实体继承 `BaseEntity`，包含审计字段和逻辑删除。实际唯一约束需兼容停用、逻辑删除后重新导入；不能简单用一个全局 Set 丢弃来源。至少规划规范化词条查找、分类关联、启用状态等查询索引。

分类若复用字典，必须补被引用分类的改码/删除保护，并确保更新触发敏感词版本刷新。词库维护权限单独使用现有 RBAC 设计，不能凭普通字典编辑权限随意更改风险处置。字典仅承载分类元数据，不将词条下发到小程序公开选项接口。

### 后端分层与运行方式

- 管理 API 放在 `admin/`，继续遵守 Controller → Service → ServiceImpl → DAO → DAOImpl → Mapper。
- 词库读取与匹配放在 `common/`，`admin/` 和 `miniapp/` 不互相依赖。
- 前端页面放在 `frontend/src/pages/moderation/`，API 放在 `frontend/src/api/`，路由接入 `frontend/src/router/`。
- 数据库负责维护，服务内存中的匹配索引负责请求时匹配；不为每条提交查询数万行词条，也不逐词执行数据库 LIKE。
- 更新后先完整构建新索引，再原子切换；多实例通过现有 Redis 配合版本检查刷新。更新失败保留上一个有效版本并暴露失败状态。
- 启动时没有有效词库、读取异常等情况必须与「未命中」区分，不能静默当作通过。具体业务响应按确认后的资料/动态/评论策略处理。
- 网址类需要区分域名和路径规则，避免把所有记录当任意文本片段；含符号词条按字面文本处理。归一化、短词与词边界需要独立用例，避免过度删除空格/标点导致误拦。

## 5. 待确认的业务决策

| 决策 | 推荐方向 | 状态/原因 |
| --- | --- | --- |
| 维护模块 | 独立敏感词页及专表，分类可复用字典 | 本文已给出代码与词库证据，供用户选型 |
| 本地命中处置 | 可配置拒绝/人工复核；宽泛词、单字符词先复核或停用 | 已向用户询问；不能从词库文件名推断处置政策 |
| 评论命中宽泛词 | 单独确定；若要求人工复核，需同步补齐评论待审核状态及前后台闭环 | 现状只有重试路径，不能把永久命中做成无限重试 |
| 开关语义 | 明确本地校验与现有机审开关的关系 | 当前社区关闭机审会绕过公共审核接口 |

这些业务决策不影响「词条专表、分类可复用字典」的选型结论，但会影响正式接口、状态流转和验收用例。
