## 1. 结论、证据与成功标准

### 1.1 当前问题不是“REJECTED 状态禁止编辑”

数据库快照中 U120 的实名认证已通过，最新学历记录 `3041` 为 `REJECTED / MANUAL / DIPLOMA_NO`，驳回原因为 `kk`，审核时间为 `2026-10-12 19:59:37`。学校名称为“测试大学”，`school_code` 为空，学历为 `BACHELOR`，材料数为 0。

`VerificationServiceImpl.getEducationDetail()` 的提交资格为“实名已提交且学历不是待审核/审核中”；`submitEducation()` 也没有禁止驳回记录重提。因此，根据代码规则，此快照满足重提资格；这不是拿到该用户真实接口响应后的端到端提交验证。

真正卡住的是：旧学校名称被回填成看似完整的值，却没有后端要求的学校编码；前端将服务端资格、学校、学历、方式字段、协议全部合成 `canSubmit`，按钮颜色变浅，点击又直接返回，用户不知道缺什么。

| 证据 | 已证实现象 | 对问题的解释 |
|------|------------|--------------|
| 数据库：学校“测试大学”且编码为空 | 历史快照缺少当前必需的选校凭据 | 当前三个毕业生表单均会被选校条件挡住 |
| 视频：学信网字段可输入，填写 `13455` | 可以进入表单并输入；该值只有 5 位 | 不满足现行 12–18 位字母或数字规则，是另一独立缺项 |
| 视频：上传证书页面为 `0/4` | 尚未上传材料 | 上传方式必须至少有 1 张材料 |
| 视频：协议并非始终勾选 | 不同方式还有协议缺项 | 不能通过解除所有校验来解决 |
| 源码：`handleSubmit()` 在 `!canSubmit` 时静默返回 | 除方式、协议外，缺项没有可操作反馈 | 造成“驳回后重新填写不了”的观感 |

本次没有以真实学校资料提交该账号，也没有擅自更改其认证结论。视频不足以证明所有输入控件、上传接口或完整提交链路均正常。

### 1.2 同一重填流程的次级风险

以下是源码发现的风险，不混写成 U120 已实际触发的原因：

1. 学信网方式同样要求 `educationLevel`，但 `ChsiForm` 没有学历选择器；旧记录缺学历时无法在该表单补齐。
2. 材料只有预览和追加，没有删除/替换；驳回记录已有 4 张时无法更换错误材料。
3. 旧材料预览使用 `Promise.all`，任意一张下载失败都会让 `loadDetail` 失败，进而触发整页加载错误。
4. 三重认证中心仅初次挂载读取状态，后台驳回后返回保留页面可能仍显示旧状态。
5. 驳回原因固定定位在 `1310rpx`，不同方式表单高度不同；视频可见原因与说明区域混在一起。
6. 学历提交成功页显示“你的头像正在审核”，认证类型文案错误。

### 1.3 成功标准

- 驳回后明确展示原因和重新填写入口，学校、学历、当前方式字段可修改。
- 不合法时明确指出缺项，定位到对应字段，不发起提交请求；合法时提交一次并进入新的待审核记录。
- 历史无编码学校能重新搜索、点选，而不是静默卡死或自动伪造学校编码。
- 旧材料可删除、替换，单张预览异常不阻断整个表单。
- 返回页面更新审核状态但不覆盖正在填写的草稿；不改变聊天、登录、实名认证和审核通过规则。

Decision Gate：本次可实施边界是修复现行认证接口的重填交互，不新增认证政策。以下历史文档与代码差异必须显式保留，不能以“修 bug”名义偷偷改变：

- PRD 公共定义允许未命中学校字典时手动输入，当前 `requireSelection()` 必须有字典编码。本方案保留当前接口规则，展示重新选校提示；**放开手填学校属于另案业务决策，未经确认不得落地**。真实学校搜索无结果时保留草稿并提供重试/客服，不伪造编码。
- PRD 公共定义学校/证书编号长度写为 2–50，当前实现分别为学校 2–100、证书编号非空且最多 64。本方案镜像当前接口校验，不借此扩大或收紧规则；统一 PRD 与校验配置另行处理。
- DTO 注释说上传证书也必须有证书姓名，但当前表单与 Service 仅证书编号方式要求姓名。本方案不新增上传方式的姓名门槛，修正注释以免误导。
- 已通过后主动更新学历的原有效结果继续按现有后端派生规则生效；不改为“新提交就取消原通过”。

以上另案项不纳入本次实现清单。若实施范围要包含它们，先确认业务口径并更新方案。

## 3. 调用链与接口契约

```text
三重认证 / 我的认证
  → 查询最新认证状态、学历详情
  → 当前学历表单：权限快照 + 可编辑草稿 + 校验结果
  → prd01Api.submitEducation(buildEducationRequest(...))
  → VerificationController → VerificationService → VerificationServiceImpl
  → 共用审核服务 → AppUserAuditRecordDao → DAOImpl → Mapper
  → 新 app_user_audit_record + 审核历史
  → 返回 VerificationStatusVO → 更新本人状态 → 学历提交成功页
```

| 功能 | 方法与 URL | 请求/返回 | 处理方式 |
|------|------------|-----------|----------|
| 最新认证状态 | `GET /miniapp/verify/status` | `R<VerificationStatusVO>` | 入口及返回时刷新资格，不由前端推断审核通过 |
| 本人学历快照 | `GET /miniapp/verify/education` | `R<EducationVerifyDetailVO>` | 首次加载回填；后续刷新不盲目覆盖草稿 |
| 提交学历 | `POST /miniapp/verify/education` | `EducationSubmitReq` → `R<VerificationStatusVO>` | 校验通过后发起，新建待审核记录 |
| 学校联想 | `GET /miniapp/dict/schools` | `keyword, limit` → 学校候选 | 必须点选返回的 `name/code`；现有搜索可补学校字典，不作为纯只读查库使用 |
| 材料上传/预览 | 复用 `prd01Api.uploadEducation()` 和受保护材料下载服务 | 上传后保存材料引用，预览使用本地临时路径 | 不把临时路径提交给后端，不取消鉴权 |

资格字段 `canSubmit/blockedReason` 只解释服务端是否允许提审；表单字段及其合法性由独立的前端校验结果解释。详情尚未加载或资格未知时，不默认允许提交。时间沿用 `yyyy-MM-dd HH:mm:ss`。

## 4. 状态模型：拆开资格与完整性

新增学历专用纯函数及 Hook，页面只拼 UI 和调用事件：

- `serverState`：最新 `auditStatus/canSubmit/blockedReason`，后端为事实源。
- `draft`：公共学校/学历字段、当前方式专属字段、材料条目、协议勾选。
- `validation`：`valid`、字段错误集合、首个错误字段；按钮反馈和请求门禁复用同一结果。
- `operation`：`loading/uploading/submitting`，同步 single-flight 锁防止同一帧重复点击。
- `dirty`：只在用户实际修改后变为 true；用于防止页面返回时回填旧资料覆盖新输入。

| 后端最新状态 | 表单行为 | 操作反馈 |
|--------------|----------|----------|
| 无记录且实名已提交 | 可填写 | 提交 |
| `REJECTED` 且允许提交 | 原因提示 + 可编辑草稿 | 重新提交 |
| `EXPIRED` 且允许提交 | 失效提示 + 可编辑草稿 | 重新提交 |
| `PENDING/REVIEWING` | 只读，不可再上传或提交 | 审核中及后端 SLA |
| 实名前置条件不满足 | 不开放学历提审 | 显示后端阻断原因，引导实名 |
| `APPROVED` | 保持现有入口差异：认证中心查看通过、我的认证主动更新 | 不新增自动重新认证 |
| 状态未加载或刷新失败 | 不使用缺失资格放行 | 明确加载/重试反馈，保留已填草稿 |

按钮规则：有提审资格时提供可点击的“提交/重新提交”，点击不合法表单显示字段错误并定位，**不是放开无效 POST**；上传中、提交中、资格阻断时不可重复提交并显示原因。协议改为校验的一项，按表单顺序反馈缺项，不再始终先提示协议掩盖学校问题。

## 5. 表单与选校改造

### 5.1 校验表

| 字段/方式 | 校验及提示原则 |
|-----------|----------------|
| 方法、人群、学历 | 必须命中当前启用字典；停用旧值提示重新选择，不把 label 当 code |
| 学校 | 名称 2–100；必须有点选候选得到的编码；改名称立即清编码 |
| `CHSI` | 规范化输入后校验 12–18 位字母或数字；增加可编辑的学历选择器 |
| `DIPLOMA_NO` | 编号非空且最多 64；证书姓名非空且最多 50 |
| `STUDENT_CARD/MATERIAL_UPLOAD` | 至少 1 张成功上传的材料，最多 `min(后台上限, 4)`；在上传完成前不可提审 |
| 协议 | 当前提交必须主动勾选，不从旧审核记录默认勾选 |

字段错误就地展示，点击提交滚动到首个错误字段；文本字段可聚焦，选择器和材料区需有真实可点击入口。错误提示解除后恢复正常样式；不采用透明热区或把控件画入图片。

### 5.2 历史学校的处理

1. 学校名称有值但编码缺失时，保留名称并明确标识“旧学校信息未确认，请重新搜索并选择学校”，不伪装成已选中。
2. 提供“重新选择”动作，使用户可清除旧选择并直接输入，不要求先知道有一个隐藏编码。
3. 用户点选真实候选后同时保存规范 `name/code`，提示消失。只有名字相同不能算用户已经确认学校。
4. 缩短输入、清空、选中候选、组件卸载均使旧请求失效，防止晚返回的候选覆盖新输入；保留现有 300ms 防抖。
5. 在学历页通过可选 props 提供确认提示、错误、重选动作；共享学校组件的基础资料调用方不被强制套入学历规则。

对 U120 不执行“测试大学 → 某所真实学校”的数据库修复。编码必须来自本人真实选校；新的审核记录保存新快照，旧审核快照保持历史事实。

### 5.3 方法切换与布局

- 首次回填公共学校和学历；方式专属字段仅在历史记录方法与当前方法一致时回填，不能把旧学生证自动当毕业证材料。
- 在当前方式内保留用户输入；离开当前表单不新增跨账号或永久磁盘草稿，避免高敏认证信息遗留。
- 驳回/阻断提示归入表单上方独立块，原文换行，取消通用固定 `top: 1310rpx`。
- 学历表单、提示、说明、按钮、协议、客服采用学历页局部的顺序布局，扩展内容自然撑高；保留共用壳的默认行为。学信网 STEP 图继续作为非交互图片，不烘焙输入/按钮。
- 如需为学历页增加滚动定位能力，给壳提供可选滚动目标；原有其他认证页不改变。无异常学生页面保留视觉基线；相应坐标静态测试升级为布局顺序与运行时截图核对，不只改数字让断言过关。

## 6. 材料、异步加载与返回刷新

### 6.1 单条材料模型

用稳定条目 ID 管理 `serverUrl/previewUrl/previewStatus`，不用两个靠数组下标对齐的列表承载替换逻辑。

- 预览可重试、材料可删除；删除只移除当前草稿引用，不删除 OSS 对象或历史审核材料。
- 满 4 张也能先删除再上传；直接替换时只在新材料上传成功后替换旧引用，失败保留旧材料。
- 预览异步结果按条目 ID/请求代次合并，不能在条目删除后重新写回。
- 详情数据成功后即可显示表单，材料预览独立处理；单张 403/404/下载错误显示占位和重传动作，不让整页失败。
- 不全局修改 `resolveProtectedFilePreviews()` 的错误语义，学历 Hook 针对单条调用 `resolveProtectedFilePreview()` 并隔离结果。系统性 401 仍走现有登录失效流程，不能吞掉鉴权错误。
- 后台将材料上限收紧至小于旧材料数时，显示全部旧条目供删除，要求主动降至新上限；不再静默 `slice()` 丢弃用户材料。

### 6.2 页面生命周期

1. 首次进入：等待必要配置、字典和学历详情；仅首次成功加载初始化草稿。
2. 返回认证中心/我的认证：重新获取最新状态；已有页面静默刷新，不重复清空整页制造闪屏。
3. 返回学历表单：仅更新资格、原因等服务端状态；不重新覆盖用户改好的学校、材料、验证码或协议。
4. 请求使用递增代次并在卸载时失效，晚返回的初次数据不得覆盖较新状态。
5. 服务端变为审核中时禁用提审，不把前端保留草稿当成可再次提审的依据；后台变化以 POST 校验为最终门禁。
6. 请求失败保留草稿并展示重试；明确失败与“未提交”的区别。网络超时后先查最新资格，若已进入待审核不再重复 POST。

提交成功使用响应中的真实认证状态、现有 `emitProfileUpdated` 通知及页面返回查询刷新本人状态；成功页改为“学历认证已提交，等待审核”，不再显示头像审核文案。不在提交成功时自行写 `APPROVED`。

## 7. 后端、数据库与配置

### 7.1 业务服务不重写

- 保留 `VerificationController → VerificationService → VerificationServiceImpl` 及既有共用审核服务/DAO 链；不让 ServiceImpl 直接访问 Mapper，不引入 admin/miniapp 互相依赖。
- 保留 `EducationSubmitReq` 和 `EducationVerifyDetailVO` 字段。前端通过 `buildEducationRequest()` 只发送当前方式字段、规范化文本和真实材料引用。
- 每次合法重提创建新的 `app_user_audit_record` 和提交历史，旧驳回记录不更新为待审核、不删除。复用 `BaseEntity`、逻辑删除、审计字段及既有索引，无新增表/索引。
- 保留服务端实名前置、待审核拒绝重复提交、学校匹配、字典校验和材料地址校验；前端校验不能替代后端校验。
- 本次不升级多设备并发提审锁策略；前端 single-flight 仅保证本页面操作，不能宣称提供全局严格幂等。

### 7.2 提示文案

复用 `app_config` 中 `prd01.copy.rules`，沿用 `Prd01RuntimeConfigResolver` 和 `usePrd01Store.copy()`。计划新增学历专属字段错误、旧学校待确认、材料删除/预览失败、重新提交、学历成功提示等 copyKey；实施时给出完整种子及字段映射，不把 key 或空字符串直接显示给用户。

## 8. 权限与安全

| 项目 | 规则 |
|------|------|
| 用户身份 | 复用 `X-Auth-Token`，用户 ID 从上下文获取，请求体不得指定其他用户 |
| 后台权限 | 不新增权限；查看高敏编号、原图和审核动作沿用既有 RBAC/二次确认与审计 |
| 材料访问 | 继续使用受保护下载及现有上传凭据；不改 bucket ACL、不泄露签名 URL |
| 敏感数据 | 日志仅记录状态、字段错误码和数量，不记录完整手机号、姓名、验证码、证书编号、Token 或材料地址 |
| 401/403 | 401 按登录失效处理；材料访问 403 不改成公网绕过；保留重传入口与明确反馈 |
| 草稿 | 页面内存保存，登出/切账号销毁；不新增高敏字段跨账号持久化 |

## 9. PRD-07 推广裂变联动影响

| 项目 | 设计 |
|------|------|
| 本次提交是否直接发奖励 | 否，提交/驳回/编辑材料不是认证通过事实 |
| 后续审核通过事件 | 沿用实名、学历均有效后首次入箱的既有审核服务接入点 |
| 幂等键 | 沿用 `verify:{userId}`、既有奖励键与唯一约束；驳回再批准不能重复奖励 |
| 主流程失败策略 | 不新增前端奖励调用；推广消费失败按既有收件箱补偿，不逆向取消认证 |
| 关联数据 | 不改推广奖励、事件、通知或资产表；材料上传不触发认证奖励 |
| 回归 | 已奖励用户重提/再次通过不重复奖励；首次合法通过仍正常触发既有奖励 |

## 10. 验证方案与验收矩阵

| E16 | 无记录、审核中、已通过主动更新、原有效状态及推广 | 现有业务行为无回归，首次奖励幂等不变 |
