## 1. 背景与目标

在现有微信文本内容审核前增加本地敏感词检查。后台提供独立敏感词管理能力，按附件分类维护词条。命中任意启用词条时，直接采用该业务现有的微信机审不通过流程；本地检查通过后再调用微信。根据用户补充确认，本地词库不可用时跳过该检查，继续微信审核及原后续流程。

本次不改变准入资料审核与社区审核的业务归属，不增加机审驳回后的人工复审机制，不改变诚意贴的人工审核要求。

## 3. 审核覆盖与处理规则

### 3.1 前置检查的内容

| 内容 | 是否检查本地敏感词 | 接入位置 |
| --- | --- | --- |
| 自我介绍 | 是 | OpenTextAuditServiceImpl → WechatTextSafetyProvider → checkText |
| 「关于我」资料问答 | 是 | OpenTextAuditServiceImpl → WechatTextSafetyProvider → checkText |
| 社区普通动态正文 | 是 | CommunityServiceImpl → checkPost → checkText |
| 诚意贴正文 | 是 | CommunityServiceImpl → checkPost → checkText |
| 社区评论、回复文字 | 是 | CommunityServiceImpl → checkText |
| 动态、诚意贴配图 | 正文先检查；图片仍走原微信图片审核 | checkPost 中只有文字通过才继续 checkImages |
| 头像、相册、个人背景图 | 否 | 保留原微信图片审核 |
| 语音介绍 | 否 | 保留原微信音频审核 |

纯图片、音频只有媒体 URL，URL 不当成图片/音频正文送本地词库扫描。没有走微信文字审核的入口，本次不额外扩展。原有 Mock 模式及机审关闭分支保持不变；只有实际走微信文字审核的调用才进入此前置检查。

### 3.2 审核顺序

```text
用户提交文字
  → 原有参数、身份、业务权限校验
  → 本地敏感词检查
      ├─ 命中启用词 → 返回 REJECT → 该模块原机审不通过流程
      ├─ 未命中 → 微信文字审核 → 该模块原审核流程
      └─ 词库不可用 → 跳过本地检查 → 微信文字审核 → 该模块原审核流程
```

本地未命中和本地故障跳过，都进入微信审核。两者仅在本地阶段采用相同的后续路径，不直接将内容判为最终通过；微信的通过、不通过、待复核和异常结果均保持原有处理。

### 3.3 各业务命中后的结果

| 内容 | 本地命中后 | 人工及 C 端行为 |
| --- | --- | --- |
| 自我介绍、资料问答 | 调用原 machineReject，保存机审驳回与历史 | 继续沿用准入模块现有状态、已通过内容生效规则及安全失败提示 |
| 普通动态、诚意贴 | 保存为 rejected，不公开 | 社区后台可查看已驳回记录；不新增重新人工通过入口；C 端沿用现有发布回执 |
| 评论、回复 | 保存为 rejected，不公开、不增加评论数 | C 端沿用「评论未通过审核」回执；不新增人工待审记录 |

本地命中相当于微信明确判定不通过。本地词库读取、版本检查或索引构建失败时，跳过本地检查并继续微信审核；不会仅因该本地故障让资料保持待处理、动态/诚意贴转人工，或让评论提示重试。业务状态与 C 端回执由后续微信审核及原业务规则决定。微信自身返回待复核或异常时，仍走其原有处理分支。

诚意贴在本地未命中或因故障跳过后，继续微信机审；微信机审通过后仍进入原有人工审核，人工通过后公开。普通动态和评论在本地未命中或因故障跳过后，按微信结果继续各自原有发布逻辑。图文内容仍须按原顺序完成微信文字及图片审核。

准入审核与社区审核继续分别保存和展示：准入使用 app_user_audit_record；动态使用 community_post；评论使用 community_comment。共享的是敏感词能力，不合并审核列表。

## 4. 敏感词管理页面

### 4.1 入口与列表

根据用户 2026-09-09 最新确认，后台入口调整为「运营中心 → 敏感词管理」，排列在「消息通知记录查询」之后，路由保持 `/sensitive-words`。该页面统一维护供准入和社区文字机审共用的敏感词库。现有菜单ID、按钮权限和词库数据保留；已有页面角色补齐运营中心父目录关联，父目录本身不增加业务操作权限。

| 区域 | 内容 |
| --- | --- |
| 筛选 | 敏感词关键词、分类、启用/停用状态 |
| 列表 | 敏感词、分类、状态、备注、创建时间、更新时间、操作 |
| 分页 | 默认 20 条，每页最多 100 条 |
| 操作 | 新增、编辑、启用/停用、删除 |

按用户最新要求，未删除词条在整个词库中全局唯一，分类不作为去重条件。同一词只维护一条未删除记录；启用和停用记录都参与查重，已删除记录不阻止重新新增。初始化时同词涉及多个分类，只从其实际出现过的分类中随机选择一个并保存。新增、编辑仍由管理员单选一个分类，不支持多选，也不在日常查询或修改时重新随机归类。

### 4.2 新增、编辑与删除

新增/编辑表单包含敏感词、分类、状态、备注：

- 敏感词必填，按本节统一规则去除首尾空白后，最多 256 个 UTF-16 代码单元（Java String.length 与前端计数一致；补充平面字符占两个）；不允许空白词。
- 分类必选且为单选，必须属于服务端定义的 18 类。
- 状态为 ENABLED/DISABLED，新增默认启用。
- 备注可选，最多 500 字符。
- 初始化、新增、修改均按去除首尾空白后的原词精确比较，采用同一全局去重规则，范围为所有 deleted=0 记录，包含停用记录，不按分类缩小查重范围。编辑时排除自身 ID，仅修改本记录的分类、状态或备注不会与自身冲突；重复时提示“该敏感词已存在”。
- 根据用户确认，词条表不设 version 字段，编辑、启停和删除不提交或校验记录版本。按 ID 操作有效记录；多人编辑时以最后一次成功保存为准。已删除记录不能被编辑恢复，仍保留权限、字段合法性和全局重词校验。
- 删除需要确认，采用逻辑删除。请求失败保留表单内容，成功后刷新列表。
- 列表启停按钮调用状态专用 PATCH，仅提交目标状态，不从旧列表拼接全量 PUT。服务端取得刷新行锁后读取当前记录，只更新状态、审计字段与刷新标记。重复设置相同状态幂等成功，不重复构建；已删除记录报不存在。完整编辑表单仍采用最后一次成功保存生效。

无查看权限时不请求词库；无新增、编辑、删除权限时不显示对应按钮，同时服务端校验权限。

**输入、查询和排序契约：**

- 初始化生成器和后台 API 共用同一首尾空白集合：U+0009–000D、U+001C–0020、U+0085、U+00A0、U+1680、U+2000–200A、U+2028–2029、U+202F、U+205F、U+3000。仅剥离两端，不变更内部字符；不直接混用 Python strip 与 Java trim/strip 的不同口径。
- 原词列采用 MySQL 8 的 `utf8mb4_0900_bin`，保存和查重均使用参数绑定；大小写、全半角作为原词分别保存。输入边界、索引字节长度在目标 MySQL 核对。
- page 默认 1，size 默认 20；page < 1、size 不在 1–100、非法分类/状态返回参数错误。ID 必须为正数。空筛选项按未设置处理。
- keyword 最多 256 个 UTF-16 代码单元，按原词字面包含搜索；`%`、`_`、反斜杠不当用户通配符，使用明确的 LIKE 转义实现。分类、状态精确筛选。
- 列表按 id 倒序稳定分页；关键词输入及分类、状态切换立即请求列表并回到第一页；搜索按钮和回车可主动重查，重置清空全部条件后立即请求。删除导致页码越界时回到最后有效页，零记录时仍显示第一页空态。

2. 用户已明确要求：最新附件的所有初始化词均为 ENABLED，词库是否准确由用户后续维护，本次不作语义清洗或误拦停用。2026-09-09 已移除旧有效初始化记录，导入最新 clean3 附件的 48,244 条词并全部启用；此前默认停用决定已被用户指令替代。
3. 保留原始词，按文件所属分类初始化；词条不保存来源文件名或来源指纹。正确处理中文、特殊字符、引号、反斜杠和长网址。
4. 合并所有文件后按去首尾空白的原词做全局去重，重复词只初始化一条词记录。只有一个候选分类的词直接保留该分类；多个候选分类先去重再随机选择一个。生成脚本固定随机种子及词条、候选分类排序，将选择结果固化到初始化 SQL，使同一附件重复生成得到相同结果。随机过程仅在生成初始化数据时执行，不新增来源字段、随机标识字段或分类关联表；后台新增和修改使用管理员选择的单个分类。
5. 初始化以新建空词条表为前提，在同一事务内先取得现有词库全局刷新记录的锁，检查词条表全部数据（包含逻辑删除记录），仅为空时一次性写入整批词库并更新刷新标记；任一批次失败则全部回滚。表中已有任何数据时跳过整批初始化并报告，不逐词补写，也不重新启用停用词、恢复已删除词或覆盖管理员修改。空表判断仅在整批开始时执行一次，不能每个插入批次重新判断。
6. 首次初始化完成后核对 18 个分类选项（17 个非空）、48,244 条全局词记录、每词恰好一个分类且属于附件候选分类、未删除词条全局无重复、字符编码和词库刷新标记。词条已被后台维护后，不再强行恢复到初始数量；已有数据但初始化情况不明时先核对迁移执行记录及数据，不自动补写。

## 6. 数据库设计

分类固定为代码枚举，提供分类选项接口；词条独立存储，不把五万余个词放入通用字典选项。

### 6.1 content_sensitive_word

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT | 自增主键 |
| category_code | VARCHAR(64) | 必填，单选分类编码 |
| word | VARCHAR(256) | 原词；utf8mb4_0900_bin 用于精确查重 |
| status | VARCHAR(20) | ENABLED/DISABLED，复用 CommonStatusEnum |
| remark | VARCHAR(500) | 备注 |
| create_time/update_time | DATETIME | 审计时间 |
| created_by/updated_by | BIGINT | 操作人 |
| deleted | TINYINT | 逻辑删除标记 |

实体继承 BaseEntity。按用户确认，词条只保留上述业务字段和基础审计字段，不增加来源字段或辅助生成列。使用普通组合索引 `(word, deleted)` 辅助原词全局查重，分类另外建立查询索引，并补状态及逻辑删除查询索引；不将该组合设为唯一索引，避免同词多次删除、再新增时历史记录冲突。新增和编辑由服务端检查整个词库中同词、deleted=0 的有效记录，查询不带分类条件，编辑时排除自身 ID；停用但未删除的词同样参与查重。按去首尾空白后的原词及二进制排序规则精确查重，不能使用仅含启用词且做过规范化的 AC 缓存代替未删除记录的全局查重。删除后允许以新 ID 重新新增，历史记录继续保留逻辑删除状态。

### 6.2 content_sensitive_word_revision

此表仅是服务端用于发现词库变化的全局刷新标记，与已取消的词条记录 version 无关，不做记录版本冲突校验，也不要求前端提交。单行表 id=1，记录全局 revision，并包含标准审计字段和逻辑删除标记。每次实际新增、编辑、启停、删除及初始化，在同一事务内更新词条与全局刷新标记。后台维护属于低频写操作，复用此单行记录的数据库事务锁，在读取词条和查重前取得锁，查重使用当前读，保证多实例并发维护不会绕过重复校验；不新增锁表或用户版本号参数。所有写入口遵守相同锁顺序。

版本更新失败时事务回滚，避免数据库已修改而缓存永远不刷新。

### 7.1 管理接口

| DELETE /admin/sensitive-words/{id} | sensitive-word:delete | id | R<Void> |

SensitiveWordVO：id、word、categoryCode、categoryName、status、remark、createTime、updateTime。时间按全局约定返回 yyyy-MM-dd HH:mm:ss。分类 VO 为 code、name。

### 7.3 匹配算法、内存与更新

#### 7.3.1 匹配语义

- 待审文本和词条统一执行 NFKC 及 Locale.ROOT 小写，然后按字面子串匹配；原文仍保存在数据库。
- 只要正文任意位置包含任意启用敏感词，就返回 REJECT，不要求分词或整词边界。
- 不执行词条中的正则表达式，不自动去除内部空格或标点，不扩展谐音或拼音规则。网址词也按字面子串匹配。
- 原词精确唯一与匹配规范化是两种不同目的的规则：例如 `ABC` 与 `ＡＢＣ` 可作为两条原词记录存在，各自只有一个分类，但共享同一个规范化匹配键。构建时从同键的启用原词中选最小有效记录 ID 为代表，索引和内部证据仅保留该代表的 ID、原词及单个分类；下次重建重新选择仍启用的代表。不得把索引聚合解释成后台一词多分类，也不能因其中一条停用就移除仍有其他启用记录的匹配键。

#### 7.3.2 方案比较与选择

| 方式 | 每次审核的主要工作 | 结论 |
| --- | --- | --- |
| 加载词条列表后逐词 contains | 最坏对数万词分别搜索正文 | 不采用，缓存列表没有解决重复匹配问题 |
| SQL LOCATE / 反向 LIKE | 对候选启用词逐条判断正文是否包含该词；无命中时必须检查全部候选 | 能实现，但普通 word B-tree 索引不能直接定位这种反向包含命中，作为低频备选，不作为在线审核主方案 |
| AC（Aho–Corasick）多模式匹配 | 词库预先构建为索引，每次沿正文扫描，发现命中即结束 | 本方案采用，避免每次按词数重复扫描正文 |

SQL 的状态、逻辑删除索引可以筛选候选记录，但不能消除剩余候选的包含判断。LIMIT 1 只对提前命中的情况有帮助；将词库循环转移到数据库，不会自动获得按词查找的索引收益。这里依据 MySQL 范围索引规则推断，实际 SQL 耗时仍需要目标环境执行计划和测试才能量化。[MySQL 索引范围优化说明](https://dev.mysql.com/doc/refman/8.0/en/range-optimization.html)

AC 将词库编译为共享前缀及失败跳转结构。按适当的状态转移表示，经典查询复杂度为 O(N + Z)，N 为正文长度、Z 为输出命中数；本业务只需要首个命中，因此无需枚举全部输出。词数增加主要影响索引构建和容量，不会让每篇正文都重新遍历全部词条。[字典多模式匹配研究](https://arxiv.org/abs/1001.2860)

另一个可使用等值索引的方向是枚举正文子串，再对规范化词做 IN / JOIN 查询；这会产生大量候选。本附件包含 64 种词长，按这些词长枚举一篇 300 字符正文，会产生 16,969 个位置与长度组合（去重前）。本次无需引入该查询和候选构造复杂度，也不新增搜索服务。

#### 7.3.3 索引容量与实现约束

早期 Vocabulary.7z 的历史实验统计（非当前词库）：分类记录 76,702 条，原文跨分类去重 51,344 个词；以 NFKC 加小写预估为 51,085 个规范化词。规范化词的 UTF-8 文本合计 675,720 字节（约 0.64 MiB），总字符数 416,973；按 Unicode 码点计算，共享前缀节点含根共 277,830 个，最长词 107 字符。

这些是离线 Python 统计，不能当作 Java 实际堆占用、性能测试结果或毫秒级响应承诺。Java 构建后还需要状态转移、失败指针、命中标识、分类映射及重建临时空间，正式实现时需以 Java 的统一规范化结果重新核对。

- 每个后端应用实例只维护一份当前不可变 AC 快照，请求并发共享；不按用户、请求或业务模块复制词库。
- 使用紧凑数组或双数组的 AC 表示，避免为每个字符节点创建大量 HashMap，也避免建立“全部节点 × 全部字符”的稠密转移表。具体 Java 实现需验证中文、补充平面字符及字面匹配一致性。[双数组 AC 结构研究](https://arxiv.org/abs/2207.13870)
- 运行态仅保留匹配和审计必需数据，不长期缓存完整数据库实体、重复原始列表或无限增长的请求结果。
- 使用现成 Java 双数组 AC 工具包 com.hankcs:aho-corasick-double-array-trie，已用 1.2.3 版本进行独立内存评估。审核调用 findFirst 或可取消回调，在首个命中后停止，不生成正文的全量命中列表；词条分类集中保存。保留工具包原生索引与输出结构，不自行重写或裁剪算法；其内部输出表已计入本次测量。
- 单实例同时只允许一次词库重建。替换时存在新旧索引及构建临时数据，必须测量峰值内存；旧快照在已有读取结束后释放引用。
- 后续验收测量启动构建时间、稳定堆占用、重建峰值、并发吞吐及匹配 p95/p99。包含首部命中、尾部命中、完全未命中、长共同前缀和各业务最大合法正文长度；不得只用容易提前命中的文本估计性能。

本批数据已使用 Java 21.0.11 和现成 AC 工具包完成独立测量：单份索引及词条信息 14.26 MiB，首次构建采样堆峰值 118.04 MiB，保留旧索引重建时采样峰值 120.71 MiB；在 Xmx=256 MiB 的独立进程内完成，未出现 OOM。这些值不含整个业务服务的内存需求，不是严格峰值上限。工具包采用 Apache 2.0 许可，本地匹配不按次数收费。测量范围、原始数据及应用容量限制见同目录《2026-09-08-敏感词AC内存评估.md》。

#### 7.3.4 词库更新与一致性

AC 工具包只负责构建索引与匹配，不自动监听数据库变化。本项目采用“提交后主动预热 + 审核前核对刷新标记 + 新索引原子替换”。更新机制由 common 中的词库服务负责，下述为实现约束，是否已经实现和验证以测试报告为准。

**后台维护到索引生效：**

1. 新增、编辑、启停、删除先执行权限与格式校验；随后进入事务，先锁定全局刷新行，再以当前读读取目标记录并执行全局查重，写入词条后递增 revision。统一顺序为“锁刷新行 → 当前读/查重 → 写词条 → 更新刷新标记 → 提交”；不得在取得锁前完成决定写入结果的数据库查重。回滚时词条与标记同时回滚。
2. 只有数据库成功提交后，才触发当前实例的索引刷新。复用项目 AfterCommitExecutor 注册提交后动作，在回调中向公共词库专用的单线程执行器提交任务。已有执行器的 action.run() 本身不是异步，不把构建过程直接放进同步回调。任务提交失败、线程池拒绝或异步构建失败只记录日志，不把已经提交成功的保存操作误报为失败。
3. 刷新任务先取得最新刷新标记，读取所有 status=ENABLED 且 deleted=0 的词条，再创建新的 AhoCorasickDoubleArrayTrie 对象并完成规范化及 build。新增词进入新树，修改词以新内容进入，停用/删除词不进入；不只更新数据库而遗漏内存索引。
4. 构建前后核对数据库刷新标记，期间有变动则重试，最多三次；只发布与读取结果一致的完整快照。单实例同时最多一个构建任务，连续修改合并处理，只记录最新待刷新状态，避免每次点击都排队保留一份全量词库。
5. 新树、对应词条/分类数据及 revision 组成一个不可变快照，通过 AtomicReference 一次替换。发布后的对象仅用于查询，不再调用 build 或修改其内容；已有读取持有旧快照完成后，旧对象即可回收。工具包说明其 build 完成后支持并发查询。[工具包使用说明](https://github.com/hankcs/AhoCorasickDoubleArrayTrie#usage)

Spring 支持将动作绑定到 AFTER_COMMIT 阶段；必须在提交后触发，避免事务回滚后缓存却提前生效。[Spring 事务事件说明](https://docs.spring.io/spring-framework/reference/data-access/transaction/event.html)

**每次实际微信文字审核前：**

- 读取主库单行全局刷新标记，与当前实例的快照比较。相同则直接用现有 AC 扫描正文，不加载全量词库。
- 本地快照落后或尚未建立时，复用同一个刷新任务并在有限超时范围内等待；成功后使用新快照，不为每个请求另建一棵树。
- 刷新标记读取失败、重建失败、持续变更超过重试次数或等待超时，均按用户已确认规则跳过本地检查，继续微信审核。发现过期时不继续用过期词库作出拒绝结论。
- 正常维护后所有词都停用/删除，可以构建合法空快照，正常进入微信审核。
- 这里每次审核增加一次单行标记查询，但不会每次读取五万词。实际正文匹配在 JVM 内存完成；本次不引入 Redis 全量词库或额外消息队列。

**多实例与生效边界：**

- 每个后端实例维护自己的 AC 快照，并核对同一主库刷新标记。即使没有收到主动刷新事件、进程重启或管理员的请求落在另一实例上，后续审核也能发现词库变化；不需要后台逐台调用刷新接口。
- 数据库保存成功后开始本地校验的请求，应读取到已提交的新标记，并使用对应的新快照或按故障规则跳过；在修改提交前已开始校验的请求可以完成当时的快照检查，不追溯重审已完成的内容。保存成功表示数据库已提交，不表示所有实例在同一瞬间完成构建。
- 标记和启用词条读取使用连接同一主库的小型专用只读连接池，与外层业务事务、业务连接池隔离。DAOImpl 经独立 MyBatis Mapper/SqlSession 执行短查询；每次读取使用新的自动提交会话，关闭会话立即归还连接，不复用外层 RR 读视图或 MyBatis 查询缓存，不走只读副本。词条读完即释放连接，再在内存构建，最后新会话核对标记。后台写入继续现有业务事务管理器。该实现不依赖共享主池的嵌套 REQUIRES_NEW，避免业务请求持有第一条连接又一起等第二条连接。
- 当前使用数据库标记保障下一次审核发现更新。Redis Pub/Sub 可作为以后让其他实例提前预热的优化，但不能作为唯一刷新依据，因为断线期间的消息可能丢失；本次不增加该广播链路。[Redis 投递语义](https://redis.io/docs/latest/develop/pubsub/#delivery-semantics)
- 全局 revision 是服务端刷新用途，不恢复已经删除的词条 version 字段，也不要求管理员提交版本号。任何人工直接修改词库的运维脚本也必须同步递增该标记。

#### 7.3.5 超时、并发和资源预算

以下为首期工程默认值，可由后端配置调整；属于待目标环境验证的参数，不是已取得的生产指标。

| 项 | 默认约束 |
| --- | --- |
| 专用词库读连接池 | 每实例最大 2 个连接，最小空闲 0；复用现有主库连接配置，禁止记录凭证；不改变业务主池配置 |
| 连接获取 | 500 ms；词库读池初始化不要求数据库立即可用，失败不阻断应用启动 |
| 词库读 JDBC 连接/网络超时 | connectTimeout 1000 ms，socketTimeout 2000 ms；只作用于词库读连接 |
| SQL 查询 | 标记查询 1 s，启用词条加载 2 s；在 Mapper/JDBC 层实际设置，不能只写 Future 超时 |
| 等待新快照 | 当前请求最多等待 1000 ms；超时结束自身等待，不取消其他请求共享的构建任务 |
| 刷新执行器 | 单线程，只保留一个运行任务和合并后的待刷新状态，无界队列禁止；提交回调仅入队 |
| 一轮稳定快照尝试 | 最多 3 次；构建前后标记不一致则重读，耗尽返回不可用并释放运行标记 |
| 重建故障冷却 | 失败后同一实例至多每 1 s 发起一轮重试；冷却期间仍检查标记，缺有效快照时跳过本地 |
| 服务退出 | 拒绝新刷新任务，释放连接池和线程；不能等待无界任务队列 |

标记检查和刷新等待是两个阶段：一次正常新查询的预算是连接等待及查询耗时，发现过期时再加最多 1000 ms 的快照等待；不得对外把“等待树 1 s”宣传为“本地阶段总耗时一定小于 1 s”。DB 故障试验需实测连接等待、网络超时和刷新等待的累计时间；JVM 停顿及操作系统调度不属于硬实时保证。服务指标至少记录快照 revision、启用词数、构建次数/耗时、最近成功时间、跳过原因计数；日志不含完整待审文本。

额外资源是每实例最多 2 个主库连接、一条构建线程及已评估的 AC 堆余量，不增加数据库实例、Redis 词库副本或 MQ。新增读会话资源需明确限定名与生命周期，不能让它替代 Spring Boot 自动配置的业务 DataSource、SqlSessionFactory 或事务管理器。

Spring 官方说明 REQUIRES_NEW 会另取连接且可能导致池耗尽；这里选择隔离读资源，而非单纯扩大业务池。[Spring 事务传播](https://docs.spring.io/spring-framework/reference/6.2/data-access/transaction/declarative/tx-propagation.html)、[HikariCP 配置](https://github.com/brettwooldridge/HikariCP#configuration-knobs-baby)。

#### 7.3.6 本地故障跳过规则

按用户确认，本地检查异常采用跳过策略，后续路径与本地未命中一致：

- 覆盖词库数据库连接/查询失败、版本读取失败、启动预热失败或尚无索引、更新后索引重建失败及无法取得一致版本等本地检查故障。
- 本地结果为 REJECT 时直接返回原机审不通过流程，不得降级放行；PASS 或本地 UNAVAILABLE 时继续正常微信文字审核。内部将未执行成功的检查记录为“跳过”，不伪造本地已匹配通过的审计事实。
- 异常处理仅包围本地检查调用。微信请求、微信结果解析、业务校验及保存失败均继续原有处理，不可被本地跳过逻辑吞掉或改成 PASS。 本地检查异常的事务传播和捕获不得让健康的外层业务事务仅因本地失败被标记为 rollback-only，需在实现时核对并验证该事务边界。
- 本地词库预热失败不单独阻断应用启动；后续请求按版本检查及现有超时约束重新尝试加载，成功后自动恢复敏感词检查，不进入永久跳过状态。
- 若版本检查或更新失败，当前请求直接走上述跳过路径，不用无法确认有效性的旧索引拒绝内容。重建仍遵守单实例单次构建及有限重试约束，不无限等待词库恢复。
- 跳过仅保障本地检查不阻断后续流程。若业务自身依赖的数据库等也不可用，业务仍按原规则处理该故障，不承诺整次提交一定成功。

### 7.4 审核记录与用户提示

审核来源 auditSource 继续使用 MACHINE/MANUAL。机审步骤另区分 `local-sensitive-word` 与 `wechat-content-security`。

本地命中记录全局 revision、代表词条 ID、原词及单个分类，机审码使用 `local_sensitive_word:<id>`。内部证据用 ObjectMapper 序列化；技术说明固定为 `local_sensitive_word_hit`。不得把证据 JSON 放入可能被客户端使用的 detail/rejectReason。

| 流转位置 | 契约 |
| --- | --- |
| LocalSensitiveWordService → CommunitySecurityResult | 增加可选内部 evidenceJson，与 conclusion/providerCode/detail 分开；兼容既有三参数构造及微信静态工厂 |
| WechatProviderResultMapper | 本地来源为 local-sensitive-word；rawResponseJson 包含结构化 evidence；rejectReason 使用固定技术码，沿用原资料安全提示映射。所有 JSON 改为 ObjectMapper 序列化，覆盖控制字符 |
| 准入审核记录 | external_provider_task.response_payload_json 与 app_user_audit_record.machine_signal_json 保存历史证据；reject_reason 保持普通用户提示 |
| 社区动态/评论记录 | machine_code 保存本地命中码，machine_detail 仅保存固定技术说明；不把无限长 JSON 塞入 VARCHAR(1000) |
| 社区机审审计 | 复用 community_audit_record.after_snapshot（现有 JSON）保存此次机审的 source、conclusion、code、evidence；reason 仅为普通技术说明，不新增审核表或证据列 |
| 管理端审核详情 | 准入详情从历史 machineSignalJson.evidence 提取白名单字段展示；社区审核日志 VO 增加受原审核查看权限约束的 machineEvidence，并由既有详情的机审日志区域显示来源、命中原词、分类、revision |

### 15.5 启停跨域与即时查询修复（2026-09-09）

实际浏览器经前端代理携带 Origin 调用 PATCH 启停接口时，旧 WebConfig 未允许该方法，Spring 返回403 `Invalid CORS request`；前端统一403提示使它看起来像账号缺少权限。此前无 Origin 的真实API调用与拦截器独立测试未覆盖这个边界。
