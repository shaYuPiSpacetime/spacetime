# 私信账号切换身份隔离技术方案

日期：2026-10-12。范围：小程序登录态、按需加载的 LiteChat 网关、聊天页面异步请求；保持当前发送、历史合并和滚动策略。

## 1. 证据与根因

用户 120/1052 有唯一有效 TIM 映射且均已同步。2026-10-12 09:10:11—09:10:23，120→1052 的四条消息在平台及腾讯云双向漫游历史中一致。09:12:21—09:12:32 的四条反向操作却出现在 **120→120** 的自身漫游记录中，1052→120 没有对应记录；凌晨截图中两条缺失消息同样属于 120→120。

`loadMessageImGateway` 原来缓存整个应用唯一网关；业务退出只清 Token，未清这个懒加载实例。聊天页 `ensureConnected` 仅凭 `isReady()` 跳过凭证获取，因此业务登录 B 后仍以 A 的 TIM 身份向 A 发送。页面使用 B 的头像绘制 outgoing 气泡，掩盖了实际 sender。微信授权与验证码登录共用按 App userId 签发的 IM 凭证，本次故障是两套登录态没有同步。

之前 REST 管理员双向联调绕开了手机残留连接，证明云端投递正常但无法排除此缺陷。此结论补充既有私信双源一致性方案。

## 2. 方案与调用链

业务登录身份/Token 变化 → 内存认证代次递增 → 旧网关同步失效 → 异步 logout/destroy → 消息分包按需创建新网关 → 当前 Token 获取 `/miniapp/im/credentials` → TIM login → SDK_READY → 正常发送。

只使用已有接口和唯一 `app_user_im_account`，不新增服务或数据库表。认证代次、UserSig、原始消息不持久化。主包只引用轻量生命周期模块，不静态加载 TIM。

## 3. 状态边界

| 触发 | 行为 |
|---|---|
| 用户或 Token 改变、退出、恢复不同登录态 | 代次递增，立即使旧网关不可用；排队完成旧实例销毁后才新建 |
| 同一用户/Token 的昵称头像更新、主页返回 | 网关和滚动缓存继续复用 |
| 旧 SDK_READY、旧导入 Promise、旧凭证响应迟到 | 代次校验拒绝，禁止初始化或恢复旧身份 |
| 旧页面持有网关引用 | 所有 SDK 操作检查所属代次；发送、历史、已读不能借用旧身份 |
| 目标等于当前 TIM 用户 | 在气泡创建、发送和重试前拒绝 |
| 发送完成时已切号 | 不合并到新账号页面 |

继续使用原有平台/TIM 双源排序、首屏单次提交、分页和返回位置策略。历史错发消息没有真实 1052 的发送身份，本次不自动改写或补发这些消息。

## 4. 端范围、安全与 PRD-07 推广裂变联动影响

后端、管理端、权限、计费、关系匹配和数据库均无变更。Token 仍为 `X-Auth-Token`，IM UserID/UserSig 仍由后端签发。原 skill 的 2026-05-22 推广方案和架构文件已不存在，已参照现存 `2026-07-27-PRD-07推广裂变与邀请奖励重构-tcdesign.md` 第 10 节：注册归因和奖励继续由后端首次事实及事件键处理。本修复只清客户端 IM 会话，不新增推广事件、奖励或注册调用，不改变幂等键和失败策略。
