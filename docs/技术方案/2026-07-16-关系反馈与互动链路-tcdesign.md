## 1. 背景与目标

本方案把已冻结的 PRD-02 关系反馈规则转换成可实施的数据模型、后台接口、权限审计和管理后台交互设计。当前仓库已有 App 用户列表、独立统计接口、商业化资产与解锁记录，但不存在喜欢、访客、匹配、匹配来源和匹配弹窗状态表；管理后台“模块补充”弹窗中的关系摘要与四类明细仍为前端硬编码数据。

本轮技术方案覆盖：

1. 喜欢、访客、匹配、匹配来源、匹配弹窗状态及失效联动的公共领域模型。
2. App 用户管理列表中的关系准入/VIP 筛选，以及模块补充弹窗的关系摘要和四类真实分页查询。
3. 注销匿名化、最小权限、敏感字段脱敏、查看审计和永久留存。
4. 管理后台按已同步静态 Demo 还原，App 用户主列表继续固定每页 9 条。
5. 移动端后端实现喜欢、访客、匹配、弹窗及两步单条解锁接口；小程序页面仍由后续移动端任务按 handoff 对接。

## 3. 总体架构与方案选型

### 3.1 总体架构

| 层 | 设计 |
|----|------|
| 后端技术栈 | Java 21、Spring Boot 3.4、MyBatis-Plus、MySQL、Redis |
| 分层 | `Controller -> Service -> ServiceImpl -> DAO -> DAOImpl -> Mapper` |
| 模块边界 | `admin/` 与 `miniapp/` 不互相导入；关系实体、枚举、DAO、状态机和失效服务放 `common/` |
| 管理后台 | React 18 + TypeScript + Vite + Tailwind；API 放 `frontend/src/api/` |
| 数据一致性 | 关系写入、来源变更、失效和弹窗状态使用数据库事务；唯一约束兜底并发 |
| 查询策略 | App 用户列表只返回卡片必要字段；关系摘要和四类明细在弹窗打开后懒加载 |
| 审计 | 复用 `content_operation_log`，记录每次关系摘要/明细查看；不记录响应中的手机号或完整个人资料 |
| 删除策略 | 关系事实不物理删除，也不开放逻辑删除入口；`deleted` 仅为项目统一基线字段 |

### 3.2 方案比较

| 方案 | 说明 | 优点 | 缺点 | 结论 |
|------|------|------|------|------|
| A. 单张通用关系表 + JSON | 喜欢、访客、匹配统一存类型和 JSON | 表少、初期快 | 状态约束弱，索引、分页、唯一关系和审计查询复杂 | 不采用 |
| B. 分类型事实表 + 公共领域服务 | 喜欢、访客、匹配、来源、弹窗分别建表；后台懒加载 | 约束清晰、查询稳定、与 PRD 状态机一一对应 | 表较多，需明确事务边界 | 推荐 |
| C. 事件溯源 + 独立读模型 | 所有动作写事件，再构建关系读模型 | 扩展性强、审计完整 | 当前规模下基础设施和运维成本过高 | 暂不采用 |

### 3.3 关键取舍

1. **访客去重以数据库游标保证正确性。** 不只依赖 Redis 锁，也不使用固定半小时自然桶。每个访问用户对持有一条游标，事务内 `SELECT ... FOR UPDATE`，按最近一次访问时间做滚动 30 分钟归并。
2. **原始访客事件与展示记录分离。** 每个真实页面进入事件用 `event_no` 幂等落库；展示记录汇总 `pv_count`。网络重试不重复增加 PV，UV 按访客用户去重。
3. **解锁沿用现有资产事实表。** 扩展 `app_user_unlock_record` 关联具体喜欢/访客记录，不新增第二套关系解锁台账。
4. **主列表不聚合关系明细。** 关系统计不参与 9 条卡片查询；避免用户列表随着关系数据量增长变慢。
5. **不设固定 SQL 条数上限。** 以禁止 N+1、索引命中、批量补充和 P95 指标验收；后续新增必要数据允许增加固定次数查询。
6. **喜欢我的使用用户级读取游标和查询快照。** `(liked_time,id)` 同时作为已读位置与本次分页上界；首屏确认已读后，后续页继续回传同一快照，避免并发新喜欢导致重排、重复或漏项。
7. **在线状态使用“鉴权请求即活跃”。** `TokenInterceptor` 仅对已通过鉴权的 `/miniapp/**` 请求刷新 Redis；在线标记 TTL 5 分钟，最近活跃时间保留 30 天，关系列表按当前页用户批量读取，禁止逐用户 Redis 查询。

## 4. 前后台闭环设计

| 闭环 ID | 移动端 | 公共后端 | 管理后台 | 通知/反馈 | 验证方式 |
|---------|--------|----------|----------|-----------|----------|
| `CL-02-01` 喜欢 | 发起/取消喜欢、查看喜欢我的并确认已读 | 写 `app_relation_like`，用 `app_relation_like_inbox_state` 保存用户级读取位置，检查匹配来源 | 喜欢 Tab 查询方向、来源、状态、失效原因 | 前台只返回有效对象；并发新喜欢不被旧游标误读 | 移动端 Controller/L3 + 后台 API |
| `CL-02-02` 访客 | 进入婚恋主页上报事件、查看最近访客 | 事件幂等、30 分钟归并、PV 累计；查询时按访客用户聚合 | 摘要显示 7 天 UV/PV，访客 Tab 查明细 | 超 7 天前台不返回；普通用户全部已解锁访客加最近 10 个未解锁访客，VIP 全量 | 移动端 Controller/L3 + 并发边界测试 |
| `CL-02-03` 匹配 | 双向喜欢/回爱心/悄悄话回复 | 单一有效匹配，多来源追加 | 匹配 Tab 展示来源、状态、原因 | 双方各生成一次待展示状态 | 唯一约束 + 移动端查询测试 |
| `CL-02-04` 弹窗 | 查询待展示并主动动作回执 | `matchNo + userId` 独立保存 | 后台只读查看关系，不人工改状态 | 失败渲染/异常退出不标已读 | Controller + L3 幂等测试 |
| `CL-02-05` 单条解锁 | 两步弹窗，第二步确认扣币 | 喜欢按具体关系记录授权；访客按目标用户授权并保留触发记录号审计；复验、幂等、扣币 | 解锁 Tab 关联关系与资产记录 | 取消不扣币；同一访客的新 `VIS-*` 不重复扣币；失效不自动退款 | quote/confirm 事务与余额防透支测试 |
| `CL-02-06` 关系失效 | 前台立即移除 | 拉黑/账号/认证事件批量失效 | 后台保留原因和时间 | 不向前台暴露真实原因 | 状态联动测试 |
| `CL-02-07` 注销 | 前台不再展示 | 关系事实保留、身份输出匿名化 | 显示 `ANON-*`，不展示原昵称/手机号/头像 | 无前台失效弹窗 | 权限与脱敏测试 |
| `CL-02-08` 客服排查 | 无 | 只读聚合与分页接口 | 卡片 -> 模块补充 -> 关系反馈 Tab | loading/空态/失败提示 | L2/L4 + 截图证据 |

## 5. 后端设计

### 5.1 管理后台接口清单

所有路径沿用现有 `AppUserController` 基地址 `/admin/users/app`，Controller 返回精确 `R<T>`。项目当前业务异常由 `GlobalExceptionHandler` 包装为 `R.code`，除权限拦截返回 HTTP 403 外，不在本需求中单独改变全局 HTTP 状态策略。

| 端 | Method | Path | 权限 | 入参 | 出参 | 业务错误码 |
|----|--------|------|------|------|------|------------|
| ADM | GET | `/admin/users/app/list` | `user:app:list` | 既有条件 + `relationshipAccess`、`vipStatus`，主列表 `size=9` | `Page<AppUserListVO>` | `4001` 参数错误 |
| ADM | GET | `/admin/users/app/{userId}/relations/summary` | `user:app:relation:view` | `userId` | `AppUserRelationSummaryVO` | `20009` 用户不存在、`20010` 审计不可用 |
| ADM | GET | `/admin/users/app/{userId}/relations/likes` | `user:app:relation:view` | `RelationPageReq` | `Page<AppUserRelationLikeVO>` | `20008` 查询参数错误、`20010` |
| ADM | GET | `/admin/users/app/{userId}/relations/visits` | `user:app:relation:view` | `RelationPageReq` | `Page<AppUserRelationVisitVO>` | `20008`、`20010` |
| ADM | GET | `/admin/users/app/{userId}/relations/matches` | `user:app:relation:view` | `RelationPageReq` | `Page<AppUserRelationMatchVO>` | `20008`、`20010` |
| ADM | GET | `/admin/users/app/{userId}/relations/unlocks` | `user:app:relation:view` | `RelationUnlockPageReq` | `Page<AppUserRelationUnlockVO>` | `20008`、`20010` |

#### 5.1.1 列表筛选契约

| 参数 | 允许值 | SQL 口径 | 展示映射 |
|------|--------|----------|----------|
| `relationshipAccess` | `OPEN` / `CLOSED` / `ABNORMAL` | `OPEN`=账号正常且核心准入允许；`CLOSED`=账号正常但资料/认证未满足；`ABNORMAL`=冻结、注销中或已注销 | 开放 / 未开放 / 账号异常 |
| `vipStatus` | `active` / `inactive` / `expired` | 读取 `app_user_asset`；无资产行按 `inactive`；到期时间已过即按 `expired`，不依赖定时任务是否刚执行 | VIP会员 / 未开通 / 已过期 |

`relationshipAccess` 是对 PRD-01 核心准入与账号状态的后台展示投影，不新增持久化状态字段。旧中文值和 `ACTIVE/NONE/EXPIRED` 不作为新契约；前后端同一次发布切换到上表值。`hideVisitRecord` 从 `AppUserPageReq` 和前端 API 类型中删除。

`AppUserListVO` 增加 `relationshipAccess、vipVisible、vipStatus`，关系准入由统一投影服务计算，VIP 对当前页用户一次批量加载。没有 `commercial:user:view` 时，前端隐藏 VIP 筛选和列表 VIP 字段；后端若仍收到 `vipStatus` 参数则返回 403，防止通过筛选结果反推会员身份。

#### 5.1.2 明细分页契约

`RelationPageReq` 字段：

| 字段 | 类型 | 默认 | 规则 |
|------|------|------|------|
| `page` | int | 1 | 大于等于 1 |
| `size` | int | 10 | 只允许 10、20、50 |
| `direction` | enum | `ALL` | `ALL`、`OUTBOUND`（当前用户发起）、`INBOUND`（当前用户接收） |
| `status` | string | 空 | 按当前 Tab 的正式状态枚举校验 |
| `source` | string | 空 | 喜欢/访客用来源场景；匹配用匹配来源；解锁用场景 |
| `startTime` | datetime | 访客为 7 天前，其余为空 | `yyyy-MM-dd HH:mm:ss`，闭区间起点 |
| `endTime` | datetime | 当前时间或空 | 不早于 `startTime`，闭区间终点 |

每个 Tab 按业务时间倒序、`id` 倒序稳定分页。切换 Tab、筛选条件或每页条数由前端回到第 1 页。

#### 5.1.3 响应字段

| VO | 核心字段 |
|----|----------|
| `AppUserRelationSummaryVO` | `userId, relationshipAccess, vipVisible, vipStatus, activeLikedCount, visitorUv7d, visitorPv7d, activeMutualCount, lastMatchTime` |
| `RelationCounterpartyVO` | `userId, userNo, nickname, maskedPhone, avatar, anonymous`；注销后 `userId=null`，只返回 `userNo=ANON-*` 和 `anonymous=true` |
| `AppUserRelationLikeVO` | `recordNo, direction, counterparty, sourceScene, status, invalidReason, invalidTime, likedTime, unlockNo` |
| `AppUserRelationVisitVO` | `recordNo, direction, counterparty, sourceScene, status, invalidReason, invalidTime, firstVisitTime, lastVisitTime, visitCount, unlockNo` |
| `AppUserRelationMatchVO` | `recordNo, counterparty, primarySource, activeSources, status, invalidReason, invalidTime, matchedTime` |
| `AppUserRelationUnlockVO` | `unlockNo, targetBizType, targetBizNo, counterparty, unlockScene, unlockMethod, coinCost, status, effectiveTime, expireTime, targetAvailable, targetInvalidReason, targetInvalidTime, assetVisible` |

没有 `commercial:user:view` 时，摘要返回 `vipVisible=false, vipStatus=null`；解锁记录仍可显示业务编号、状态和目标关系，但 `coinCost` 等资产字段为空且 `assetVisible=false`。

#### 5.3.4 迁移脚本

实现阶段新增：

- `backend/docs/sql/schema-relation.sql`：关系领域完整建表基线。
- `deploy/sql/prod/056_prd02_relation_feedback.sql`：生产增量迁移与权限种子。

迁移顺序固定为：

1. 预检 `app_user_unlock_record` 历史状态、重复请求和缺失目标数据，输出数量，不删除记录。
2. 创建 8 张关系表，并以每名用户迁移时最新有效喜欢初始化喜欢收件箱读取基线。
3. 为 `app_user`、`app_user_unlock_record` 增加字段。
4. 将解锁历史 `ENABLED -> active`、`DISABLED -> expired`；为历史记录回填 `unlock_no=ULK-LEGACY-*`。
5. 历史喜欢/访客解锁无法确定具体关系记录时，保留 `target_biz_type/target_biz_no=NULL` 作为审计记录，不自动授予任意新关系记录清晰权益。
6. 为已注销用户生成随机稳定 `anonymous_no`；不在 SQL 或日志输出手机号、openid 等身份信息。
7. 建唯一约束和查询索引，再写 `user:app:relation:view` 功能权限种子。

迁移必须可重复执行；新增列通过 `information_schema` 检查，种子使用 `NOT EXISTS`。不提供破坏性 down 脚本：代码回滚时隐藏入口并停止新写入，保留已产生的永久关系事实。生产迁移不插入演示关系数据，测试数据只进入测试 fixture 或本地专用 seed。

| `active` | 发起方取消 | `cancelled` | marker=NULL、原因 `like_cancelled`；撤销对应匹配来源 |
| `active` | 拉黑/冻结/注销/封禁/认证回退 | `invalid` | marker=NULL，写真实原因和时间 |
| `cancelled/invalid` | 再次合法喜欢 | 新 `active` 生命周期 | 新 likeNo；历史记录不修改、不删除 |

#### 5.4.2 访客

| 当前状态 | 事件 | 目标状态 | 同事务副作用 |
|----------|------|----------|----------------|
| 无 | 新 eventNo 且不在 30 分钟滚动窗口 | `visible` | 新展示记录，PV=1，游标指向新记录 |
| `visible` | 新 eventNo 且距最近访问不足 30 分钟 | `visible` | 同记录 PV+1，更新 lastVisitTime；不新增展示记录 |
| 任意 | 重复 eventNo | 不变 | 幂等返回，不增加 PV |
| `visible` | 超过 7 天 | `expired_window`（查询即时判定，批任务可补写） | 前台查询按时间窗口立即排除 |
| `visible/expired_window` | 账号/关系失效 | `invalid` | 写真实原因和时间 |

#### 5.4.3 匹配与来源

| 当前状态 | 事件 | 目标状态 | 同事务副作用 |
|----------|------|----------|----------------|
| 无 | 首个合法来源 | `matched` | 规范化 low/high，插入来源，为双方各写 pending 弹窗 |
| `matched` | 新来源事件 | `matched` | 幂等追加来源，不新建匹配、不再生成弹窗 |
| `matched` | 单个爱心来源撤销且仍有其他 active 来源 | `matched` | 仅来源转 revoked |
| `matched` | 最后一个来源撤销 | `invalid` | marker=NULL，原因 `like_cancelled`，待展示弹窗取消 |
| `matched` | 拉黑/冻结/注销/封禁/认证回退 | `invalid` | 整体失效，不受其他来源是否 active 影响 |
| `invalid` | 后续新合法来源 | 新 `matched` 生命周期 | 新 matchNo、新来源、双方重新各有一次弹窗 |

#### 5.4.4 匹配弹窗

| 当前状态 | 事件 | 目标状态 | 说明 |
|----------|------|----------|------|
| `pending` | 待展示接口返回 | `pending` | 只写 deliveredTime，不视为已读 |
| `pending` | 稍后/关闭/去主页/去聊天/系统返回 | `read` | 客户端成功渲染后按用户主动动作调用回执 |
| `pending` | 加载失败、未渲染、应用异常退出 | `pending` | 不调用回执，下次继续返回 |
| `pending` | 匹配先失效 | `cancelled` | 后续不返回弹窗 |
| `read/cancelled` | 重复回执 | 不变 | 幂等成功 |

#### 5.4.5 解锁

| 当前状态 | 事件 | 目标状态 | 说明 |
|----------|------|----------|------|
| 无 | 第二步复验成功并扣币 | `active` | 写触发 relationNo、目标用户、流水和 active_marker=1；访客权益按目标用户复用 |
| `active` | 时间型场景到期 | `expired` | 关系单条解锁为永久，expireTime=NULL，不走此分支 |
| `active` | 特批退款完成 | `refunded` | marker=NULL，记录 refundNo，权益失效 |
| `active` | 目标关系/账号失效 | `active` | 财务事实不改、不自动退款；前台因 targetAvailable=false 移除 |

### 5.5 事务、幂等、并发与失效联动

#### 5.5.1 访客写入

```text
事务开始
  插入 visit_event(eventNo)；唯一冲突则返回原结果
  INSERT IGNORE visit_cursor(visitorId, targetId)
  SELECT visit_cursor ... FOR UPDATE
  若 lastVisitTime >= now - 30min 且当前记录可归并：visit.pvCount + 1，并保留展示记录首次 sourceScene
  否则：插入新的 visit 展示记录
  更新 event.visitId 与 cursor
提交
```

`app_relation_visit_event.source_scene` 永久保存每次实际进入的精确来源；`app_relation_visit.source_scene` 保存该 30 分钟展示记录的首次来源，后续归并访问不覆盖，以避免聚合记录来源随最后一次访问漂移。Redis 只可作为热点削峰，不能成为正确性唯一依据。服务端以接收时间校正明显超前/滞后的客户端时间，避免伪造时间绕过去重。

#### 5.5.2 最近访客列表投影与解锁

最近访客查询使用 MySQL 8 CTE 和窗口函数，不改写底层访问事实：

1. 过滤 `target_user_id=当前用户、visit_status=visible、last_visit_time>=当前时间-7天、deleted=0`。
2. 按 `visitor_user_id` 分组，聚合 `MIN(first_visit_time)、MAX(last_visit_time)、SUM(pv_count)`；使用 `ROW_NUMBER()` 选出最近一条展示记录的 `id、visit_no、source_scene`。
3. 将有效访客单条解锁按 `target_user_id` 分组后关联。普通用户保留全部已解锁访客和最近 10 个未解锁访客，VIP 保留全部访客。
4. 可见集合统一按 `last_visit_time DESC、最近展示记录 id DESC` 分页；`total` 按窗口内访客用户去重，`visibleTotal` 按当前权益集合计数，`hiddenCount=total-visibleTotal`。
5. `blur/clear` 均批量组装基础资料、字典中文和 Redis 在线状态；`displayStatus` 只作为客户端展示依据。

访客 quote 仍要求当前 `targetBizNo` 对应有效且未超 7 天的展示记录，以防伪造目标；授权判断使用该记录解析出的 `targetUserId`。confirm 先锁定当前用户资产行，再复验是否已存在 `userId + visit + targetUserId` 的有效解锁，因此并发确认或同一访客新记录报价都不会重复扣币。落库仍保存触发 `targetBizNo`，便于客诉和财务审计。

#### 5.5.3 匹配写入

用户对统一规范为 `low=min(A,B), high=max(A,B)`。先按 `source_type + source_event_no` 做幂等；查询有效匹配并加行锁，无有效记录时插入 active_marker=1。并发插入由 `uk_match_active_pair` 兜底，捕获唯一冲突后回查有效匹配并继续追加来源。只有创建新生命周期时才插入两条弹窗记录。

#### 5.5.4 失效入口

`RelationLifecycleService` 提供以下公共方法，供现有模块在自身事务内调用：

| 方法 | 调用方 | 原因 |
|------|--------|------|
| `invalidateByUser(userId, ACCOUNT_FROZEN, time)` | App 用户冻结/停用 | `account_frozen` |
| `invalidateByUser(userId, ACCOUNT_DELETED, time)` | 注销中/已注销 | `account_deleted` |
| `invalidateByUser(userId, RISK_BANNED, time)` | 风控封禁 | `risk_banned` |
| `invalidateByUser(userId, CERTIFICATION_REVOKED, time)` | 核心准入从允许回退 | `certification_revoked` |
| `invalidateByPair(userId, targetId, BLOCKED, time)` | 黑名单新增 | `blocked` |

解除拉黑、解冻或重新认证不恢复旧关系；用户后续重新满足条件时生成新生命周期。`admin/` 和 `miniapp/` 都只调用 `common` 服务，禁止互相导入。第一阶段实现需接入账号状态、黑名单和统一审核服务的状态变化点；风控封禁若上游尚无正式事件，只保留公共方法和契约，不虚构调用。

#### 5.5.5 摘要与明细查询

摘要使用索引聚合实时计算，不建立冗余计数快照：

- `activeLikedCount`：当前用户为接收方且 like_status=active。
- `visitorUv7d`：按 `app_relation_visit_event.visit_time` 精确截取最近 7 天，关联非 invalid 展示记录后对 visitorUserId 去重。
- `visitorPv7d`：按同一事件时间范围统计 eventNo 数量；不直接汇总跨越 7 天边界的整条 30 分钟展示记录。
- `activeMutualCount`：用户参与且 match_status=matched。
- `lastMatchTime`：用户全部匹配生命周期的最大 matchedTime。

四类明细先分页查询事实表，再按当前页 counterparty IDs 批量加载用户；喜欢/访客页的解锁号也按当前页 relationNos 批量查询。禁止循环内逐用户或逐记录查库。

1. 基础集合只查 `like_status=active AND active_marker=1 AND deleted=0`。取消喜欢、账号或认证异常、拉黑等状态变化由关系生命周期服务更新关系表，列表不重复拼装账号状态条件。

3. 普通用户的 `visibleTotal` 为全部有效单条已解锁记录加最近 10 条未解锁记录；VIP 的 `visibleTotal=total`。`pages/hasMore` 按 `visibleTotal` 计算。
4. SQL 使用 MySQL 8 窗口函数给未解锁集合独立编号，已解锁记录不占用 10 条名额；随后按新喜欢、早期已解锁、早期未解锁三段排序。

6. 卡片返回 `onlineStatus/lastActiveTime/onlineText`；顶部新喜欢头像摘要返回 `onlineStatus` 和头像 URL。
7. 模糊态和清晰态均返回完整基础资料，包括 `userId、avatar、nickname、age、school、company` 及 `identity、industry、occupation、annualIncome` 的 code/中文 label；前端只依据 `displayStatus` 控制展示样式，字典按本页实际 code 批量加载，不逐记录查询。

### 6.1 小程序在线状态

1. `TokenInterceptor` 完成 token 解析并写入 `UserContext` 后，仅对 `/miniapp/**` 调用 `MiniappPresenceService.touch(userId, now)`；管理后台请求不刷新小程序在线状态。
2. Redis 在线键：`miniapp:presence:online:{userId}`，值为 ISO 本地时间，TTL 5 分钟。
3. Redis最近活跃键：`miniapp:presence:last-active:{userId}`，值为 ISO 本地时间，TTL 30 天。
4. 喜欢列表对当前页和头像摘要涉及的用户 ID 分别执行两次 `multiGet`，得到在线标记和最近活跃时间；Redis无记录时以 `app_user.last_login_time` 兜底。
5. 在线写入和读取均为附加展示能力，异常时不阻断鉴权和关系查询；降级结果为最近登录时间推算或离线。
6. `onlineText` 由后端统一生成：在线、N分钟前在线、N小时前在线、N天前在线、7天前在线。

PRD 边界：

- PRD-02 只返回 `canEnterConversation`。
- PRD-03 在会话内返回 `canSend`、`protectStatus`；女性保护不得使 `canEnterConversation=false`。
- PRD-04 负责报价、扣币、流水和特批退款。
- PRD-05 负责婚恋用户主页主体与动作入口。
- 一期无隐藏访问字段、接口、过滤或统计分支。

### 10.2 查看审计

每次摘要或明细成功返回前写一条 `content_operation_log`：

| 字段 | 值 |
|------|----|
| `biz_type` | `PRD02_RELATION_VIEW` |
| `biz_id` | 被查询 App 用户 ID |
| `action` | `VIEW_SUMMARY/VIEW_LIKES/VIEW_VISITS/VIEW_MATCHES/VIEW_UNLOCKS` |
| `before_value` | NULL |
| `after_value` | 只记录 tab、page、size、筛选 code、结果条数、资产字段是否可见、requestId |
| `remark` | `关系反馈受控查看` |

日志不记录昵称、手机号、头像、关系对方清单或完整响应。审计写入失败时敏感查询失败关闭，返回 `20010`，不能无日志放行。查看日志和关系事实均无删除入口。

### 10.3 匿名化与保留

1. 关系表只保存内部用户 ID，不保存昵称、手机号、头像快照。
2. 账号为 `CANCELLING/CANCELLED` 时，后台关系 DTO 只返回稳定 `ANON-*`；不返回原昵称、手机号、头像或可跳转用户详情动作。
3. 喜欢、访客、匹配、来源、弹窗、解锁和查看审计永久保留，不调用逻辑删除。
4. 财务订单、币流水和退款仍由 PRD-04 受控留存；关系服务不修改财务事实。
5. 任何后续物理清理必须单独经过法务/安全留存规则评审，不属于本模块普通运维能力。

## 11. 性能、可观测性与降级

### 11.1 性能目标

| 场景 | 目标 | 设计保障 |
|------|------|----------|
| App 用户列表 9 条 | 不因关系数据量增加而放大查询 | 不查询关系摘要/明细；VIP 当前页批量补充；关系筛选在 SQL 层完成 |
| 关系摘要 | 测试环境 P95 <= 800ms | 索引聚合，不加载明细，不建 N+1 |
| 明细 10/20/50 | 测试环境 P95 <= 800ms（50 条） | 事实表稳定分页 + 对方/解锁批量组装 |
| 并发访问写入 | 同一用户对无重复 active 事实 | 行锁、请求唯一键、active_marker 唯一约束 |

不设置“最多 5 条 SQL”等固定总数。实现后记录每个 API 的 SQL 次数、扫描行数和 P95；数据补充必须是固定次数批量查询。若 EXPLAIN 未命中设计索引或扫描行数显著大于返回行数，先调整查询/索引，再考虑缓存。首版不缓存摘要，避免失效与客服实时排查口径漂移。

### 11.2 监控与日志

- 指标：接口 P50/P95/P99、失败率、审计写入失败、唯一冲突次数、访客归并次数、关系失效批量行数。
- 慢查询：摘要/明细超过 800ms 记录 userId 哈希、Tab、筛选和耗时，不记录用户 PII。
- 数据一致性告警：同一 active 用户对重复、active_marker 与状态不一致、匹配无来源、popup 非双方两条。

### 11.3 降级

| 故障 | 降级行为 |
|------|----------|
| 关系摘要查询失败 | 弹窗摘要显示 `-` 和重试；App 用户主列表不受影响 |
| 某明细 Tab 失败 | 只显示该 Tab 失败态，保留摘要和其他 Tab 数据 |
| PRD-04 资产查询失败 | 关系记录可查，资产字段置空、解锁/流水跳转置灰 |
| 审计写入失败 | 关系敏感查询失败关闭，不返回数据 |
| Redis 不可用 | 访客去重继续依赖数据库游标；在线状态以最近登录时间兜底，活跃写入失败不阻断鉴权和关系接口 |

## 12. 风险与处理

| 风险 | 影响 | 处理/验证 |
|------|------|-----------|
| 历史解锁无法映射具体关系记录 | 误授予或误拒绝清晰权益 | 历史记录仅审计展示，不自动映射；上线前输出预检数量并由业务确认 |
| `ENABLED` 与正式 `active` 状态并存 | 解锁幂等和后台筛选错误 | 同一迁移规范化数据并同版本修改枚举/服务；L1 校验无旧值 |
| 账号/认证状态变更未调用失效服务 | 前台可能继续显示不可互动对象 | 对账号、黑名单、审核状态变化点做集成测试；提供一致性巡检 SQL |
| 访客事件量长期增长 | 表体积和索引成本上升 | 按月监控行数和索引；永久留存不删除，达到阈值后单独设计归档库/分区迁移 |
| 在线状态被理解为严格实时 | 关闭小程序后短暂仍显示在线，静止页面可能转离线 | 接口及文案明确为最近5分钟活跃；严格前台在线留给后续心跳/WebSocket方案 |
| 权限只在前端控制 | 敏感关系数据越权 | 每个后端接口强制 `@RequirePermission`，资产字段二次裁剪 |
| 匿名号生成失败 | 注销用户身份泄露 | API 失败安全：只显示“匿名用户”，绝不回退原身份；修复任务补生成 |
| 前端快速切 Tab 回包乱序 | 旧数据覆盖当前筛选 | AbortController/请求序号；前端用例覆盖 |
| 移动端未按展示状态处理完整资料 | 未解锁记录被错误展示为清晰态 | 前端必须以 `displayStatus` 为唯一展示依据；`blur` 统一应用模糊头像和受限文本样式 |
