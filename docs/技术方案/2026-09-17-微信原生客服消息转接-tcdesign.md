# 微信原生客服消息转接技术方案

> 日期：2026-09-17
> 关联需求：`docs/superpowers/specs/2026-09-16-official-assistant-wechat-service-design.md`；微信小程序原生客服会话无法进入“客服小助手”待接入队列。

## 1. 背景、目标与现状

小程序“官方小助手”已经使用 `Button openType="contact"` 打开微信原生客服会话。公众平台已开启“消息推送”，推送 URL 指向 `/miniapp/content-security/wechat/callback`。该 URL 的现有 POST 实现仅处理 `wxa_media_check` 内容安全审核：普通客服消息缺少 `trace_id`，最终报 `media_trace_missing`；非媒体审核事件可能报 `media_callback_event_invalid`。Controller 只会返回 `success`，没有返回微信客服转接消息。因此用户可在自己的会话中看到已发送消息，客服小助手却无法接入。

目标：用户发给原生客服的消息进入微信“客服小助手”的待接入队列；现有图片/音频异步审核回调继续正常处理。验收同时覆盖首次消息、再次进入会话、多人客服在线和审核回调不回归。

## 2. 关键决策及范围

| 项 | 决策 | 依据 |
|---|---|---|
| 客服产品 | 保留微信原生客服及“客服小助手” | 用户此前已选定该方案，本次只补齐转接 |
| 消息推送 | 保持开启，共用现有回调 URL | 内容安全异步审核也依赖此 URL |
| 数据存储及后台 | 不新建客服消息表、坐席后台、分配规则 | 会话和坐席由微信管理，本次不建设自有系统 |
| 小程序前端 | 原生客服入口不变 | 入口已能打开会话，故障在服务端转接 |
| 微信平台配置 | 保持当前“明文模式 + JSON”直至联调完成 | 与当前截图一致；协议格式必须在微信官方文档及真机回调中复核 |

没有待用户选择的产品决策。上线前的技术门禁：使用微信官方当前协议核对转接响应字段、大小写、Content-Type 和超时要求；以真机消息在客服小助手出现为最终验证。微信开发者文档入口：<https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/customer-message/trans.html>。该站点当前无法由本工作环境直接读取，不把未核验的协议细节当作已确认事实。

## 3. 方案取舍

| 方案 | 做法 | 结论 |
|---|---|---|
| 最小改动 | 在现有 POST 入口验签、分类，并为客服消息返回转接响应；审核消息继续走原服务 | **推荐**，改动集中、无需数据库或管理后台 |
| 平衡方案 | 抽出独立的微信回调路由 Service，并复用审核 Service；加入类别级指标和安全审计 | 若后续还会接入更多微信事件，可在最小方案基础上演进 |
| 完整方案 | 建自有会话、坐席分配和管理后台 | 与“微信原生客服”决策冲突，当前不做 |
| 关闭消息推送 | 由微信直接把用户消息送到客服工具 | 可能中断媒体审核异步回调，不选 |

## 4. 总体调用链

```text
用户点击 openType="contact" 并发消息
  → 微信消息推送 POST /miniapp/content-security/wechat/callback
  → 验签、解析原始 JSON、识别消息/事件类型
    ├─ wxa_media_check → 现有 CommunityMediaAuditCallbackService → 纯文本 success
    ├─ 用户客服消息 → 构造微信客服转接响应 → 客服小助手待接入队列
    └─ 其他微信事件 → 记录类别级日志，按协议应答；不误转接给坐席
```

用户一旦被客服接入，后续消息由微信客服系统处理；如果微信再次把消息推送到本端，应仍按当前类型路由，不靠本地内存标记判断“已接入”。

## 5. 后端设计

### 5.1 接口及分层

| 层 | 文件/职责 | 变更 |
|---|---|---|
| Controller | `miniapp/controller/CommunityMediaAuditCallbackController.java` | GET 验证 URL 保持不变；POST 从固定 `success` 改为输出路由 Service 的原始微信协议响应；显式设置响应类型；错误响应不能被通用 `R<T>` 包装。该回调是第三方协议端点，属于普通业务 API 的返回体例外。 |
| Service | 新增微信消息推送路由接口 | 输入验签参数、Content-Type、原始消息；输出 `success` 或转接响应，不依赖数据库。 |
| ServiceImpl | 新增路由实现 | 统一验签、解析与分类；仅识别到真实用户客服消息才转接。转接回复交换 `ToUserName`/`FromUserName`，设置协议要求的时间及 `MsgType=transfer_customer_service`；字段名和序列化按当前微信官方协议实现。 |
| 现有审核 Service | `CommunityMediaAuditCallbackServiceImpl` | 继续处理 `wxa_media_check`，保留现有 trace_id、状态流转和幂等规则；必要时拆出已验证负载入口，避免重复验签和误分类。 |
| DAO/Mapper | 不变 | 本次不持久化客服消息。 |

路由条件须先看明确的事件类型和 `MsgType`，不能简单以“没有 `trace_id`”推断为客服消息。只有微信定义的用户消息类型进入转接分支；`wxa_media_check`、进入会话事件和其他系统事件不得转接。对未知类型记录类型、时间和请求关联 ID，不记录消息正文、OpenID 明文或密钥。

### 5.2 安全与错误响应

- POST 与 GET 均在处理前按现有 Token 校验微信签名；对非法签名返回真正的 HTTP 4xx，而不是 HTTP 200 中包装业务错误 JSON。
- 验签后、JSON/XML 解析前按 UTF-8 字节数限制回调体为 1 MiB；超限返回 HTTP 400 和 `fail`。微信的媒体审核回调仅携带事件结果，不携带原始媒体文件；原有审核处理逻辑与幂等规则不变。
- 检查 JSON 结构和必要字段；签名无效或格式损坏时不返回转接消息。
- 客服消息响应必须在微信规定时限内完成，不能同步调用慢查询或其他远端服务。
- 媒体审核处理异常不得被伪装为 `success`；分别记录审核失败和客服转接失败指标，避免静默丢消息。
- 当前截图已暴露回调 Token 和 EncodingAESKey。上线时应在后端私有环境与公众平台协调轮换，先完成配置一致性验证；源码、文档、日志均不写真实值。

## 6. 数据库、管理后台与小程序

本次无表结构、管理后台 API/RBAC、管理后台页面或小程序页面变更。坐席在微信“客服小助手”查看和接入，不在本项目后台“反馈箱”中查看。多人在线不意味着每人都收到一份独立消息；以微信客服工具的接入/分配行为为准。

## 7. 测试与验收

| 层级 | 验证点 |
|---|---|
| 单元测试 | 合法客服文字/图片等消息返回正确转接响应；`wxa_media_check` 仍调用原审核服务并返回 `success`；其他事件不转接；非法签名、缺字段、未知类型按协议处置。 |
| MockMvc | GET 挑战应答不回归；POST 的 Content-Type、状态码、原始响应体准确；异常不被全局 `R<T>` 包装。 |
| 现有回归 | 运行 `CommunityMediaAuditCallbackServiceImplTest`、`CommunityMediaAuditCallbackControllerTest` 和相关内容安全测试。 |
| 测试环境真机 | 两个不同用户账号各发一条客服消息；客服小助手在线账号能看到“待接入用户”并回复；用户能收到回复；同时提交图片/音频审核素材并核对回调任务终态。 |
| 安全测试 | 错签、重复消息、非客服事件、缺失字段、超大负载；日志不得含敏感正文与密钥。 |

没有真实测试环境账号和微信平台回调日志时，真机验收标记未执行，不以本地 Mock 代替成功结论。

## 8. 实施顺序与回滚

1. 复核微信当前转接协议与现有“明文 + JSON”配置，采集脱敏后的真实客服消息回调样本。
2. 先补失败测试，再实现消息路由、原始协议响应和签名错误的 HTTP 状态。
3. 运行审核回调及客服消息测试；在测试环境验证媒体审核和客服接入两条链路。
4. 更换已暴露的 Token/EncodingAESKey，协同更新后端私有环境与微信平台配置；部署后用新测试消息验收。
5. 回滚时恢复上一版后端及一致的回调密钥；不能只关闭消息推送，否则审核回调可能停止。
