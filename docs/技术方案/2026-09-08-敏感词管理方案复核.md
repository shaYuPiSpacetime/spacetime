## 结论

方案主要方向可实现，也符合当前单体六层架构：公共微信文本适配器是可复用接入点；本地 REJECT 可复用原状态机；全局刷新行锁配合当前读可实现未删除原词全局唯一；AC 不可变快照与主库 revision 可发现跨实例更新。无需引入新的审核业务状态机或消息基础设施。

当前仍不宜标记为“全部验收通过”或“后台已有真实词库”。方案存在以下 P1 契约与验证缺口，修订后可进入实现。没有从当前源码确认必然发生的 P0 运行缺陷；初始化全部启用的业务误拦策略由主线程向用户确认，本复核不代决策。

## 问题与建议

### P1-01：维护事务步骤存在矛盾

- 证据：技术方案 6.2 明确“读取词条和查重前取得锁”；7.3.4 第一步却写“先执行权限、参数和全局去重校验”，再在事务中保存并更新 revision。
- 风险：照后者实现会发生锁外查重，两个管理员同时新增相同原词均通过；普通 `(word, deleted)` 索引无法兜底。
- 更正：权限与无数据库依赖的参数校验 → 开启事务 → 锁定 id=1 刷新行 → 当前读目标及全局查重 → 更新词条 → 递增 revision → 提交 → 安全提交异步任务。初始化与所有维护入口相同锁顺序；刷新行缺失必须失败回滚，不能当 revision=0 继续写入。
- 验收：真实 MySQL 两连接用屏障同时新增、跨分类新增、修改撞词；最终只有一条未删除原词成功，失败请求不递增 revision。包含删除后新增及已停用词冲突。

### P1-02：证据、机审说明与用户提示尚无安全的数据契约

- 证据：方案 7.4 承诺保存 revision、id、原词、分类；`common/community/CommunitySecurityResult.java` 当前仅 conclusion/providerCode/detail。`common/provider/impl/WechatProviderResultMapper.java` 的 REJECT 把 detail 传给 rejectReason；`miniapp/service/impl/OpenTextAuditServiceImpl.java` 的 userFacingRejectReason 对含中文原因直接返回。社区 `CommunityServiceImpl.java:424`、`:535`、`:1237` 将 detail 写入 machineDetail 和审计 reason。
- 风险：若把含中文词库证据 JSON 直接放 detail，会被资料端当用户原因返回。现有 Mapper 的手写 JSON 也未完整处理换行等控制字符。方案未说明社区证据落在哪个容量足够的字段、后台如何读取展示。
- 更正：明确本地技术码、固定普通用户提示、结构化内部证据的独立契约；给出从本地结果到 Provider、external_provider_task/app_user_audit_record、community_post/comment/audit_record 再到后台 VO 的字段映射。使用 ObjectMapper；不要以“含中文”作为本地技术证据能否展示的判断。核对现有 SQL 的 machine_detail VARCHAR(1000)（058 迁移）和审计 reason 容量；长度不足时使用明确的独立证据字段/引用，不无声截断 JSON。
- 验收：构造中文、双引号、反斜杠、换行和最长合法词的命中，后台能解析并看到完整历史证据；所有 C 端响应只含普通提示，词条后续修改/删除不改写历史证据。

### P1-03：只有“有限超时”，无法证明故障不会拖垮业务线程及连接池

- 证据：方案 7.3.4 只写有限等待、最多三次；`CommunityServiceImpl.java:391/504`、`OpenTextAuditServiceImpl` 的提交入口已有外层事务。方案建议每次审核用独立 REQUIRES_NEW 读取主库。
- 风险：外层事务占用连接时，新事务还需一条连接；并发请求可占满共享主池并同时等待第二条连接。只限制 Future 等待不能限制之前同步获取连接、revision 查询或词条读取耗时；共享构建被单个请求超时取消也会影响其他请求。
- 更正：列出连接获取、单次查询、请求总等待、构建重试和失败恢复的实际可配置预算与默认值；明确执行器容量及关闭行为。将独立读事务落实到独立代理，评估主库小型专用只读连接池或保证有界并发及连接余量。不得只靠增大主池；读完成立即释放连接，构建在事务外。请求超时退出等待但不取消其他请求共用的构建；失败清理 running 标记，允许后续恢复。
- 验收：小连接池压力场景下，外层已有写入的并发审核在预算内进入微信且健康事务可提交；任务拒绝、查询超时、构建异常、重试耗尽后均可恢复。明确测量包含连接等待的端到端耗时。

### P1-04：启停操作与六接口的全量 PUT 契约不一致

- 证据：页面要求独立启停；7.1 只有携带 word/categoryCode/status/remark 的全量 PUT，无状态专用接口。
- 风险：若状态按钮从旧列表拼完整 PUT，会把另一个管理员刚修改的词、分类或备注覆盖。用户确认“最后保存生效”允许两个完整编辑覆盖，但状态按钮语义不应暗含重新保存其他字段。
- 更正选项 A（建议）：增加状态专用 PATCH 或 PUT 子路径，更新 status 与审计、revision，其余字段从锁内当前记录保留，更新接口数与测试。选项 B：保留六接口，只在完整编辑表单内启停，移除独立行开关并明确整个记录最后保存生效。仅先 GET 再全量 PUT 不能消除竞态。
- 验收：A 修改原词成功后，B 在旧列表点击停用，只改变状态；若采用 B，则页面与文档均不得暗示仅切换状态。

### P1-05：现有测试编号覆盖了主题，但不足以证明数据库及线上交付成立

- 证据：测试用例把全局并发查重、提交后、rollback-only、外层旧读视图等均归于 L3 JUnit，未约定真实事务引擎、独立连接或 Spring 代理；L1 只有 CRUD；L4 未给后台真实初始化词库的证据要求。
- 风险：Mock DAO 返回预设 revision、手动调用回调或直接 new Service，可以全绿却完全没有验证 MySQL 锁、RR 旧视图、Spring REQUIRES_NEW 和真实提交时序；Playwright 路由 mock 不能证明真实入库。
- 更正：保留纯算法/映射单测，另列 MySQL+Spring 事务集成验收（专用测试库，用户已有环境授权后执行）。缺环境时标 SKIPPED/BLOCKED，不宣称全部回归完成。新增真实后台验收矩阵：实际 API 非 mock、合法后台角色、一级菜单、18 分类、51,344 初始原词、真实启停/CRUD、搜索可见附件样本、刷新重登仍可见；记录环境与应用版本及迁移结果，令初始化完成与后续维护数量分开。
- 验收：DATA-04、L3-01/05/15/17/18/19/20 每项对应测试方法和证据；所有编号均有 PASS/FAIL/SKIPPED 及原因，不能以单一“服务测试通过”替代。真实微信路径应通过可注入的 HTTP/Token 传输边界验证本地命中零调用，而不是 mock 整个审核入口。

### P2-01：原词精确比较、规范化碰撞与参数边界需具体化

- 证据：4.2 用“去首尾空白、256 字符”；生成草稿使用 Python strip，Java 的 trim/strip 并非相同 Unicode 空白集合。7.3.1 将不同原词规范化后聚合，但证据写“该词标识及其启用分类”未明确碰撞时选择规则。
- 更正：统一初始化和 API 的首尾空白算法、字符长度单位、具体 MySQL 二进制排序规则及查询方式；给定分页默认值/上限、关键词通配符转义语义、排序稳定次键、非法筛选参数处理。碰撞时选确定性启用记录（例如最低 ID）作为证据，停用其中一条不得丢掉其他启用记录。
- 验收：普通空格/NBSP/全角空格、补充平面字符、a/A/全角Ａ分别入库与规范化匹配；碰撞记录逐一停用后结果正确；%/_ 搜索及空页边界。

### P2-02：实施状态与旧草稿需要明确分隔

- 方案目前标“实施暂停/最终版”，应随主线程确认的当前授权更新状态。旧 SQL/测试/前端少量 untracked 草稿不算实现：主线程已确认其中仍有 version/source/active_marker、旧 moderation 子菜单、localUnavailableStopsWechat 等旧预期。不得拿这些草稿的存在或运行结果证明本方案交付。
- 当前对 backend/src/main/java 的 SensitiveWord 搜索无实现匹配；现有微信 checkText 仍直接发请求。本复核仅对方案可行性负责。

## 实施取舍
