# 2026-08-08 发布动态图片预览顺畅交互技术方案

## 1. 范围

- 小程序页面：`/pages/qianxun/compose`。
- 设计基线：千寻 66 稿 `013.png`、`020.png`、`191.png` 与 2026-08-05 发布动态运行态单图截图。
- 本次只调整图片选择、上传状态、缩略图预览和关闭链路；不改社区接口、草稿结构、发布 payload、审核流程和后台配置。

## 2. 根因

1. 图片上传失败时，`compose.tsx` 将运行时文案 `community.copy.upload_retry` 作为可点击 `Text`，点击后直接复用临时文件重新上传，因此页面会出现“重新上传”入口。
2. 成功缩略图没有点击事件，发布页不存在大图预览；若直接改用 `Taro.previewImage`，微信原生预览不提供可靠的最大缩放配置。
3. 图片工具栏和九宫格加图方块都能触发 `Taro.chooseImage`，原实现缺少同步互斥，连续点击可能重复拉起系统选择器。
4. 同批图片原来逐张串行上传，多图场景等待时间偏长。

## 3. 设计基线与组件映射

| 交互 | 设计/产品口径 | 实现 |
|---|---|---|
| 成功图片 | 3 列圆角缩略图、右上真实删除按钮 | 保留 `UploadImage[]` 九宫格；缩略图点击预览，删除按钮阻止冒泡 |
| 上传中 | 图片底部半透明状态层 | 展示运行时“上传中”文案，状态层不可点击 |
| 上传失败 | 不出现重新上传按钮 | 只展示不可点击“上传失败”和右上删除按钮 |
| 大图预览 | 完整展示、可拖拽和双指缩放、避免无限放大 | 全屏 `MovableArea` + `MovableView`，`scaleMin=1`、`scaleMax=3`、`outOfBounds=false` |
| 关闭预览 | 真实可见关闭按钮 | 左上 72rpx 可见圆形按钮；关闭即卸载组件 |
| 连续选图 | 系统选择器只能出现一个 | `choosingImagesRef` 在调用系统能力前同步拦截 |
| 多图上传 | 兼顾速度与资源占用 | 单批最多 3 路并发上传 |

预览图片使用 `aspectFit`，不拉伸、不裁切；缩略图继续使用 `aspectFill`。所有点击区都由真实可见组件承载，没有透明热区或截图伪交互。

## 4. 状态与事件

```text
点击加图
  -> 选择器互斥检查
  -> 系统选图
  -> 图片立即进入 queued
  -> 最多 3 路并发上传
     -> success：缩略图可点击预览
     -> failed：只显示失败，可删除后重新选择

点击成功缩略图
  -> 打开全屏预览（1 倍）
  -> 拖拽/双指缩放（最大 3 倍）
  -> 点击关闭
  -> 卸载预览；下次重新从 1 倍打开
```

## 5. 回归门禁

- `miniapp/scripts/validate-qianxun-topic-demo-closure.mjs`
  - 禁止发布页引用 `COMMUNITY_COPY_KEYS.uploadRetry`。
  - 强制选择器同步互斥。
  - 强制独立预览层、原生手势容器和 1～3 倍缩放边界。
- `miniapp/scripts/verify-compose-image-preview-runtime.cjs`
  - 本地隔离接口提供单图草稿，不写真实账号数据。
  - 验证预览打开、全视口尺寸、原生缩放属性、关闭卸载与再次打开复位。
- `npm run build:weapp`
  - 运行全量前置门禁并生成正常微信小程序产物。

## 6. 风险控制

- 删除按钮调用 `stopPropagation()`，避免删除同时打开预览。
- 预览层 `zIndex=200` 覆盖正文、话题浮层和底部工具栏，关闭按钮独立置顶。
- 失败图片仍占一个槽位并禁止发布，用户需要删除后重新选择；该规则避免把失败项误提交到发布 payload。
- `upload_retry` 后台配置暂不删除，仅发布页不再消费，避免扩大到其他历史配置或数据迁移。
- 微信开发者工具 2.01.2510260 的 `App.captureScreenshot` 在当前自动化会话持续超时；运行态改用 DOM、尺寸、属性和点击闭环验收，截图能力恢复后可通过 `WX_CAPTURE_SCREENSHOTS=true` 补采。
