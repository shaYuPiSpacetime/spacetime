# 私信双源一致性与顺滑体验技术方案

> 日期：2026-10-12
> 范围：小程序私信会话、TIM 历史、平台归档消息与消息发送态
> 状态：实施中

## 1. 现象与证据

本次核对了用户 `15821262446`（App 用户 1052）与 `18702694264`（App 用户 120）的真实会话：

- 两个账号的 TIM UserID、UserSig 登录和 C2C 映射均正常。
- 双向实时发送均成功，双方漫游历史均返回同一批消息，消息后回调也正常写入 `app_message_record`。
- 但发送方页面存在仅本机显示的旧“发送中”消息；平台库与 TIM 均不存在这些消息。
- TIM 历史与平台归档数量曾出现 11 对 8 的差异，说明旧回调窗口或历史悄悄话生命周期造成了双源差异。
- 平台归档按数据库自增 ID 返回，前端又把平台历史和 TIM 历史异步拼接；同秒消息缺少统一顺序字段时，列表顺序依赖请求完成顺序。
- 首屏只等待 180ms 的 TIM 预算，冷启动会先提交不完整列表，再补消息并再次滚动，造成闪烁、跳位和“滑动才出现”。

结论：不是腾讯 TIM 账号故障，主要是客户端发送状态没有最终态回写、缓存没有与远端快照校准、双源排序不确定，以及首屏分阶段提交。

## 2. 落地目标

1. 发送成功/失败必须回写同一个本地气泡；超时不能留下永久 `sending`，也不能因立即重发造成重复消息。
2. 进入会话时以 TIM + 平台返回的远端消息校准缓存；过期且远端不存在的本地发送项转为 `failed`，保留重试入口。
3. 消息排序完全由 `sentAt + TIM sequence/random + timMsgKey/clientMsgId` 决定，不依赖网络返回顺序。
4. 冷启动只做一次首屏提交；已有缓存恢复时保持当前位置，后台补齐不强制滚动。
5. 保留现有 TIM 实时通道、平台归档和已读接口，不引入第二套发送服务或破坏现有聊天交互。

## 3. 方案与边界

### 3.1 发送状态闭环

`LiteChatMessageImGateway.sendText` 在发送 Promise 结束时再次发送标准化 `conversation_updated` 事件，成功事件携带 `sent`，失败事件携带 `failed`，并复用原 `clientMsgId`。页面超时只提示“结果确认中”，不恢复输入框、不创建第二条消息；后续事件负责替换乐观气泡。若远端历史确认窗口结束仍没有 TIM 回执，则由缓存校准将其标记失败。

### 3.2 双源合并与排序

新增纯领域函数：

- 解析 TIM MsgKey 中的 sequence/random 作为平台消息的排序兜底；
- 对已存在的消息执行字段补齐和状态升级；
- 首次远端快照完成后，对超过发送确认宽限期的本地 `sending` 项标记 `failed`；新发送项保留，避免误判进行中的请求。

不删除远端消息，不改变消息编号，不改变服务端游标协议。

### 3.3 首屏加载与返回位置

冷启动等待详情、平台首屏和第一批 TIM 历史后一次性提交；已有会话缓存立即恢复，远端刷新只合并差异且不改变用户当前位置。只有明确发送、收到新消息且用户在底部时才滚动到最新。

## 4. 验收标准

- A→B、B→A 双向消息都能在两端历史中出现，发送方乐观气泡最终只保留一条 `sent`。
- SDK 超时后消息最终成功时，页面不出现重复气泡；最终失败时可重试且不会永久 `sending`。
- 平台消息与 TIM 消息同秒、乱序返回时，两个账号展示顺序一致。
- 从私信列表进入定位到最新；从对方主页返回保持原滚动位置；冷启动不先顶端再跳底部。
- 现有消息域、私信会话和性能测试全部通过。
