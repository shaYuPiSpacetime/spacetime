# APP 用户管理列表查询性能优化技术方案

> 日期：2026-07-14  
> 状态：已实现并完成本地验证  
> 复杂度：中等。涉及列表查询放大、统计口径、筛选请求时机和潜在索引取舍，但不新增业务状态机，不新增业务表。  
> 实施说明：2026-07-14 确认取消“列表不超过 5 条 SQL”的硬门槛；改为消除随分页记录数线性增长的重复查询，允许后续卡片扩展增加必要的批量查询。

## 1. 背景与目标

管理后台“用户准入 -> App 用户管理”当前列表查询体感较慢。代码和现有 MyBatis 日志表明，主要问题不是当前数据量，而是列表行组装时重复访问数据库，导致查询次数随每页用户数线性增长。

本方案目标：

1. 将 App 用户列表数据库访问从 `O(N)` 收敛为与每页条数无关的常数级查询。
2. 头部统计不再复用完整列表接口，避免为统计总数加载用户详情、审核记录、字典和资料完整度。
3. 搜索条件只在点击“搜索”或“重置”后生效，避免输入一个字符发起一次请求。
4. App 用户主列表固定请求每页 9 条，桌面端三列卡片形成 3 x 3 完整宫格。
5. 保持最新审核状态、业务生效状态、核心准入和资料完整度口径不变，不通过回写快照字段换性能。

### 1.1 本轮不做

- 不新增或恢复 `app_user` 审核状态、核心准入、资料完整度等快照字段。
- 不引入 Elasticsearch、Redis 搜索索引或新的前端数据请求框架。
- 不在本性能优化中补造 PRD-02 关系反馈、7 日访客等尚无事实表/服务的数据。
- 不把头像、实名、学历等审核列表的每页 10 条改为 9 条。
- 不在技术方案确认前修改任何业务代码。

## 3. 当前链路与根因

### 3.1 当前调用链

```text
CustomersPage 首屏
├── GET /admin/users/app/list?page=1&size=10
├── GET /admin/users/app/list?page=1&size=1
└── GET /admin/users/app/list?page=1&size=1&coreAccessStatus=CORE_ALLOWED

单次 list
Controller
  -> AppUserAdminServiceImpl.getUserPage
     -> app_user COUNT + 分页 SELECT
     -> 审核记录批量 SELECT
     -> 头像批量 SELECT
     -> 相册批量 SELECT
     -> 4 次字典 SELECT
     -> 对每个用户计算资料完整度
        -> 1 次 app_config SELECT
        -> 当前配置下 6 次审核事实 SELECT
```

### 3.2 SQL 放大公式

从现有日志可还原一次默认列表请求：

| 分类 | SQL 数量 |
|------|----------|
| `app_user` 总数 + 当前页 | 2 |
| 列表基础审核、头像、相册批量查询 | 3 |
| 四类资料字典 | 4 |
| 每个用户重新读取运行配置 | `1 x N` |
| 当前完整度配置下每个用户审核事实查询 | `6 x N` |
| 合计 | `9 + 7 x N` |

因此：

- 当前每页 10 条：`9 + 7 x 10 = 79` 条 SQL，与日志一致。
- 只改成每页 9 条但不做根因优化：仍有约 `9 + 7 x 9 = 72` 条 SQL。
- 结论：每页 9 条是视觉需求，只能降低约 9% 查询量，不能作为性能方案。

### 3.3 已确认问题分级

| 级别 | 问题 | 影响 |
|------|------|------|
| P0 | 资料完整度在列表逐用户读取配置和审核事实 | 查询数随用户数线性增长，是主瓶颈 |
| P0 | 头部统计复用完整列表接口两次 | 统计总数也执行完整列表行组装，首屏额外放大 |
| P1 | 关键词和筛选输入直接触发请求 | 输入连续字符会产生并发请求，旧响应可能覆盖新响应 |
| P1 | 审核记录、头像、相册重复查询同一事实表 | 增加 SQL、结果行和序列化开销 |
| P1 | 四类字典每次列表固定执行四次查询 | 稳定的额外开销，可收敛为一次 |
| P1 | `CORE_ALLOWED/CORE_PENDING` 与后端当前识别值不一致 | 核心准入统计/筛选可能退化为全量结果；截图中“当前用户”和“核心准入开放”相同与此一致 |
| P2 | 主列表每页 10 条不适配三列卡片 | 桌面端最后一行只剩一张卡片，视觉上像数据缺失 |

### 3.4 同链路发现的功能风险

以下问题不是本次“慢”的根因，但重构查询时必须留出边界，不能继续静默忽略：

1. `identity` 已从前端传入，但当前 `getUserPage` 未应用该条件。
2. `relationshipAccess`、`vipStatus`、`hideVisitRecord` 已传入 DTO，但当前服务未落到 SQL。
3. 前端会员和关系反馈选项发送展示中文，DTO 注释定义的是状态码，接口契约不一致。
4. 导出当前复用列表 `PAGE_SIZE`；主列表改成 9 后，导出不能被误解为只导出当前 9 条，导出应只复用“已应用筛选条件”。

上述跨模块筛选建议单独作为功能补齐项，不与首轮性能优化捆绑；但性能测试必须明确哪些条件真实生效。

## 4. 方案选型

### 4.1 方案 A：分页后批量组装，计算阶段纯内存（推荐）

做法：继续先查 `app_user` 分页，再按当前页 9 个用户 ID 一次加载审核事实；一次加载配置和字典；在内存中派生状态、头像和资料完整度。统计改为独立计数接口。

优点：

- 保持现有接口和“审核事实实时派生”架构。
- 不新增快照表，不引入缓存一致性问题。
- 改动范围可控；按当前四类字典分别查询的实现，预计列表 SQL 从 79 条降到约 8 条，且不再随每页用户数增长。
- 容易通过 DAO 调用次数测试证明不存在 N+1。

缺点：

- 当前批量审核查询仍会读取这 9 个用户的相关历史记录；单用户审核历史极多时，结果行数仍可能增长。
- 需要为资料完整度增加“预加载上下文”入口，避免单用户计算方法继续访问 DAO。

### 4.2 方案 B：用户、最新审核和生效状态合并成一条复杂聚合 SQL

做法：通过窗口函数/派生表一次返回用户卡片全部字段，再配一条 COUNT。

优点：数据库往返最少，理论查询数可降到 2 条。

缺点：最新记录、最近有效记录、头像不回退等口径集中在大 SQL 中，COUNT 和数据查询容易出现条件漂移；后续 PRD-02/03/04 字段叠加会让 SQL 难以维护。对当前 63 个用户属于过度设计。

### 4.3 方案 C：维护用户卡片读模型/快照

做法：认证、资料和资产变化时更新专用汇总表或 Redis 读模型，列表直接读取。

优点：大规模数据下查询最快。

缺点：引入事件、重算、补偿和一致性问题；与现有技术方案“不保存审核和核心准入快照”的已确认决策冲突，现阶段不采用。

### 4.4 决策

采用方案 A。首轮以“消除 N+1、删除重复列表统计调用、显式搜索触发”为主；完成后再通过 `EXPLAIN ANALYZE` 和压测决定是否需要索引或升级为审核事实聚合 SQL。

## 5. 总体架构

```text
GET /admin/users/app/list?page=1&size=9
  -> Controller
  -> AppUserAdminService
  -> AppUserAdminServiceImpl
     1. AppUserDao：COUNT + 当前页 9 个用户
     2. AppUserAuditRecordDao：一次加载当前页所需审核事实
     3. AppConfigDao：一次加载资料完整度配置快照
     4. ProfileDictionaryService：按所需字典类型固定次数加载，不按用户重复查询
     5. Service 内存组装 AppUserListVO，不再访问 DAO

GET /admin/users/app/stats
  -> Controller
  -> AppUserAdminService
  -> AppUserDao：只做总数和核心准入计数，不加载列表记录
```

## 6. 后端设计

### 6.1 接口清单

| Method | Path | 权限 | 入参 | 出参 | 说明 |
|--------|------|------|------|------|------|
| GET | `/admin/users/app/list` | `user:app:list` | 保持 `AppUserPageReq`，前端固定传 `size=9` | `R<Page<AppUserListVO>>` | 路径和响应结构不变 |
| GET | `/admin/users/app/stats` | `user:app:list` | 无；统计不跟随列表筛选 | `R<AppUserStatsVO>` | 一次返回当前用户数、核心准入开放数 |

`AppUserStatsVO` 首轮字段：

| 字段 | 类型 | 口径 |
|------|------|------|
| `currentUserCount` | long | `app_user.deleted = 0` |
| `coreAccessAllowedCount` | long | 首登完成、账号正常、实名业务生效、最新头像通过、学历业务生效 |

关系反馈开放和 7 日访客 UV 等 PRD-02 指标在对应事实表和服务实现后扩展，不在本轮返回模拟值。

### 6.2 分层职责

| 层 | 文件/类型 | 设计职责 |
|----|-----------|----------|
| Controller | `AppUserController` | 保持精确 `R<T>`；新增只读 stats 路由和既有权限 |
| Service | `AppUserAdminService` | 增加 `getUserStats()` 契约 |
| ServiceImpl | `AppUserAdminServiceImpl` | 编排分页、批量审核事实、配置、字典和纯内存组装 |
| common service | `Prd01ProfileCompletenessCalculator` | 保留单用户入口；增加使用预加载规则和审核事实的无 DAO 批量计算入口 |
| DAO | `AppUserDao`、`AppUserAuditRecordDao` | 提供计数和当前页审核事实查询接口；字典沿用现有固定次数查询 |
| DAOImpl | 对应 `DAOImpl` | 唯一调用 Mapper，遵守六层架构 |
| Mapper | `AppUserMapper`、`AppUserAuditRecordMapper`、`SysDictDataMapper` | 参数化 SQL；禁止 Service 拼接 SQL 字符串 |

### 6.3 审核事实批量组装

首轮复用“一次查当前页用户相关审核记录，再单次遍历归并”的低风险方式。每个用户归并出以下内部事实：

- 各审核类型最新提交记录，用于卡片完整状态展示。
- 实名、学历是否存在当前业务生效的通过记录。
- 最新头像是否通过及对应公开头像 URL。
- 相册、背景图、关于我、问答、语音是否存在资料完整度需要的有效内容。

首轮保持 `AppUserListVO` 现有字段契约：相册和语音字段直接从同一批审核记录中归并，禁止再发独立查询。当前页面未消费的字段是否从列表契约移除，需先完成全仓消费者核对后另行处理；画像详情继续走详情接口，不受本轮优化影响。

如果压测发现单页审核历史返回行数超过 500 或审核批量查询占列表耗时 40% 以上，再将该 DAO 查询升级为“最新记录 + 生效标记”的聚合查询；该升级不改变 Service 契约。

### 6.4 资料完整度计算

当前 `calculate(AppUser)` 同时负责读取配置、查询审核事实和计算分值，不适合列表场景。目标拆分为：

1. 每个列表请求只获取一次运行配置快照和计分规则。
2. 审核事实由列表批量查询结果提供。
3. 每个用户的分值计算是纯函数，不访问 `AppConfigDao` 或 `AppUserAuditRecordDao`。
4. 单用户详情/移动端原入口保持兼容，后续可复用同一预加载上下文逐步优化。

### 6.5 字典加载

增加按多个 `dictType` 一次查询的 DAO 能力，单次加载身份、学历、职业、年收入四类字典并在内存分组。首轮不引入本地缓存，避免字典修改后的失效策略扩张；若后续监控仍显示字典查询占比高，再沿用项目 Redis 能力做带明确失效的缓存。

### 6.6 核心准入口径统一

核心准入列表标签、筛选和统计必须调用同一业务判定，统一包含：

```text
first_login_completed = 1
AND account_status = NORMAL
AND 实名存在业务生效 APPROVED 记录
AND 最新头像记录状态 = APPROVED
AND 学历存在业务生效 APPROVED 记录
```

请求值先归一为内部枚举，再生成查询条件；实现期兼容当前历史别名，前端最终只发送一个规范值，避免 `CORE_ALLOWED` 被后端静默忽略。

### 6.7 SQL 查询控制原则

| 场景 | 当前 | 目标 |
|------|------|------|
| 列表无筛选，10 条 | 79 | 不适用，分页改为 9 |
| 列表无筛选，9 条 | 预计 72 | 当前字段预计约 8 条；不设固定上限，但禁止按用户逐条补查 |
| 头部统计 | 2 次完整 list | 1 个 stats HTTP 请求；只执行统计查询，不组装列表明细 |
| 首屏合计 | 3 个 list HTTP 请求 | 1 个 list + 1 个 stats HTTP 请求 |

## 7. 前端设计

### 7.1 查询状态

将页面筛选状态分成两组：

- `draftFilters`：输入框和下拉框当前值，仅用于表单显示。
- `appliedFilters`：最近一次点击“搜索”后提交的条件，作为列表请求依赖。

触发规则：

1. 首屏加载一次默认列表。
2. 输入关键词或选择筛选项时不自动请求。
3. 点击“搜索”时提交 `draftFilters`、回到第 1 页并请求一次。
4. 点击“重置”时清空两组条件、回到第 1 页并请求一次。
5. 翻页仅改变页码并请求一次。
6. 新请求发出时取消上一次列表请求，或使用递增请求序号丢弃过期响应，防止旧响应覆盖新结果。

请求生命周期建议抽到 `frontend/src/hooks/useAppUsers.ts`，页面组件只负责表单、卡片和弹窗拼装，符合 `TEAM_STANDARDS.md`。

### 7.2 每页 9 条

- 将 App 用户主列表常量改为语义化的 `APP_USER_PAGE_SIZE = 9`。
- 请求参数、分页组件和“9条/页”文案统一引用该常量。
- 卡片与表格视图共用同一份分页结果，均为 9 条；切换视图不改变页码和记录边界。
- 桌面端三列形成 3 x 3；中小屏仍按现有响应式列数自然换行，不根据屏宽动态改变服务端 page size。
- 头像、实名、学历、资料图片、开放文字等审核页继续每页 10 条。

### 7.3 统计请求

前端移除两次 `getAppUserList({size: 1})`，改为一次 `getAppUserStats()`。统计失败只影响统计卡片，不清空已加载的用户列表。

### 7.4 导出边界

导出使用 `appliedFilters`，不复用 `page` 和 `APP_USER_PAGE_SIZE`。即使主列表每页 9 条，导出仍表示“按当前已应用筛选导出全部符合条件的数据”。

## 8. 数据库与索引策略

### 8.1 首轮结论

首轮不直接新增索引。理由：当前日志中的用户总数为 63，而单次列表已经产生 79 条 SQL，先消除 N+1 的收益远大于索引调整；此时盲目加索引无法解决主要问题，还会增加写入成本。

### 8.2 实现后必须执行的 EXPLAIN

在相同测试数据上对以下 SQL 执行 `EXPLAIN ANALYZE`：

1. 默认 `app_user` 按 `create_time DESC, id DESC` 分页。
2. 关键词为空和非空的 COUNT/分页查询。
3. 当前页用户 ID 的审核事实批量查询。
4. 核心准入统计查询。

### 8.3 条件候选索引

仅当 EXPLAIN 出现全表扫描、filesort 或扫描行数明显大于返回行数，且压测未达到验收指标时，再单独确认以下索引迁移：

| 表 | 候选索引 | 服务查询 | 备注 |
|----|----------|----------|------|
| `app_user` | `(deleted, create_time, id)` | 默认分页和稳定排序 | 同时将排序补充为 `create_time DESC, id DESC` |
| `app_user_audit_record` | `(user_id, audit_type, deleted, submit_time, id)` | 当前页审核事实、最新记录 | 需与现有 `idx_audit_user_type_time` 对比后决定替换还是保留 |

关键词当前使用前缀通配的多字段 `LIKE`，普通 B-Tree 索引不能有效解决。若用户量达到 5 万以上且关键词查询仍未达标，再单独设计“用户 ID/手机号/身份证精确哈希命中 + 昵称/学校/标签全文检索”，不在首轮性能优化中引入。

## 10. 测试与验收标准

### 10.2 性能验收

| 指标 | 门槛 |
|------|------|
| 列表 SQL 放大 | 从 1 条到 9 条时，审核事实、运行配置和字典查询次数不随用户记录数增长；新增卡片数据必须使用批量查询 |
| 统计查询边界 | 不查询列表记录，不加载字典、头像、相册和资料完整度；新增统计指标允许增加必要的聚合查询 |
| 首屏 HTTP 数 | App 用户业务数据只允许 1 次 list + 1 次 stats |
| 同数据集相对耗时 | 列表 P95 相比优化前下降至少 70% |
| 测试环境绝对耗时 | 1 万用户、10 万审核记录下，无筛选列表 P95 不高于 500ms；关键词模糊查询单独记录 |
| 批量审核结果行 | 单页超过 500 行时触发聚合查询升级评估，不静默放任增长 |

### 10.3 测试建议

1. L3：Mock DAO，分别返回 1 条和 9 条用户，验证配置、字典、审核 DAO 调用次数保持常数。
2. L3：覆盖最新状态、旧有效记录、最新头像驳回、无审核记录和完整度分值一致性。
3. L2：验证 `/list` 和 `/stats` 的精确返回类型、权限和分页参数。
4. L1：使用可控测试库记录 SQL 数量，执行默认、关键词、核心准入、认证状态和末页场景。
5. 前端：验证输入不自动请求、搜索/重置/翻页请求次数、过期响应丢弃和 9 条分页。
6. Playwright：桌面宽屏检查 3 x 3 卡片、分页文案和末页空位；移动端检查无横向溢出。

## 11. 风险与降级

| 风险 | 处理 |
|------|------|
| 批量审核查询历史记录过多 | 监控结果行；超过门槛后在 DAO 内升级为最新/生效聚合查询 |
| 纯内存完整度与原单用户入口口径漂移 | 共用同一字段评分函数，以预加载上下文替换数据访问，不复制评分规则 |
| stats 核心准入口径与列表不一致 | 提取同一内部判定/SQL 片段并用一致性测试锁定 |
| 旧客户端仍发送历史状态值 | 服务端先归一兼容别名，日志告警；前端改为规范值后再逐步移除别名 |
| 9 条分页与冻结文档冲突 | 实现前先同步 PRD、端内定义、Demo 和原技术方案 |
| 当前工作区已有未提交改动 | 实现时基于现状增量修改，不覆盖 `AppUserAdminServiceImpl`、完整度计算器及相关测试中的现有变更 |

## 14. 本地实施结果

2026-07-14 在本地开发库和已登录管理后台接口上完成验证。以下数字用于说明本轮优化效果，不作为后续卡片字段扩展的固定 SQL 上限。

| 场景 | 结果 |
|------|------|
| 优化前无筛选 `size=10` | 已有日志实测 79 条 SQL |
| 仅把分页改为 `size=9` 的理论值 | 约 72 条 SQL |
| 优化后无筛选 `size=9` | 实测 8 条 SQL，返回 9 条、总数 68；5 次请求平均约 191.2ms |
| 优化后无筛选 `size=1` | 实测仍为 8 条 SQL；5 次请求平均约 132.6ms |
| `GET /admin/users/app/stats` | 实测 2 条计数 SQL，单次约 56ms；不加载列表、字典和完整度 |
| 首屏请求 | 从 3 次 list 改为 list + stats |

结论：按 `size=9` 同口径估算，SQL 数量从约 72 条降到 8 条，减少约 88.9%；`size=1` 和 `size=9` 的查询条数相同，说明逐用户查询放大已消除。后续新增卡片数据可以增加必要的批量查询，但不得恢复逐用户补查。

验证记录：

1. 后端完整测试：247 通过、0 失败、1 个既有条件测试跳过。
2. 前端生产构建：通过。
3. 聚焦 Playwright：独立 stats、9 条分页、输入不自动请求、点击搜索提交条件，1 个用例通过。
