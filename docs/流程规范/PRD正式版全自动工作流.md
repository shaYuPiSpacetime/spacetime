# PRD 正式版全自动工作流

> 适用场景：后续 PRD-03、PRD-04 等模块需要按“Codex 编写正式 PRD + Claude Code CLI 核查 + Codex 整改 + 二轮复核”的方式推进时，统一按本文执行。

---

## 1. 工作流目标

把 PRD-02 已验证有效的临时协作方式固化为固定流水线：

1. Codex 按 `.claude/skills/prd-design/SKILL.md` 编写正式版 PRD。
2. Codex 调用本机 Claude Code CLI 做第一轮只读核查。
3. Codex 根据核查报告整改 PRD，并写入整改记录。
4. Codex 再调用 Claude Code CLI 做第二轮深度复核。
5. 二轮通过后，输出核查汇总，作为进入 UI、技术方案或测试用例阶段的门禁依据。
6. Codex 根据通过后的 PRD 实现静态 Demo，并输出 Demo 自测与交付报告。**实现完 Demo 才是本流程最后一步。**

这套流程的重点不是“多问一个模型”，而是让核查、整改、复核、归档都有固定文件落点，后续模块可以重复执行。

---

## 2. 角色边界

| 角色 | 执行者 | 职责 | 禁止事项 |
|------|--------|------|----------|
| PRD 编写者 | Codex | 读取 PRD 标准、原始需求、确认清单，编写正式版 PRD、页面规格、前置准备清单 | 不把未确认口径伪装成定论 |
| PRD 整改者 | Codex | 根据 Claude 核查报告修改 PRD，并维护 `核查整改记录` | 不删除用户确认的不整改原则 |
| 独立核查者 | Claude Code CLI | 只读核查正式版 PRD 与原始 PRD 的遗漏、冲突、模糊、不一致和下一阶段可用性 | 不直接编辑文件 |
| 决策者 | 用户 | 对 P0 冲突、跨模块边界、不整改项做最终拍板 | 不需要参与机械核查和文件整理 |

---

## 3. 触发口径

用户出现以下表达时，进入本流程：

- “按 PRD 全自动流程处理 PRD-03”
- “用 Claude Code CLI 核查这个 PRD”
- “正式 PRD 写完后自动让 ClaudeCode 查一遍”
- “继续 PRD 固定流程”
- “全自动化版本开始”

如果用户只要求普通 PRD 编写，仍先按 `prd-design` 执行；当用户要求“ClaudeCode 核查”“全自动核查”“固定流程”时，再执行本文的 Claude CLI 核查闭环。

## 4. 前置条件

| 条件 | 要求 | 检查方式 |
|------|------|----------|
| Claude CLI | 本机可执行 `claude` | `claude --version` |
| 非交互能力 | 支持 `claude -p` | `claude --help` 中存在 `-p, --print` |
| PRD 标准 | `docs/需求文档/标准/` 完整 | 必须至少存在 README、00、05、20、30 |
| 原始资料 | 原始移动端/后台 PRD 或确认问题清单存在 | 作为 `--source` 参数传入 |
| 正式版目录 | 模块正式版目录已创建 | 作为 `--prd-dir` 参数传入 |

Claude CLI 核查默认使用只读工具权限：

```bash
claude -p --permission-mode dontAsk --allowedTools Read,Grep,Glob,LS --output-format text
```

### 4.1 PRD-03 实测成功路径（优先避坑）

PRD-03 实测发现：标准脚本在目录级核查任务过宽时，可能长时间无输出且报告文件保持 0 字节；此时不是 PRD 失败，也不一定是 Claude CLI 不可用。后续模块遇到同类情况，按以下降级路径执行。

| 场景 | 判断方式 | 处理方式 |
|------|----------|----------|
| Claude CLI 可用性 | `claude --version` 有版本号；`claude -p "请只输出 ok" --output-format text` 返回 `ok` | 继续执行核查 |
| Read 工具可用性 | 用一条短任务读取单个公开项目文件并输出摘要 | 确认 `--allowedTools Read` 可用 |
| 标准脚本长时间无输出 | 运行超过 2 分钟且报告文件仍为 0 字节 | 中断脚本，改用“收窄任务文件 + 直接 Claude CLI” |
| Claude 输出 `Permission deny rule "Rm"/"Sudo" matches no known tool` | 仅为本机配置中无效工具名提示 | 不视为失败；只要最终报告非空且进程退出 0，即可采用 |
| 第二轮任务再次卡住 | 报告仍为 0 字节，且任务包含大量原始资料和全量页面 | 将任务收紧为“上轮闭环表 + 关键整改点 + 全量文件存在性/门禁评估”，并限制输出字数 |

直接 Claude CLI 调用模板：

```bash
claude -p --permission-mode dontAsk --allowedTools Read --output-format text \
  < "docs/需求文档/需求文档-正式版/XX-模块名称/PRD-XX_Claude核查任务_第N轮.md" \
  > "docs/需求文档/需求文档-正式版/XX-模块名称/PRD-XX_核查报告_第N轮.md"
```

收窄任务文件必须满足：

1. 明确列出待读文件路径，不要求 Claude 递归扫描目录。
2. 第 1 轮允许抽查关键页面，但必须在报告中标出未覆盖范围。
3. 第 2 轮必须读取第 1 轮报告、整改记录、全部页面规格和必要全局定义。
4. 输出格式固定为 P0/P1/P2、闭环表和门禁结论。
5. 第二轮建议限制在 3500 字以内，避免泛化长报告。

## 6. 标准执行步骤

### Step 0：范围确认

Codex 必须先确认：

| 维度 | 必填 |
|------|------|
| 模块编号 | 如 `PRD-03` |
| 模块名称 | 如 `消息、私信与通知中心` |
| 原始资料 | 移动端 PRD、管理后台 PRD、确认问题清单、用户补充口径 |
| 目标端 | 移动端、管理后台或两者 |
| 是否需要 Demo 可编写性评估 | 通常第二轮需要 |

如果用户已经明确说“直接做”“不用确认”“开始固化流程”，可以跳过等待确认，但仍要在工作记录里写明采用的输入范围。

### Step 1：Codex 编写正式版 PRD

Codex 按 `.claude/skills/prd-design/SKILL.md` 执行：

1. 读取 `docs/需求文档/标准/README.md`。
2. 读取 `docs/需求文档/标准/00_PRD编写规范.md`。
3. 按模块需要读取 `20_模板_模块PRD.md`、`30_模板_页面规格.md`、`05_PRD评审清单.md`。
4. 输出模块公共定义、端内定义、模块 PRD、页面规格、甲方前置准备清单。
5. 自检不得遗留未闭环的 `[待确认]`；确实阻塞时必须写 `[阻塞] + 负责人 + 截止日期`。

### Step 2：第一轮 Claude CLI 核查

第一轮核查目标：

1. 对比正式版 PRD 与原始 PRD，找遗漏、冲突、模糊和结构偏差。
2. 按 P0/P1/P2 分级输出问题。
3. 标出每个问题的文件路径、问题描述、影响和建议处理方式。
4. 只读核查，不改文件。

命令示例：

```bash
scripts/prd_workflow/claude_prd_review.sh \
  --module-id PRD-03 \
  --module-name 消息、私信与通知中心 \
  --prd-dir "docs/需求文档/需求文档-正式版/03-消息、私信与通知中心" \
  --source "docs/需求文档/移动端/细化PRD-03_消息、私信与通知中心.md" \
  --source "docs/需求文档/管理后台/管理后台细化PRD-03_消息、私信与通知中心.md" \
  --source "docs/需求文档/PRD找茬确认问题清单.md" \
  --round 1
```

如果标准脚本长时间无输出或报告文件为 0 字节，立即改走 4.1 的直接调用方式。第 1 轮收窄任务文件建议读取：

1. PRD 编写规范与评审清单。
2. 原始移动端 PRD、原始后台 PRD、一期上线目标。
3. 正式版核心文件：模块公共定义、前置准备清单、端内定义、模块 PRD。
4. 关键页面规格抽查文件。

第 1 轮如果只抽查部分页面，必须要求 Claude 在报告中标出未覆盖页面，并在第 2 轮补全。

### Step 3：Codex 整改并写整改记录

Codex 读取 `PRD-XX_核查报告_第1轮.md` 后：

1. 逐条判断是否整改。
2. 用户明确不整改的项，写入处理原则。
3. 已整改项必须写清文档落点。
4. 跨 PRD 承接项必须写入甲方前置准备清单或跨 PRD 后续承接表。
5. 输出或更新 `PRD-XX_核查整改记录.md`。

整改记录至少包含：

| 章节 | 内容 |
|------|------|
| 处理原则 | 不整改项、跨模块边界、架构拆分原则 |
| 核查问题处理表 | 问题、处理结论、状态、文档落点 |
| 新增与修改文件清单 | 本轮改了哪些文件 |
| 跨 PRD 后续承接项 | 后续模块需要承接什么 |
| 自检结论 | 是否仍有待确认、旧称、冲突、Demo 阻塞 |

### Step 4：第二轮 Claude CLI 深度复核

第二轮核查目标：

1. 确认第一轮问题是否全部闭环。
2. 深挖整体需求遗漏、冲突、模糊、不一致。
3. 评估管理后台页面规格是否可直接进入静态 Demo。
4. 评估是否可进入技术方案或测试用例阶段。

命令示例：

```bash
scripts/prd_workflow/claude_prd_review.sh \
  --module-id PRD-03 \
  --module-name 消息、私信与通知中心 \
  --prd-dir "docs/需求文档/需求文档-正式版/03-消息、私信与通知中心" \
  --source "docs/需求文档/移动端/细化PRD-03_消息、私信与通知中心.md" \
  --source "docs/需求文档/管理后台/管理后台细化PRD-03_消息、私信与通知中心.md" \
  --previous-report "docs/需求文档/需求文档-正式版/03-消息、私信与通知中心/PRD-03_核查报告_第1轮.md" \
  --fix-log "docs/需求文档/需求文档-正式版/03-消息、私信与通知中心/PRD-03_核查整改记录.md" \
  --demo-reference "docs/静态Demo/04-商业化（VIP、千寻币、解锁与资产中心）" \
  --round 2
```

如果第二轮目录级任务仍卡住，优先使用收窄版第 2 轮任务。PRD-03 验证有效的第 2 轮任务结构如下：

1. 必读：一期上线目标、第 1 轮报告、整改记录、模块公共定义、前置准备清单、UI 缺少页面清单。
2. 全局定义：共享层、移动端端专属层、管理后台端专属层。
3. 页面规格：移动端全量页面、管理后台全量页面。
4. 复核重点：上轮问题闭环、关键整改点、一期目标口径、页面规格完整性、Demo/技术方案/测试门禁。
5. 输出限制：3500 字以内；P0/P1/P2 无问题时写“无”。

### Step 5：二轮后收口

二轮后按以下门禁判断：

| 门禁 | 通过标准 | 不通过处理 |
|------|----------|------------|
| P0 问题 | 0 个未闭环 P0 | Codex 继续整改，重新跑第二轮 |
| P1 问题 | 已整改或登记为有条件通过 | 写入整改记录和后续承接项 |
| 待确认项 | 无普通 `[待确认]` 残留 | 回到用户 Decision Gate |
| 页面规格 | 字段表、操作表、状态、验收、画板清单完整 | 补页面规格后再复核 |
| Demo 可编写性 | 后台页面可直接写 Demo，或明确缺口 | 缺口写入设计稿缺少页面清单 |
| 下一阶段 | 可进入 UI、静态 Demo、技术方案或测试 | 写入两轮汇总报告 |

### Step 6：实现静态 Demo（最后一步）

二轮复核通过后，Codex 必须继续实现静态 Demo；不能只停在“可进入 Demo”。

#### 6.1 Demo 输入

| 输入 | 说明 |
|------|------|
| 两轮汇总报告 | 用于确认门禁结论、未闭环风险和后续跟踪项 |
| 模块公共定义 | 用于统一术语、枚举、状态机、错误码和接口口径 |
| 移动端页面规格 | 决定 `miniapp.html` 的页面、状态和交互 |
| 管理后台页面规格 | 决定 `admin.html` 的独立页面、合并承接区和后台交互 |
| UI 缺少页面清单 | 用于 Demo 自测报告登记设计稿缺口 |

#### 6.2 独立页面与合并承接规则

Demo 实现前必须先判断页面规格性质：

| 页面规格类型 | Demo 处理方式 | 示例 |
|--------------|---------------|------|
| 独立页面 | 在对应端 Demo 中生成独立页面或锚点 | `消息通知记录查询页`、`社交权限与消息配置页` |
| 字段补充 | 合并到原页面，不新增孤立页 | `App用户管理列表-消息字段补充` |
| 详情区块补充 | 合并到原详情抽屉或详情页 | `App用户详情-消息互动区块` |
| 举报/审核字段补充 | 合并到原举报/审核处理页 | `举报处理-聊天举报字段补充` |
| 详情页或弹窗 | 可并入来源页面链路演示，也可单独锚点 | `通知详情页`、`邀请响应页` |

合并承接必须在 Demo 文档和页面文案中标注承接位置，例如“已合并到原 App 用户管理列表”“已合并到原举报处理详情”。

#### 6.2.1 原页面补充强制门禁

当页面规格名称、页面位置或 PRD 描述符合以下任一特征时，必须判定为“原页面补充”，不能判定为当前 PRD 的新增独立菜单页：

1. 名称包含“字段补充”“区块补充”“详情区块”“列表字段”“举报字段”“审核字段”。
2. 页面路径指向已有后台模块，例如 `App 用户管理`、`用户详情抽屉`、`举报处理`、`审核处理`、`配置详情`。
3. 页面目标是“在原列表新增字段”“在原详情新增 Tab/区块”“在原处理页新增上下文或操作”。
4. 页面没有明确新增菜单、路由、权限节点或独立运营工作台。

原页面补充的实现标准：

| 要求 | 标准 |
|------|------|
| 用户确认落点 | 实现前必须先询问并取得用户确认：补充内容放到原页面哪里，以及用按钮、弹窗、抽屉、Tab、列表列、详情区块中的哪一种形态承接；未确认不得实现 |
| 真实落点 | 必须修改原页面 Demo 文件，在原列表、原详情、原抽屉或原处理页中展示新增字段/区块 |
| 当前 PRD 页面 | 只允许保留“已合并至原页面”的说明、承接位置、跳转入口和验收说明 |
| 禁止重复实现 | 禁止在当前 PRD Demo 中额外渲染一套原页面列表、筛选、详情弹窗、详情抽屉、Tab、操作按钮或 mock rows |
| 数据归属 | 原页面补充所需 mock 数据必须放入原页面 Demo 的 mock 数据结构；当前 PRD 只保留自身独立页面所需数据 |
| 证据归属 | 截图、快照和自测证据必须来自原页面 Demo；当前 PRD 的承接说明页不能作为“已合并实现”的唯一证据 |
| 文档口径 | `00/01/02/03/04` 交付文档必须写明“用户确认的原页面路径 + 承接位置 + 承接形态 + 当前 PRD 不重复渲染” |
| 记录分页 | 弹窗、抽屉或 Tab 内承接记录类/明细类列表时必须展示分页组件；模块补充弹窗内记录列表默认每页 5 条，除非用户另行确认 |
| 反向清理 | 如果用户确认不放在列表/详情中，必须同步删除原列表卡片和详情抽屉中已铺开的补充字段，改为确认后的统一入口 |

禁止示例：

- `App用户管理列表-消息字段补充` 不能在 PRD-03 的 `admin.html` 中再做一张用户管理列表。
- `App用户详情-消息互动区块` 不能在 PRD-03 的 `admin.html` 中再做一个 `userMessageDrawer`。
- `举报处理-聊天举报字段补充` 不能新建“聊天举报中心”，应合并到原举报处理详情页。

正确示例：

- PRD-02 的“App 用户管理列表-关系反馈字段补充”经用户确认后，合并到 01 原 App 用户管理卡片的“模块补充”按钮和弹窗“关系反馈”Tab。
- PRD-03 的“App 用户管理列表-消息字段补充”经用户确认后，合并到 01 原 App 用户管理卡片的“模块补充”按钮，不在卡片直铺字段。
- PRD-03 的“App 用户详情-消息互动区块”经用户确认后，合并到 01 原 App 用户管理“模块补充”弹窗的“消息互动”Tab，不放入画像详情抽屉。
- 当前 PRD 后台页只保留“用户管理增强已合并至 01”的说明和打开 01 原页面入口。

#### 6.3 Demo 产物要求

1. 生成 `00-文档读取与页面范围.md`，列清楚读取文件、移动端页面、后台页面、合并承接页面。

#### 6.4 Demo 验证要求

| 验证项 | 要求 |
|--------|------|
| 静态检查 | Demo 目录无未闭合占位符；JS 语法通过 |

原页面补充必须额外执行反查：

|--------|----------|

## 8. 故障处理

| 情况 | 处理 |
|------|------|
| `claude` 不存在 | Codex 报告 Claude CLI 不可用，并生成核查任务文件供人工执行 |
| Claude CLI 认证失败 | 不尝试读取或暴露 token；提示用户检查本机 Claude 登录状态 |
| Claude 输出为空 | 先检查报告文件大小；若仍为 0 字节，收窄任务文件后直接调用 Claude CLI 重跑 |
| Claude 长时间无输出 | 超过 2 分钟且报告仍为 0 字节时中断，不继续等待；按 4.1 降级 |
| Claude 输出无效工具名警告 | 如 `Permission deny rule "Rm"/"Sudo" matches no known tool`，仅记录为本机配置警告，不单独判失败 |
| Claude 误改文件 | 本流程默认不给编辑权限；如发生异常，Codex 必须先检查 git diff，再征求用户处理 |
| 核查报告过泛 | Codex 调整任务文件，要求按文件路径和 P0/P1/P2 重新输出 |

## 9. 安全要求

1. Claude CLI 默认只读，不授予 `Edit`、`Write`、`Bash`。
2. 不在提示词、报告或聊天记录中粘贴 `.claude/settings*.json`、`.env`、token、API key。
3. 如果核查需要外部资料，优先传文件路径，不复制敏感配置内容。
4. 自动报告可以记录命令参数，但不得记录环境变量值。
