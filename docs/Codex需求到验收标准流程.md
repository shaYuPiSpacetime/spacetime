# Codex 需求到验收标准流程

> 适用项目：Spacetime 成家立业  
> 适用对象：使用 Codex 推进需求分析、PRD 冻结、技术方案、开发、自测、验收的团队成员  
> 流程版本：v1.11
> 核心目标：用同一套 Codex 流程，让一次性交互交付达到 95% 以上
> 示例需求：`docs/需求文档/需求文档-正式版/01-用户准入与资料认证初始化/`

## 1. 流程目标

本流程用于处理从轻量直改到完整需求交付的 Codex 工作。标准/完整流程通常处理一个完整需求目录，需求目录可包含整体需求、模块公共定义、移动端需求、管理后台需求、页面规格、移动端 UI 图等文件。

标准/完整流程链路（轻量直改不走此链路）：

```text
文档盘点 -> 三轮需求分析与对齐评审 -> 用户确认 -> PRD 冻结 -> 技术方案 -> 技术方案确认 -> 测试用例 -> 实现 -> 自测 -> 验收报告 -> 一致性校验
```

这套流程的目标不是“把文档读一遍”，而是让 Codex 在写代码前先发现 95% 以上会导致返工的问题：

1. 移动端流程是否闭环。
2. 管理后台流程是否闭环。
3. 移动端提交的数据、状态和审核结果是否能在后台承接。
4. 后台审核、配置、导入、导出、审计等动作是否能反向影响移动端。
5. 管理后台需求与静态 Demo `admin.html` 是否对齐。
6. 移动端需求与需求目录 `移动端/ui图/` 是否对齐。
7. 整体 PRD、端内 PRD、页面规格、UI 图和静态 Demo 是否互相一致。
8. 需求、技术方案、测试用例、代码、自测、验收是否能形成追溯链。

## 2. 默认执行协议

当用户只提供需求名称、需求编号或需求目录，并表达“按标准流程处理、全流程交付、从需求到验收、完成这个需求”等意图时，Codex 默认先进行流程路径判断；判定为标准或完整流程后，再进入阶段 0-8。轻量直改按轻量 Checklist 执行，不进入全流程。

用户只需要给出需求名称、需求编号或需求目录路径，例如：

```text
按照 docs/Codex需求到验收标准流程.md，完整处理这个需求：
{需求名称 / 需求编号 / 需求目录路径}
```

如果用户只说“xxxx 需求”，Codex 必须自行定位正式需求目录、移动端 UI 图和静态 Demo，不得要求用户手动补全路径。

### 2.0 流程路径选择：轻量 / 标准 / 完整

Codex 在执行前必须先判断需求规模，不是所有小改动都走完整 9 阶段。默认按最小充分流程处理，避免小需求被三轮分析、PRD 冻结和技术方案拖慢。

| 路径 | 适用场景 | 必走步骤 | 不需要做 |
|------|----------|----------|----------|
| 轻量直改 | 文案、注释、配置、小样式、小 bug、单点校验、1-3 个文件内可完成；不新增表/API/权限/状态/跨端闭环 | 读相关文件 -> 直接修改 -> 最小自测 -> 总结证据 | 三轮需求分析、PRD 冻结、技术方案、测试用例文档 |
| 标准流程 | 单模块需求，涉及接口、页面、后台 Demo 或移动端 UI 对齐，但不涉及复杂状态机/多模块依赖 | 阶段 0-8，按门禁推进 | 不做超出冻结范围的实现 |
| 完整严格流程 | 新模块、跨端闭环、表设计、权限/审计、资金/资产/安全/隐私、核心状态机、多模块联动 | 阶段 0-8 全量执行，复杂方案和表设计统一确认 | 不允许跳过任何确认门禁 |

轻量直改必须同时满足以下条件：无新增业务表、无新增接口、无权限变化、无状态机变化、无前后台闭环变化、无 Demo/UI/需求口径冲突、无 P0/P1 风险。只要命中任一升级条件，就必须进入标准或完整流程。

升级条件：新增/修改表字段、接口契约变化、权限/审计变化、状态流转变化、后台 Demo 与需求不一致、移动端 UI 与需求不一致、跨端数据回写、用户要求全流程、执行者无法判断影响范围。

### 2.1 需求与关联资产自动发现协议

当用户只提供需求名称或需求编号时，Codex 必须按以下顺序自动发现关联资产：

1. 在 `docs/需求文档/需求文档-正式版/` 下按需求编号、需求名称、中文关键词进行匹配，确定正式需求目录。
2. 在已确定的正式需求目录下查找移动端 UI 图，优先识别 `移动端/ui图/`；如目录不存在，继续查找移动端下包含图片资源或 UI 命名的目录，并在阅读证据矩阵中记录实际路径。
3. 在 `docs/静态Demo/` 下按同一需求编号、需求名称、中文关键词匹配静态 Demo 目录，并优先查找 `html/admin.html`；如果只存在 `html/index.html` 或其他入口，只能作为辅助证据，必须在三轮分析中标记“admin.html 缺失/待补齐或待确认”，不得默认视为后台 Demo 已对齐。
4. 如果出现多个候选目录，先列出候选项和匹配依据，选择最可能的一项继续；无法可靠判断时才向用户确认。
5. 如果找不到 UI 图或 Demo，不得编造路径或视为已对齐，必须在三轮分析中标记为“关联资产缺失/待补充”。
6. `蓝湖UI缺少页面清单.md` 不是必需输入，不作为需求分析、冻结、技术方案或实现门禁；如存在可作为辅助背景，不得替代 `移动端/ui图/` 和正式需求文档。

流程文档中的路径只作为发现规则和候选位置，不作为用户必须输入的硬编码路径。

标准/完整流程必须按以下协议执行；轻量直改只执行路径判断和轻量 Checklist：

1. 先读取本流程文档、`AGENTS.md`、需求目录；如仓库存在 `TEAM_STANDARDS.md` 或其他团队规范文档，也必须读取。若团队规范文档不存在，不得因此跳过技术方案、测试用例、实现、自测或确认门禁，代码规范以 `AGENTS.md`、现有代码风格、技术方案和本流程为准。
2. 标准/完整流程自动执行阶段 0 到阶段 8，但阶段 1 需求分析、阶段 3 技术方案存在用户确认门禁，不要求用户每一步手动下命令。
3. 标准/完整流程每进入一个阶段，声明本阶段使用的 Codex skill。
4. 标准/完整流程每完成一个阶段，写入对应阶段产物，并检查门禁。
5. 阶段 1 必须执行三轮全量需求分析；每一轮都同时覆盖“需求合理性与闭环评审”“管理后台需求 vs 静态 Demo admin.html 对齐评审”“移动端需求 vs 移动端 ui图 对齐评审”。
6. 三轮分析的目的不是重复粘贴结论，而是用第二轮、第三轮补漏、交叉核对和收敛等级；每轮都必须保留新增问题、修正问题和仍待确认问题。
7. 阶段 1 三轮分析完成后，必须输出三类问题清单和需求分析确认清单，并停止推进等待用户确认；用户确认前不得输出技术方案。
8. 用户确认需求未对齐项后，必须先同步修正需求文档和管理后台静态 Demo `admin.html`；需求文档是最终准确口径，管理后台 Demo 必须与需求文档对应。
9. 移动端 UI 图也必须与需求文档保持一致；但 Codex 不修改 UI 图文件本身，只记录 UI 图待调整项，并在后续接口设计中以需求文档为准、参考 UI 图。
10. 阶段 3 技术方案中，简单方案由 Codex 自检复杂度和实现路径，并在技术文档中记录依据；复杂方案必须写清方案选型、关键取舍和待确认项。无论简单或复杂，技术文档输出后都必须等待用户统一确认。
11. 表设计必须放在技术方案文档的数据库/表设计章节中，并在同一份技术方案的“待确认项与统一确认清单”里体现，由用户统一确认。
12. 涉及新增/修改业务表时，技术方案必须写清表结构、字段定义、字段类型、长度、是否必填、默认值、字段描述、索引、唯一约束、状态字段、审计字段、逻辑删除和迁移脚本；不得只写字段名或“后续建表时确认”。
13. 阶段 3 技术文档输出后必须停止推进，等待用户确认；用户确认前不得进入测试用例、实现、自测、验收或一致性校验。
14. 门禁满足时，自动进入下一阶段；门禁不满足时，停止推进，输出阻塞清单、影响范围和建议处理方式。
15. 需要环境、Token、账号、测试数据时，先从仓库配置读取；读取不到时只问缺失项，不编造。
16. 需要破坏性操作、外部网络、生产环境、真实资金或敏感数据时，必须先停下确认。
17. 自测、验收、一致性校验必须基于真实证据，不能用“应该可以”代替结果。
18. 标准/完整流程最终输出交付总结，列出产物路径、通过/失败/跳过项、遗留问题和下一步建议；轻量直改只输出修改文件、验证结果和未覆盖风险。

### 2.2 标准/完整流程自动推进与停止条件

| 场景 | Codex 行为 |
|------|------------|
| 阶段 1 三轮分析未完成 | 不进入 PRD 冻结或技术方案 |
| 阶段 1 三轮分析完成 | 输出三类问题清单和需求分析确认清单，等待用户确认 |
| 用户确认需求分析结论、无 P0，且 P1 已有明确处理方案 | 先同步修正需求文档和管理后台 Demo，再进入 PRD 冻结 |
| 已确认未对齐项但未完成需求文档/Demo 同步 | 停止推进，不进入 PRD 冻结或技术方案 |
| PRD 已冻结或可冻结 | 根据复杂度执行技术方案确认协议 |
| 技术文档已输出并经用户确认 | 自动生成测试用例 |
| 技术方案复杂或存在表设计 | 在技术方案待确认清单中体现，等待用户统一确认 |
| 测试用例覆盖 P0/P1 | 自动进入实现 |
| 实现完成 | 自动执行可执行的自测 |
| 缺测试环境、Token、账号或数据 | 记录跳过项和补测条件，不伪造通过 |
| 发现 P0 阻塞 | 停止推进，不进入下一阶段 |
| 发现 P1 阻塞但有明确降级方案 | 可有条件推进，并在后续产物中持续追踪 |
| 发现需求超范围 | 记录超范围项，不静默实现 |
| 发现代码/测试失败 | 使用 `systematic-debugging` 定位根因后再修复 |

### 2.3 最终交付包

标准/完整流程完成后，交付包以第 5 章“标准产物目录”为准。最终总结必须列出实际生成的产物路径、缺失/跳过原因和补测条件。轻量直改只需要列出修改文件、验证结果和未覆盖风险。

如果完成代码实现，还应在最终总结中列出：

| 类型 | 必须说明 |
|------|----------|
| 后端改动 | Controller、Service、DAO、Mapper、实体、SQL 等 |
| 管理后台改动 | 页面、路由、API、权限、状态管理等 |
| 移动端后端接口改动 | 接口、状态、错误码、异常态、对接文档等 |
| 测试改动 | 单测、接口脚本、页面测试、手工验收项 |
| 未执行项 | 缺什么环境或数据，如何补测 |

### 2.4 深度阅读与证据协议

需求评审、PRD 冻结、技术方案、测试用例、验收报告和一致性校验都必须遵守“先读证据，再下结论”的协议。尤其是阶段 0 和阶段 1，不允许只看文件名、目录结构、关键词命中或片段抽查后直接给出冻结建议。

Codex 必须做到：

1. 对需求目录内的模块公共定义、端内定义、模块 PRD、页面规格等文本文件逐文件全文阅读；对移动端 UI 图逐文件查看、截图/视觉核对，并在阅读证据矩阵中记录文件名、页面含义、字段/状态/交互证据和无法识别的缺口。
2. 对管理后台需求与静态 Demo 进行对齐阅读：先按“需求与关联资产自动发现协议”定位对应静态 Demo，再读取匹配目录下的 `html/admin.html`；如需要辅助证据，可继续读取同目录 `index.html`、`miniapp.html`、`assets/`、`mock/`。
3. 对移动端需求与移动端 UI 图进行对齐阅读：先按“需求与关联资产自动发现协议”定位正式需求目录，再读取匹配到的移动端 UI 图目录，优先为正式需求目录下的 `移动端/ui图/`。
4. 对项目级全局定义、端专属全局定义、`AGENTS.md` 至少阅读与当前阶段相关的全文或完整章节；如仓库存在 `TEAM_STANDARDS.md` 或其他团队规范文档，也必须纳入阅读证据。不存在时在阅读证据矩阵中记录“团队规范文档缺失，按 `AGENTS.md` 和现有代码风格执行”，不得把缺失当作跳过代码规范的理由。
5. 在需求评审报告中记录“阅读证据矩阵”，说明每个文件读到了什么、支撑了哪些判断、是否发现矛盾或缺口。
6. 每个 P0/P1/P2 问题都必须能追溯到具体文件、章节、页面规格、静态 Demo `admin.html` 位置或 `移动端/ui图/` 证据；不能只写“感觉有风险”“后续确认”。
7. 每个“可冻结 / 有条件冻结 / 不可冻结”的判断都必须对应门禁证据，不能只因为没有发现明显问题就默认通过。
8. 如果文件过多，允许先做目录盘点，但在输出阶段 1 结论前必须完成逐文件阅读；未完成时只能输出“阶段 0 盘点结果”，不能输出冻结建议。
9. 如果只能通过关键词检索、抽查或已有报告进行初评，必须在结论中明确标注“初评”，不得写成“深度评审”或“可冻结”。

推荐在评审报告中保留以下字段：

```markdown
## 阅读证据矩阵

| 文件 | 阅读方式 | 关键证据 | 支撑结论 | 遗留疑点 |
|------|----------|----------|----------|----------|
```

## 3. Codex Skill 使用原则

本流程以本文档列出的 Codex skills 为主入口。技术方案、PRD 冻结、测试用例、实现、自测和验收均按本文档阶段门禁执行，不依赖旧 `.claude` 技术方案/PRD skill 路由。

如果 `AGENTS.md` 与本文档在技术方案或 PRD 流程入口上存在差异，以本文档为准；不得因为旧 `.claude` skill 路由缺失或不使用而跳过技术方案、测试用例、用户确认或验收门禁。

当前可用 Codex skills：

| 阶段 | Codex skill | 用途 |
|------|-------------|------|
| 三轮需求分析与对齐评审 | `brainstorming` | 识别需求边界、业务闭环、后台 Demo 对齐、移动端 UI 图对齐、疑问与验收条件 |
| 技术方案 | `writing-plans` | 形成可实施的技术设计和任务拆解 |
| 实现 | `test-driven-development` | 新行为先定义测试或可验证条件 |
| 实施执行 | `executing-plans` | 按计划逐步开发 |
| 并行执行 | `subagent-driven-development` | 多个独立任务可并行推进时使用 |
| 调试 | `systematic-debugging` | 出现 bug 或测试失败时先定位根因 |
| 自测 | `verification-before-completion` | 完成前运行验证命令并记录证据 |
| Review | `requesting-code-review` | 提交前审查缺陷、风险、遗漏测试 |
| 处理 Review | `receiving-code-review` | 收到评审意见后逐条验证和修改 |

### 3.1 阶段技能速查

| 阶段 | 必用 Codex skill | 可选 Codex skill | 触发提示词 |
|------|------------------|------------------|------------|
| 阶段 0：文档盘点 | `brainstorming` | 无 | “先盘点这个需求目录的文档结构和缺失项” |
| 阶段 1：三轮需求分析与对齐评审 | `brainstorming` | `systematic-debugging` | “连续三轮检查需求闭环、后台 admin.html 对齐、移动端 ui图 对齐” |
| 阶段 2：PRD 冻结 | `brainstorming` | 无 | “基于需求评审结论冻结 PRD，P0 不允许冻结” |
| 阶段 3：技术方案 | `writing-plans` | `brainstorming` | “基于冻结 PRD 输出技术方案，复杂方案和表设计进入统一确认” |
| 阶段 4：测试用例 | `test-driven-development` | `writing-plans` | “基于技术方案生成测试用例，覆盖接口和页面闭环” |
| 阶段 5：实现 | `test-driven-development`、`executing-plans` | `subagent-driven-development`、`systematic-debugging` | “按技术方案和测试用例实现” |
| 阶段 6：自测 | `verification-before-completion` | `systematic-debugging` | “执行接口测试、管理后台页面测试、构建测试并出自测报告” |
| 阶段 7：验收报告 | `verification-before-completion` | `requesting-code-review` | “基于测试证据输出验收报告” |
| 阶段 8：一致性校验 | `verification-before-completion`、`requesting-code-review` | `systematic-debugging` | “校验 PRD、方案、测试、代码、自测、验收是否一致” |

使用规则：

1. 每个阶段开始时，先声明本阶段使用的 skill。
2. 一个阶段有多个必用 skill 时，按表格顺序使用。
3. 如果阶段门禁不满足，不进入下一阶段。
4. 如果出现 bug、测试失败、闭环断链，立即使用 `systematic-debugging` 定位根因。
5. 如果要声明“完成、通过、可验收”，必须先使用 `verification-before-completion` 获取证据。

## 4. 需求目录标准结构

| 目录存在 | 否 | 只能证明文件存在，不能证明需求合理 |

## 7. 阶段 1：需求合理性与闭环评审

**本阶段使用技能：**

| 类型 | Skill | 用法 |
|------|-------|------|
| 必用 | `brainstorming` | 判断需求是否合理，梳理移动端闭环、管理后台闭环、前后台联动和疑问分级 |
| 条件使用 | `systematic-debugging` | 当发现流程矛盾、状态断链、字段冲突时，用根因分析方式定位问题来源 |

**阶段输出前必须说明：** 已使用哪个 skill、发现了哪些 P0/P1/P2/P3 问题、是否允许进入 PRD 冻结。

### 7.1 目标

这是整个流程最重要的阶段。Codex 必须先判断需求是否合理、是否有问题、移动端和管理后台是否闭环，再决定能不能冻结 PRD。

### 7.1.1 三轮全量分析协议

阶段 1 必须连续执行 3 轮分析。每一轮都必须同时覆盖以下三类评审，不允许把三轮拆成三个不同主题：

| 轮次 | 必须覆盖的三类评审 | 本轮重点 | 输出要求 |
|------|------------------|----------|----------|
| 第 1 轮 | 需求合理性与闭环评审；管理后台需求 vs 静态 Demo `admin.html` 对齐评审；移动端需求 vs 移动端 `ui图` 对齐评审 | 完整阅读、建立基线、发现显性问题 | 输出三类初始问题清单 |
| 第 2 轮 | 同上三类 | 反向追溯、交叉核对、检查第一轮遗漏 | 输出新增问题、修正等级、仍待确认项 |
| 第 3 轮 | 同上三类 | 收敛结论、核对 P0/P1/P2 是否都有证据和处理建议 | 输出最终三类问题清单和需求分析确认清单 |

三轮分析必须保留每轮的阅读证据和差异，不得只输出第三轮汇总。若第二轮或第三轮没有新增问题，也必须说明“无新增”的证据范围。

三轮完成后必须暂停，等待用户确认需求分析结论；用户确认前不得进入 PRD 冻结、技术方案或后续阶段。

### 7.1.2 三轮分析时间盒与收敛标准

三轮分析的目标是补漏和收敛，不是无限制造问题清单。除大需求拆分页面组外，单轮分析建议控制在 30-45 分钟；超过时间仍无法覆盖时，必须拆分页面组或标记阻塞，不得继续无边界扩散。

| 轮次 | 收敛要求 | 停止条件 |
|------|----------|----------|
| 第 1 轮 | 建立完整基线，暴露显性问题 | 三类评审均有初始清单 |
| 第 2 轮 | 反向追溯 P0/P1 和遗漏 | 新增 P0/P1 已归类，重复问题已合并 |
| 第 3 轮 | 只做收敛和门禁判断，原则上不再发散 P2/P3 | P0/P1/P2 均有证据、处理建议和确认对象 |

如果第 3 轮仍新增大量问题，说明需求范围或文档质量不适合继续堆问题，必须停止并输出“需拆分/需补充资料/需用户确认”的阻塞结论。输出给用户时要合并同类项，优先呈现 P0/P1/P2，不把几十条重复细项直接丢给用户确认。

### 7.2 评审维度

| 维度 | 必查问题 |
|------|----------|
| 业务目标 | 需求目标、用户价值、运营目标是否清楚 |
| 范围边界 | 本期做什么、不做什么、延期什么是否明确 |
| 移动端闭环 | 用户从入口、填写、提交、失败、重试、完成、进入核心链路是否闭环 |
| 管理后台闭环 | 后台从列表、详情、审核、配置、导入、导出、审计是否闭环 |
| 前后台联动 | 移动端提交的数据是否进入后台；后台处理结果是否回到移动端 |
| 数据闭环 | 字段、枚举、字典、状态、配置是否有统一来源 |
| 状态闭环 | 每个状态是否有进入条件、退出条件、展示文案和后续动作 |
| 权限闭环 | 后台角色、权限点、敏感字段、下载、导出、审计是否明确 |
| UI 闭环 | 页面规格和移动端 UI 图是否能支撑实现和验收 |
| 异常闭环 | 空态、失败、驳回、第三方不可用、权限拒绝、重复提交是否覆盖 |
| 测试可行性 | 每条核心需求是否能转成接口测试、页面测试或手工验收 |

### 7.3 移动端闭环检查

每条移动端主流程必须按以下链路检查：

```text
入口 -> 页面展示 -> 用户输入 -> 前端校验 -> 接口提交 -> 后端处理 -> 状态反馈 -> 用户下一步动作 -> 核心能力开放/阻断
```

最低检查项：

| 检查项 | 说明 |
|--------|------|
| 入口 | 用户从哪里进入该页面或流程 |
| 前置条件 | 是否需要登录、资料、认证、权限、定位、上传授权 |
| 字段 | 字段是否来自公共定义或端内定义 |
| 操作 | 主按钮、次按钮、跳过、返回、重试是否明确 |
| 接口 | 是否能推导出需要的提交、查询、上传、状态接口 |
| 状态 | 提交中、成功、失败、审核中、驳回、已通过是否明确 |
| 异常 | 年龄不符、定位失败、上传失败、第三方不可用等是否有处理 |
| 后续 | 完成后进入哪个页面或能力，未完成时如何拦截 |

### 7.4 管理后台闭环检查

每个管理后台页面必须按以下链路检查：

```text
菜单入口 -> 权限校验 -> 列表/筛选 -> 详情 -> 操作 -> 状态变更 -> 通知/回写 -> 审计日志 -> 列表刷新/后续处理
```

最低检查项：

| 检查项 | 说明 |
|--------|------|
| 菜单入口 | 页面属于哪个菜单、路由、权限点 |
| 角色权限 | 谁能看、谁能操作、谁能导出、谁能看敏感字段 |
| 列表字段 | 字段是否脱敏、是否支持筛选/排序/分页 |
| 详情信息 | 是否能支撑审核或运营判断 |
| 操作结果 | 通过、驳回、复核、配置、导入、导出后的状态变化 |
| 移动端回写 | 后台结果是否通知移动端、是否影响准入状态 |
| 审计 | 敏感查看、原图下载、导出、高风险配置是否留痕 |
| 异常 | 无权限、数据不存在、重复审核、导入失败、第三方失败是否覆盖 |

### 7.5 前后台闭环矩阵

需求评审必须输出前后台闭环矩阵。

```markdown
| 闭环 ID | 移动端触发 | 后端状态/数据 | 管理后台承接 | 后台处理结果 | 移动端反馈 | 是否闭环 | 问题 |
|---------|------------|---------------|--------------|--------------|------------|----------|------|
```

示例：

```text
用户提交学历认证 -> 生成学历审核记录 -> 后台学历认证审核页处理 -> 通过/驳回 -> 移动端认证页和站内信更新
```

### 7.5.1 管理后台需求 vs 静态 Demo `admin.html` 对齐检查

每一轮都必须对比管理后台 PRD、管理后台页面规格和静态 Demo `admin.html`。`admin.html` 必须由 Codex 根据需求编号/名称自动发现，不要求用户提供完整路径。

```text
候选根目录：docs/静态Demo/
目标文件：匹配需求目录下的 html/admin.html
```

最低检查项：

| 检查项 | 说明 |
|--------|------|
| 页面覆盖 | 管理后台 PRD/页面规格中的页面是否在 `admin.html` 或合并承接页面中存在 |
| 字段对齐 | 列表、详情、抽屉、弹窗、配置项字段是否一致，敏感字段是否脱敏 |
| 操作对齐 | 审核、配置、导入、导出、查看、下载、二次确认等操作是否一致 |
| 状态对齐 | 待审、通过、驳回、失败、禁用、配置生效等状态是否一致 |
| 权限与审计 | 权限点、角色差异、敏感查看、导出和下载留痕是否体现 |
| 合并承接 | 跨模块复用或合并到既有后台页面的承接位置是否明确 |
| 缺失与差异 | 缺页面、缺字段、缺操作、交互不一致必须进入未对齐清单 |

#### 管理后台 Demo 多轮对齐协议

管理后台以需求文档/冻结记录为准，以静态 Demo `admin.html` 为视觉和交互基线。阶段 1/2 中，用户确认的“需求与 Demo 未对齐项”可以同步修正需求文档和 Demo；进入实现阶段后，Demo 默认只读，未获用户明确授权不得修改。Demo 中需求已删除或不做的内容不得实现，记录为“按需求排除项”。

管理后台必须按 Demo 多轮对齐协议执行，至少 3 轮：

1. 逐页面矩阵核对：查询条件、列表列、卡片字段、详情/抽屉、弹窗、二次确认、行操作、批量操作、导入导出、分页统计、反馈提示、状态守卫。
2. Demo 截图 vs 实现截图对比：同一页面、同一状态、同一弹窗成对截图，差异进入修复清单。
3. 状态与交互回归：列表必须构造多状态数据，保证截图中能看到待处理、通过、驳回、失败、冲突、禁用等典型状态；操作按钮必须按状态守卫展示。

发现老页面已有相似功能时，仍要按 `admin.html` 逐项比对，不能默认复用即为对齐。每轮输出：对齐矩阵、截图清单、差异清单、修复结果。管理后台 1:1 还原度低于 95% 不得进入验收。

对比表：

| 页面 | Demo 截图 | 实现截图 | 核对项 | 差异 | 处理结果 | 结论 |
|------|-----------|----------|--------|------|----------|------|

输出格式：

```markdown
| 编号 | 后台需求来源 | admin.html 证据 | 未对齐类型 | 问题描述 | 等级 | 处理建议 |
|------|--------------|-----------------|------------|----------|------|----------|
```

### 7.5.2 移动端需求 vs 移动端 `ui图` 对齐检查

每一轮都必须对比移动端 PRD、移动端页面规格和移动端 UI 图。UI 图目录必须由 Codex 根据需求编号/名称自动发现，不要求用户提供完整路径。

```text
候选根目录：docs/需求文档/需求文档-正式版/
目标目录：匹配需求目录下的 移动端/ui图/
```

最低检查项：

| 检查项 | 说明 |
|--------|------|
| 页面覆盖 | 移动端页面规格中的页面是否有 UI 图或明确缺图处理口径 |
| 字段文案 | UI 图中的字段、按钮、标题、提示文案是否与 PRD 一致 |
| 流程状态 | 正常态、空态、加载、失败、驳回、审核中、权限阻断等状态是否覆盖 |
| 交互动作 | 主按钮、次按钮、返回、跳过、重试、上传、授权等交互是否一致 |
| 异常态 | 定位失败、上传失败、第三方不可用、重复提交、年龄不符等是否有 UI 或降级方案 |
| 缺图处理 | 缺图项是否明确补图、按规格实现、通用态降级或延期 |

#### 移动端接口多轮对齐协议

移动端以需求文档/冻结记录为准，以移动端 UI 图为场景和交互参考；不实现移动端前端代码。若 UI 图与需求文档不一致，以需求文档为准，并记录“UI 待调整项”。

移动端必须按接口多轮对齐协议执行，至少 3 轮：

1. 场景流程核对：逐页面/逐流程核对入口、提交、保存、回显、审核中、通过、驳回、失败、重试、跳过、权限阻断、前后台状态联动。
2. 接口契约核对：逐接口核对 Method、Path、入参、出参、字段类型、必填、默认值、错误码、状态枚举、权限、幂等、分页/上传/文件字段。
3. 前端对接核对：对照 UI 图和需求文档输出移动端接口对接文档；每个页面/动作都要能找到对应接口、请求示例、响应示例、异常处理建议。

移动端也要构造多状态数据或 mock 返回，覆盖未提交、审核中、通过、驳回、失败、资料缺失、权限不足、第三方不可用等状态。不能只测正常流程。每轮输出：接口矩阵、场景状态清单、差异清单、修复结果。移动端接口完整度低于 95% 不得进入验收。

对比表：

| 页面/流程 | UI 图/需求证据 | 接口 | 入参 | 出参 | 状态/错误码 | 前端处理建议 | 差异 | 结论 |
|-----------|----------------|------|------|------|-------------|--------------|------|------|

### 7.6 问题分级

| 等级 | 定义 | 处理规则 |
|------|------|----------|
| P0 | 主流程无法成立、前后台断链、核心数据/状态缺失、安全合规缺口 | 不允许冻结 PRD |
| P1 | 影响核心体验、核心页面、核心接口、权限、审核、支付/资产等重要链路 | 默认不冻结；如有明确降级方案可有条件冻结 |
| P2 | 不影响核心闭环，但会影响体验、效率、次要状态或运营便利性 | 可冻结，但必须记录遗留项 |
| P3 | 文案、展示、低风险优化或后续增强 | 可冻结，进入后续优化池 |

| 类型 | 判定标准 | Codex 行为 | 用户确认 |

## 11. 阶段 5：实现

**本阶段使用技能：**

| 类型 | Skill | 用法 |
|------|-------|------|
| 必用 | `test-driven-development` | 新功能、缺陷修复、状态流转和权限规则必须先有测试或可验证条件 |

| 条件使用 | `systematic-debugging` | 实现或测试中出现异常时先定位根因再修改 |

**阶段输出前必须说明：** 本次实现对应的技术方案章节和测试用例 ID。

### 11.1 目标

按技术方案和测试用例实现，不在实现阶段重新发明需求。

本阶段实现范围限定为：管理后台前端、管理后台后端、移动端后端接口。不实现移动端前端代码。

### 11.2 输入

### 11.3 实现原则

1. 严格遵守 `Controller -> Service -> ServiceImpl -> DAO -> DAOImpl -> Mapper`。
2. `admin/` 与 `miniapp/` 不互相 import，共享逻辑放 `common/`。
3. Controller 返回精确 `R<T>`。
4. 管理后台接口使用 `@RequirePermission` 和既有 RBAC 模式。
5. 业务表包含 `BaseEntity` 审计字段和逻辑删除。
6. 前端 API 放 `frontend/src/api/`，路由放 `frontend/src/router/`。
7. 页面组件只拼 UI 和调用 hook，业务逻辑放 hook/API/store。
8. 写代码必须遵守仓库现有规范：命名、分层、DTO/VO、异常、权限注解、返回结构、SQL/Mapper、前端 API/路由/组件组织都要贴合已有模式；不得随意引入新风格或临时写法。
9. 注释要求：简单 getter/setter、直观赋值不写废话注释；复杂业务规则、状态流转、权限/安全判断、跨端闭环、第三方 Provider、数据迁移、非显然取舍必须写清楚“为什么这么做”和关键约束。
10. 新增/修改 Controller、Service、DAO、Mapper、DTO/VO、实体、前端 API、页面组件时，要保证类/方法/关键字段具备必要说明；已有代码缺注释且本次修改触碰到，应顺手补齐与当前需求相关的必要注释。
11. 先实现最小闭环，再补充次要能力。
12. 不把未冻结的新需求混入当前实现。
13. 管理后台前端必须按“管理后台 Demo 多轮对齐协议”执行，在冻结范围内 1:1 还原 `admin.html`，并记录按需求排除项。
14. 管理后台后端接口必须支撑已纳入冻结范围的后台页面交互，以及技术方案/测试用例定义的权限、状态、审计、异常分支。
15. 移动端只实现后端接口和移动端接口对接文档，不写移动端前端代码。
16. 移动端接口必须按“移动端接口多轮对齐协议”执行，并输出给前端对接的接口文档。

### 11.4 门禁

进入自测前必须满足：

- 实现范围不超过冻结 PRD 和技术方案。
- 所有新增行为有测试用例或明确验证方式。
- 无调试代码、占位数据、硬编码 Token。
- 代码符合 `AGENTS.md`、现有代码风格和技术方案约束；复杂逻辑、状态流转、权限/安全、跨端闭环和第三方 Provider 有必要注释。
- 数据库变更有 SQL 或迁移说明。
- 管理后台已按“管理后台 Demo 多轮对齐协议”完成，1:1 Demo 还原度 ≥ 95%，并有矩阵、截图、差异修复记录或测试证据。
- 移动端已按“移动端接口多轮对齐协议”完成，接口完整度 ≥ 95%，并有接口矩阵、场景状态清单、差异修复记录或测试证据。
- 未修改移动端前端代码；如确需修改，必须作为超范围项重新确认。

### 12.2.1 95% 自测核查与修复循环

自测必须计算并记录两个指标：

两个指标必须用清单项计算，不能写“基本一致”“看起来完整”。每个未通过项都要有扣分原因、证据、修复动作和复测结果。

| 指标 | 达标线 | 证据 |
|------|--------|------|
| 管理后台 1:1 Demo 还原度 | ≥ 95% | `admin.html` 对比矩阵、截图、操作记录、页面/字段/按钮/弹窗/状态/异常态/控件/详情/分页统计/反馈/交互链路证据 |
| 移动端接口完整度 | ≥ 95% | 接口清单、测试用例结果、错误码/状态覆盖、权限/异常/幂等场景、移动端接口对接文档 |

如果任一指标低于 95%，Codex 必须按以下循环继续处理，不能进入验收通过结论：

```text
定位扣分项 -> 回到需求/技术方案/实现定位原因 -> 修复代码或文档 -> 重新运行自测 -> 重新生成证据 -> 重新计算 95% 指标
```

管理后台自测必须执行“管理后台 Demo 多轮对齐协议”，移动端自测必须执行“移动端接口多轮对齐协议”；对齐矩阵、截图/接口证据、差异清单、修复结果都要写入自测报告。

只有两个指标均达到 95% 以上，且 P0/P1 无关键缺失时，才能声明实现达标。若受环境、账号、数据或外部服务阻塞，必须记录阻塞原因、影响指标和补测条件，不得写成达标。

### 14.2 校验方向

| 方向 | 检查 |
|------|------|
| PRD -> 需求评审 | 核心需求是否被识别，问题是否被分级 |
| 需求评审 -> PRD 冻结 | P0/P1 是否处理后再冻结 |
| PRD 冻结 -> 技术方案 | 冻结范围是否都有设计 |
| 技术方案 -> 测试用例 | 接口、页面、状态、权限是否都有测试 |
| 测试用例 -> 实现 | 用例中的行为是否已实现 |
| 实现 -> 自测 | 改动是否被真实验证 |
| 自测 -> 验收 | 验收结论是否如实反映测试结果 |
| 全链路 | 是否有超范围实现或静默需求变更 |

## 15. 一次性交互 95% 的口径

本流程中的“一次性交互达到 95% 以上”按以下方式判定：

```text
一次性交付率 = 首轮验收通过的 P0/P1 需求数 / 冻结范围内 P0/P1 需求总数
```

计入“首轮验收通过”的条件：

1. PRD 冻结后没有因需求理解错误返工。
2. 技术方案覆盖该需求。
3. 测试用例覆盖该需求。
4. 代码实现满足该需求。
5. 自测或验收能提供证据。
6. 一致性校验无 P0/P1 断链。

不计入通过的情况：

1. 需求评审漏掉核心问题，导致实现后返工。
2. 移动端和管理后台闭环断裂。
3. 后台状态无法回写移动端。
4. 测试用例缺失导致验收时才发现问题。
5. 自测报告伪通过或缺证据。

## 16. 阶段 Checklist

每个阶段输出前必须按 Checklist 自查。轻量直改只执行轻量 Checklist；标准/完整流程按阶段执行，不允许口头跳过。

| 阶段 | 必须勾选 | 未满足处理 |
|------|----------|------------|
| 路径选择 | 已判断轻量/标准/完整；轻量直改无表/API/权限/状态/跨端影响 | 命中升级条件则进入标准/完整流程 |
| 阶段 0 文档盘点 | 需求目录、Demo、UI 图、全局定义已定位；缺失项已记录 | 只输出盘点，不给冻结结论 |
| 阶段 1 三轮分析 | 三轮均覆盖三类评审；同类问题已合并；P0/P1/P2 有证据和处理建议 | 等待用户确认，不输出技术方案 |
| 阶段 2 PRD 冻结 | 用户确认项已同步需求文档和 `admin.html`；UI 图差异已记录 | 不冻结或有条件冻结并列阻塞 |
| 阶段 3 技术方案 | PRD 追溯、接口、状态、权限、表设计（如涉及）、95% 评分表和待确认项齐全 | 技术文档未确认前不进测试/实现 |
| 阶段 4 测试用例 | P0/P1 需求、闭环、后台还原、移动端接口均有用例 | 补测试用例，不进入实现 |
| 阶段 5 实现 | 只实现冻结范围；后台按“管理后台 Demo 多轮对齐协议”实现；移动端按“移动端接口多轮对齐协议”实现后端接口和对接文档；代码符合 `AGENTS.md`、现有风格和技术方案，复杂逻辑有必要注释 | 超范围项重新确认；规范或注释缺失先补齐再进入自测 |
| 阶段 6 自测 | 构建/接口/后台页面/闭环已验证；后台 Demo 多轮对齐和移动端接口多轮对齐证据完整；两个 95% 指标已按表计分 | 低于 95% 按扣分项修复并复测 |
| 阶段 7 验收 | 需求完成度、闭环完成度、测试证据、遗留问题齐全 | 不写通过结论 |
| 阶段 8 一致性校验 | PRD、评审、冻结、方案、测试、代码、自测、验收无 P0/P1 断链 | 输出不一致或有条件一致 |

轻量直改 Checklist：确认影响范围 -> 修改文件 -> 运行最小验证 -> 输出修改点、验证结果和未覆盖风险。轻量直改不生成正式 PRD/技术方案/测试用例文档，除非用户要求或命中升级条件。

## 17. 团队标准提示词

### 17.1 默认处理提示词

## 18. 禁止事项

1. 禁止跳过需求合理性与闭环评审直接写技术方案。
2. 禁止只做一轮需求分析就进入 PRD 冻结或技术方案。
3. 禁止把三轮分析拆成三个不同主题；每一轮都必须同时覆盖需求合理性与闭环、后台 vs `admin.html`、移动端 vs `ui图`。
4. 禁止没有输出三类问题清单和需求分析确认清单就进入下一阶段。
5. 禁止用户未确认需求分析结论时输出技术方案。
6. 禁止移动端和管理后台未闭环就冻结 PRD。
7. 禁止有 P0 问题时冻结 PRD。
8. 禁止 PRD 改了但不更新技术方案和测试用例。
9. 禁止技术方案只写“按 PRD 实现”。
10. 禁止复杂方案不输出方案选型、关键取舍和待确认项。
11. 禁止表设计脱离技术方案单独口头确认；表设计必须写入技术方案，并进入统一确认清单。
12. 禁止表设计只写表名或字段名；涉及表设计时必须写清字段类型、长度、默认值、字段描述、索引、约束、状态字段、审计字段、逻辑删除和迁移脚本。
13. 禁止技术文档未经用户确认就生成测试用例、执行实现、自测、验收或一致性校验。
14. 禁止需求确认后只改报告不改需求文档；确认后的需求口径必须同步到需求文档。
15. 禁止管理后台需求已确认变更但不同步 `admin.html`；如用户明确要求本轮不改 Demo，必须记录该确认结论。
16. 禁止修改移动端 UI 图；UI 图差异只能记录为待调整项，接口实现以需求文档为准。
17. 禁止实现移动端前端代码，除非用户另行确认扩展范围。
18. 禁止管理后台实现只口头声明 1:1，还原必须有页面/字段/按钮/弹窗/状态/异常态/控件/详情/分页统计/反馈/交互链路证据。
19. 禁止移动端接口只覆盖正常流程；必须按“移动端接口多轮对齐协议”覆盖场景、契约、状态和对接文档。
20. 禁止测试报告中伪造通过结果。
21. 禁止编造 API 地址、Token、账号、测试数据。
22. 禁止管理后台和小程序端互相 import。
23. 禁止 Controller 直接调 DAO 或 Mapper。
24. 禁止 ServiceImpl 直接调 Mapper。
25. 禁止新增需求混入当前需求而不记录超范围项。
26. 禁止验收报告只写结论不写证据。
27. 禁止一致性校验跳过 P0/P1 断链。
28. 禁止只靠关键词检索、片段抽查、已有报告或目录结构输出“深度需求评审”。
29. 禁止没有阅读证据矩阵就给出“可冻结 / 有条件冻结 / 不可冻结”结论。
30. 禁止管理后台 1:1 Demo 还原度低于 95% 时声明完成。
31. 禁止移动端接口完整度低于 95% 时声明完成。
32. 禁止未重新自测和重新计算 95% 指标就把未达标项写成达标。
33. 禁止把 蓝湖UI缺少页面清单.md 当作必需输入或门禁；该文档可忽略，不得替代正式需求文档和 移动端/ui图/。
34. 禁止把轻量直改强行套完整 9 阶段流程，导致小需求交付成本过高。
35. 禁止三轮分析无时间盒、无收敛标准地持续发散问题；第三轮仍大量新增问题时必须拆分、阻塞或请求确认。

37. 禁止复杂业务、状态流转、权限/安全、跨端闭环、第三方 Provider、数据迁移等关键代码无必要注释就进入自测或验收。
