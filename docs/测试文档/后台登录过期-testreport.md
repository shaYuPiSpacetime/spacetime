## 2. 根因与修复

旧响应拦截器在 HTTP401 时只删除 `localStorage.token`，随后通过 `window.location.href` 硬跳转登录页。Zustand内存状态和 `localStorage.auth` 中仍有旧 token，登录页又根据该状态跳转后台；新的接口再次401，形成持续刷新。

本次统一清理 token、auth、内存用户及菜单，让 AuthGuard 根据清理后的状态跳回登录页。启动时修复 token 与 auth 不一致的历史缓存；HTTP401、业务401采用同一处理；登录失败保留表单错误。失效处理校验请求携带的会话 token，防止并发或迟到401清除新登录。权限、菜单的迟到响应同样检查会话；主动退出保留原 token 请求注销，立即完成本地退出。

仅清理认证相关数据，不调用 localStorage.clear，不改变后端权限规则或会话有效期。

## 5. 真实数据验证

- 撤销前 `/admin/permissions` 返回 HTTP200、业务200；通过 `/admin/logout` 撤销本次新建会话后，同一 token 返回HTTP401。
- 浏览器保留旧状态重新加载一次，收到4个401响应（开发模式下权限/菜单请求），自动稳定停留 `/login`。从触发失效到重新登录，主文档累计只加载1次。
- 不清除浏览器存储、不注入 token，通过登录表单再次登录成功。访问敏感词管理，接口HTTP200、业务200，返回真实总数 **48,243**；期间无 pageerror。
- 再次主动退出正常；结束清理本次创建的会话。未修改敏感词及业务审核记录。
