# 推荐偏好候补与全池扫描 - 测试用例

创建日期：2026-10-10。关联账号：173****9764。范围：推荐候选查询，不修改保存的偏好、浏览额度或准入规则。

## 实施方案与测试策略

现有查询把目标城市、年龄和会员高级条件作为硬过滤，精确候选不足时直接结束。调整为目标城市精确匹配 → 已开启的周边城市精确匹配 → 其他符合准入条件的异性用户。各阶段保持最近登录时间与 ID 游标排序；候补阶段跳过前两个阶段覆盖的用户，防止跨页重复。单次请求仍最多查询三批、每批六十条，预算用完返回续扫游标；只有候选池实际结束才返回终态 `no_candidate`。客户端已有分页收集器继续拉取游标，直到补满当次额度或扫描结束。

保留账号正常、认证准入、双向拉黑、本人不再推荐、已喜欢、本周期已浏览排除和每日额度。偏好作为优先级保留，不清除家乡筛选。此处“全池”指所有符合上述平台规则的用户，不表示一次展示全部注册账号。

测试策略：现有 Controller 回归（L2）＋核心扫描规则单元测试（L3）＋部署后真实账号接口核对（L1）。不修改页面，不增加 UI 测试。生产核对仅登录、读取偏好与候选，不执行浏览、喜欢或保存偏好；读取候选会按既有逻辑记录 issued，但不扣浏览额度。

## 测试数据

单元测试使用独立模拟数据，覆盖 1,021 条候选、空生日/空登录时间、直辖市区县编码和偏好组合。线上使用用户指定的既有账号与源码配置的 API 地址，凭证仅留在运行进程内，不入库、不写日志。
